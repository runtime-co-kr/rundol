# 문서 계약과 표시 설정의 소유 경계

## 맥락

문서 계획에는 서로 다른 두 종류의 설정이 있다. 첫째는 어떤 문서가 required·recommended·onDemand·disabled인지, 생략한 내용은 어디에 남길지, 어느 시점에 위반을 차단할지 결정하는 프로젝트 의미 계약이다. 둘째는 Board가 문서 유형과 상태를 어떤 문구·설명·순서로 보여줄지 정하는 표현 설정이다.

둘을 하나의 Workspace JSON에 합치면 여러 프로젝트가 서로 다른 규모·위험·산출물 정책을 갖기 어렵다. 반대로 모든 것을 `project.md`에 넣으면 조직 공통 표시 문구를 반복하고, 사람을 위한 charter와 UI 표현 설정이 섞인다. AI와 CLI가 계약을 쉽게 발견하면서도 Board 표현은 계층적으로 재사용할 경계가 필요하다.

기능 구현 준비도와 추적성도 별도 설정 파일이나 인덱스 문서로 분리하면 정본이 중복된다. 기능 계약은 해당 설계·검증 문서가 소유하고, Board가 보여주는 준비 상태는 직접 ID와 링크에서 계산하는 파생값이어야 한다.

## 결정 기준

- 프로젝트를 복제하거나 독립 브랜치로 이동해도 의미 계약이 함께 이동해야 한다.
- CLI, AI 스킬과 Board가 별도 변환 없이 같은 계약을 읽어야 한다.
- Workspace는 여러 프로젝트에 공통인 화면 문구를 한 번만 정의할 수 있어야 한다.
- 프로젝트는 필요한 표시 키만 덮어쓰고 나머지는 상속해야 한다.
- 설정 변경이 기존 문서를 자동 삭제·이동하거나 의미를 바꾸면 안 된다.
- 약한 AI도 파일 위치와 책임을 이름만으로 구분할 수 있어야 한다.

## 선택지

| 선택지 | 장점 | 단점 | 위험 |
|---|---|---|---|
| Workspace 단일 JSON에 계약과 표현을 모두 저장 | 중앙 관리가 단순함 | 프로젝트 독립성과 브랜치 이동성이 낮음 | 공통 정책이 개별 프로젝트 작업을 과도하게 제한 |
| 프로젝트별 JSON에 계약과 표현을 모두 저장 | 기계 처리와 분리가 명확함 | 사람과 AI가 charter와 별도 파일을 함께 해석해야 함 | 계약·거버넌스 설명의 불일치 |
| `project.md`에 계약과 표현을 모두 저장 | 발견 지점이 하나임 | UI 문구가 charter를 오염시키고 공통값이 중복됨 | 표현 변경이 의미 계약 변경처럼 보임 |
| 의미 계약과 표현 설정 분리 | 책임과 변경 영향이 명확하고 상속 가능 | 설정 파일이 두 종류로 늘어남 | loader와 validation 계약을 유지해야 함 |

## 결정

2026-08-14, 프로젝트 책임자는 의미 계약과 표현 설정을 분리하기로 결정했다.

- 프로젝트별 문서 의미 계약은 `projects/<key>/project.md`의 revisioned `documentProfile`이 소유한다.
- `policy`, `omissions`, `enforcement`, AI 추천 문맥을 담는 `rules.after`는 CLI·스킬·Board가 공용 evaluator로 읽는다.
- `rules.after`는 작성 품질을 위한 추천 문맥이며 문서 생성·저장·동기화를 차단하지 않는다.
- Board 표현 설정은 schemaVersion 1 `board.json`이 소유한다. 적용 순서는 내장 기본값 → Workspace `projects/workspace/board.json` → 프로젝트 `projects/<key>/board.json`이다.
- `board.json`은 label, description, order만 바꿀 수 있고 문서 ID, kind, 저장 경로와 계약 의미를 바꾸지 않는다.
- Board는 프로젝트 계약을 revision 기반으로 편집할 수 있지만 Workspace 계약 상속은 도입하지 않는다.
- 구현 문서는 기능별 `atomic-v1`과 `functionIds`를 소유하고 여러 기능을 한 범위·행·수용 기준으로 묶지 않는다.
- 기능 추적성과 준비 수는 직접 문서·태스크 링크에서 계산하며 INDEX·카탈로그·추적표를 별도 정본으로 저장하지 않는다.
- Board는 계산 결과를 읽기 전용으로 가시화하고 CLI·공용 검사기의 준비도 판단을 재구현하지 않는다.

## 결과

- 긍정적 결과: 프로젝트 의미가 해당 프로젝트 브랜치와 함께 이동하고, AI·CLI·Board가 하나의 계약을 공유한다. 조직 공통 표시 문구는 Workspace에서 재사용하면서 프로젝트가 필요한 키만 덮어쓸 수 있다.
- 긍정적 결과: 기능 명세와 테스트 증거의 소유 문서가 명확하며 파생 추적 인덱스의 동기화 비용과 불일치를 피한다.
- 부정적 결과: 사용자는 `project.md`와 최대 두 위치의 `board.json`을 구분해야 하며, Board 설정 화면은 상속 출처를 설명해야 한다.
- 후속 작업: CLI·Board·스킬의 계약 용어를 계속 일치시키고, migration 문서에서 0.22.0 이전 프로젝트의 설정 위치를 안내한다.
- 재검토 조건: 조직 차원의 문서 정책 상속 요구가 반복되거나, 사용자 정의 문서 유형이 정규 계약에 포함되거나, Board가 중앙 다중 사용자 서비스로 확장될 때 이 결정을 다시 검토한다.
