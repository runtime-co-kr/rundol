# 실행 엔진의 경계와 인가 2계층 유지

## 맥락

Rundol의 상태는 도메인별로 나뉘어 있다. 공용 이벤트 원장이 일곱 종(lease, run, verdict, driver, decision, delegation, approval)이고 문서 번호 예약이 따로 있으며, 각 원장이 자기 fold를 갖는다. 문서와 태스크는 이벤트가 아니라 파일 자체가 정본이다.

이 분리는 엔진 내부에서는 타당하다. 도메인마다 무엇이 사실인지가 다르고, Git 병합 충돌을 줄이려면 Client별 샤드가 필요하다.

문제는 사용자와 에이전트가 보는 표면이다. "사람이 지금 처리해야 할 일"을 알려면 run fold, decision 원장, delegation 원장, approval 원장, Client 레지스트리, Git HEAD를 각각 읽고 다시 조합해야 한다. 하나의 사람 대기가 절차의 `human: true`, run의 `waiting_human`, decision의 질문, delegation의 권한, approval 또는 `run.forced`, 그리고 sync의 재계산에 흩어져 있다.

성숙한 워크플로 엔진(Conductor)의 사례를 검토했다. 그 엔진은 정의와 실행 인스턴스를 분리하고, 모든 작업을 하나의 실행 상태로 정규화하며, 사람 작업을 "승인"이 아니라 "외부 신호를 기다리는 대기 상태"로 다룬다. 전달은 at-least-once로 가정하고 멱등성을 작업자에게 지운다.

이 검토에서 두 갈래의 제안이 나왔다. 하나는 원장을 통합하자는 것이고, 다른 하나는 인가 판정을 하나의 함수로 합치자는 것이다. 후자는 "최우선"으로 제시됐다.

## 결정 기준

- 되돌리기 비용. 저장 형식과 공개 명령은 한 번 나가면 비싸고, 읽기 계층은 싸다.
- 근거의 출처. 정규화의 근거가 실사용인지 상상인지.
- 이미 고친 결함을 다시 만들지 않는 것.

## 선택지

1. 실행 엔진을 통째로 도입하거나 그 저장 구조를 복제한다.
2. 원장을 물리적으로 통합해 상태 저장소를 하나로 만든다.
3. 인가 판정을 단일 함수로 합쳐 쓰기 경로와 읽기 경로가 같은 답을 내게 한다.
4. 저장은 그대로 두고, 여러 원장을 읽어 공통 작업 항목으로 투영하는 계층만 더한다.

## 결정

### 실행 의미론만 가져오고 저장 구조는 가져오지 않는다

가져올 것은 정의와 실행 인스턴스의 분리, 전달이 중복될 수 있다는 가정, 엔진이 상태 전이만 책임진다는 역할 분리다. 이 셋은 이미 절차 revision 고정, `operationId`·`requestId`·request journal, 결정적 fold로 들어와 있다.

가져오지 않을 것은 중앙 API·DB·Queue·Index·Lock을 전제한 구조다. Rundol은 서버 없는 Git 기반 협업이 핵심이고, 그 전제를 바꾸면 남는 것이 없다. 그리고 그 엔진의 사람 작업 완료 API는 "외부 신호가 왔다"는 뜻이지 "유효한 사람이 승인했다"는 뜻이 아니다 — 사람 승인 정책은 Rundol이 더 엄격해야 한다.

### 원장은 물리적으로 합치지 않는다

합치면 Git 충돌과 결합도가 함께 커진다. 도메인마다 무엇이 사실인지가 다르고, Client별 샤드는 병합 충돌을 줄이려고 나눈 것이다. 통합해야 할 것은 파일이 아니라 상태 의미와 명령 표면이다.

### 공통 작업 항목 투영을 첫 조각으로 삼는다

여러 fold를 읽어 하나의 목록으로 내리는 읽기 전용 계층을 만든다. 저장하지 않는다. 저장하지 않으므로 틀렸을 때 지우면 되고, 원장을 건드리지 않으므로 되돌릴 것이 없다.

이것이 첫 조각인 이유는 진단이 정확하고 비용이 낮기 때문이다. 그리고 이 프로젝트가 정한 메타데이터 예산 — 관계는 한 방향만 저장하고 역방향은 계산한다 — 과 같은 방향이다.

### 상태 어휘 정규화는 실사용 이벤트가 쌓인 뒤에 한다

현재 저장소에 축적된 공유 이벤트는 문서 lease 한 건과 문서 번호 예약뿐이다. 코드가 지원하는 run·verdict·decision·approval 샤드는 비어 있다. 이 상태에서 상태 모델을 정규화하면 그 정규화의 근거가 실사용이 아니라 상상이 된다.

### 인가 2계층은 유지한다

이것이 이 기록의 핵심이다.

Rundol의 인가는 두 곳에 있고, 그것은 분산이 아니라 설계다.

- 쓰기 경로: 명령이 실행될 때 "이 행위자가 지금 이 일을 해도 되는가"를 묻는다.
- 읽기 경로: 원장에 이미 있는 이벤트를 보고 "이것은 기록된 시점에 인가되었는가"를 묻는다.

두 계층이 필요한 이유는 Git 병합으로 들어온 이벤트가 CLI를 지나지 않기 때문이다. 쓰기 경로만 있으면 다른 기계에서 만들어 병합한 이벤트는 아무 검사도 받지 않는다.

두 물음의 답은 다를 수 있고 달라야 한다. 승인자가 나중에 퇴사해 비활성이 되어도 그때의 승인은 유효했다. 현재 상태로 과거를 판정하면 되돌릴 수 없는 커밋이 영원히 차단된다 — 이 결함은 실제로 발생했고 이미 고쳤다. 그 판단은 지금 코드에 이렇게 남아 있다: 그때 그 승인이 유효했는지는 그때의 사실이고, 오늘의 상태가 바꾸지 못한다.

따라서 인가를 하나의 함수로 합치는 것은 이 구분을 담을 수 있을 때만 가능하다. 담으려면 "언제 기준으로 묻는가"가 인자로 들어와야 하고, 과거 시점을 물으려면 그 시점의 Client와 멤버 상태가 남아 있어야 한다. 지금 Client 레지스트리는 현재 상태만 갖는다. 즉 인가 통합의 진짜 전제는 레지스트리를 이벤트 소싱으로 바꾸는 것이며, 그것은 별도의 결정이다.

그래서 인가 통합은 최우선이 아니라 가장 나중이다.

## 결과

- 긍정: 저장 형식과 명령 표면을 건드리지 않으므로 이번 판의 검증 면적이 늘지 않는다. 통합의 첫 조각이 되돌리기 쉬운 읽기 계층으로 시작한다.
- 긍정: 인가 2계층을 유지하는 이유가 기록으로 남아, 다음에 "권한 판정이 흩어져 있다"고 읽고 합치려는 시도가 이미 고친 결함을 다시 만들지 않는다.
- 부정: 사용자와 에이전트는 당분간 원장별 상태를 그대로 본다. 대시보드와 협업 흐름의 복잡도는 투영 계층이 생길 때까지 남는다.
- 부정: 사람 결정과 승인이 상위 모델에서 하나로 보이지 않는다. 둘은 요청·선택지·대상·권한·응답자·위임·만료·근거를 공유하므로 합칠 수 있지만, 그 통합도 투영 계층 다음이다.
- 이름 충돌 주의: `rdl action`은 이미 "이 작업을 CLI로 할지 LLM으로 할지 기록한다"는 뜻으로 쓰이고 있다. 공통 작업 항목 명령을 만들 때 이 이름을 재사용하면 두 개념이 한 이름에 얹힌다.
- 임대 통합은 하지 않는다. 문서 임대와 Driver 임대는 모양이 비슷하지만 경합 대상이 다르고, Driver 임대는 소유 토큰 기반 fencing과 얽혀 있어 공통 모델로 올리면 fencing의 뜻이 리소스마다 달라진다. 화면에서 같은 줄로 보이는 것으로 충분하다.
