# 문서 편집을 블록 편집기로 올리고 원문 보존을 직렬화에 둔다

## 맥락

보드의 문서 편집은 Markdown 원문을 그대로 여는 `textarea`였다. 블록 단위로 다루는 편집 화면을 요구받았고, 후보는 기성 블록 편집기와 직접 구현 둘이었다.

어려운 쪽은 Markdown을 읽는 일이 아니라 다시 쓰는 일이다. 기성 WYSIWYG는 문서 전체를 AST로 읽고 전체를 다시 쓴다. 이 저장소에서 diff는 검토 수단이므로, 한 글자만 고쳐도 파일 전체가 바뀌는 저장은 기능이 아니라 손실이다. 저장 경로가 CRLF와 frontmatter 뒤 빈 줄까지 되살리는 이유가 그것이다.

측정은 후보 중 Markdown을 모델로 삼는 Milkdown/Crepe으로 했다. 정본 문서를 한 글자도 고치지 않고 열었다 저장한 결과다.

| 문서 | 바뀐 줄 | 본문 wikilink |
|---|---|---|
| ADR-005 | 41 | 1 → 0 |
| MOD-002 | 61 | 2 → 0 |

`rdl check --strict`는 두 경우 모두 오류 0으로 통과했다. 링크가 깨진 것이 아니라 없는 것이 되기 때문이다 — 링크 판정은 `[[`로 시작하는 값을 찾는데 `\[\[`에는 `[[`가 연속으로 나오지 않는다. 추적성은 frontmatter의 `related`와 기능 ID로 계산하므로 본문 링크 소실을 보지 못한다.

손상 지점은 파서가 아니라 직렬화기다. 파서는 `[[…]]`를 글자 그대로 담아 아무것도 잃지 않는다. 그 글자를 다시 쓸 때 `[`가 링크로 오해될 수 있어 이스케이프된다. 직렬화기 입장에서는 옳은 동작이며, 문제는 "이건 평문이 아니라 링크다"를 아무도 알려 주지 않았다는 것이다.

## 결정 기준

- 손대지 않은 블록의 바이트가 살아남아야 한다. diff가 검토 수단이기 때문이다.
- 본문을 직접 고칠 수 있어야 한다. 블록을 하나씩 열어 고치는 방식은 요구를 채우지 못한다.
- Obsidian 고유 문법과 정본 표, mermaid가 저장을 지나며 상하지 않아야 한다.
- 발행되는 명령줄 패키지의 실행 의존성이 늘지 않아야 한다.
- 라이선스가 Apache-2.0 배포와 호환되고 고지 의무를 지킬 수 있어야 한다.

## 선택지

| 선택지 | 장점 | 단점 | 위험 |
|---|---|---|---|
| Crepe 그대로 도입 | 완성품이라 붙이면 끝 | 저장이 문서 전체를 다시 씀 | 본문 링크가 조용히 사라지고 검사가 통과 |
| Crepe 코드를 복사해 고침 | 원하는 대로 손댈 수 있음 | 의존성은 그대로 따라오고 유지보수를 떠안음 | 상류 수정이 닿지 않아 오래되면 고립 |
| ProseMirror 위에 직접 구현 | 직렬화기를 우리가 가짐 | 만들 것이 많음 | 만든 만큼 우리가 지켜야 함 |
| 도입하지 않음 | 비용 없음 | 요구를 채우지 못함 | — |

번들과 라이선스도 함께 쟀다.

| | 번들 | 라이선스 |
|---|---|---|
| Crepe | JS 2,674KB + CSS 1,477KB | 245개 패키지, 8종 |
| ProseMirror 직접 | JS 356KB + CSS 1KB | 96개 패키지, 전부 MIT |

Crepe의 기능 플래그는 런타임이라 끄더라도 번들이 줄지 않는다.

## 결정

2026-08-21, ProseMirror 위에 직접 만들고 원문 보존을 직렬화 단계에 둔다.

- 불러올 때 최상위 블록마다 그것이 나온 원문 조각을 노드를 키로 기록한다.
- 저장할 때 그 노드가 그대로면 조각을 그대로 쓰고, 아니면 그 블록만 다시 직렬화한다.
- 되돌리기는 내용이 같은 새 노드를 만들므로, 객체가 다르면 내용으로 한 번 더 찾는다.

이것이 성립하는 근거는 ProseMirror 문서가 영속 자료구조라는 점이다. 한 블록을 고치면 새 문서가 생기지만 나머지 블록은 같은 객체로 재사용된다. 순서만 바꾸면 모든 블록이 그대로이므로 정렬은 조각의 자리 교환이 된다.

Obsidian 링크는 편집기의 1급 노드로 세운다. 자산 참조 `![[…]]`는 파서 확장이 다루지 않아 글자에서 직접 뽑는다. 이스케이프를 막으려고 직렬화기를 손대지는 않는다 — 손대면 진짜 대괄호가 든 평문이 깨진다.

의존성은 개발 의존성이다. 배포물은 번들 하나이므로 발행 패키지의 실행 의존성은 늘지 않는다. 번들은 저장소에 두지 않고 설치와 배포 준비 두 자리에서 만든다.

## 결과

- 긍정적 결과: 본문을 직접 고치면서도 손대지 않은 블록의 바이트가 살아남는다. 정본 문서 전체가 열었다 저장에서 바이트 동일이며 시험이 그것을 지킨다. 앞서 필수라고 보았던 정본 Markdown 포매터 도입이 불필요해졌다 — 그 요구는 직렬화기를 남이 소유해서 생긴 것이었다.
- 부정적 결과: 보드에 빌드 단계가 생긴다. 편집 표면의 동작을 상류가 아니라 이 저장소가 책임진다. 번들에 들어간 제3자 코드의 고지를 배포마다 만들어야 한다.
- 후속 작업: 편집기 왕복은 시험이 지키지만 화면 동작은 사람이 확인한다. 이스케이프된 링크를 `RDL-LINK-007`이 잡으므로, 다른 도구가 문서를 상하게 하면 그 흔적이 검사에 남는다.
- 재검토 조건: ProseMirror 상류가 영속 자료구조 성질을 바꾸거나, 편집 표면 유지 비용이 상류를 따라가는 비용을 넘어설 때 다시 본다.
