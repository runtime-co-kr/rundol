# 에이전트 실행 격리와 태스크 클레임

## 맥락

CLI가 저장소를 감시하다가 조건이 맞으면 외부 코딩 도구를 호출하고, 그 파이프라인을 반복해서 돌리는 실행 방식을 도입하려 한다. 실행 주체는 한 대가 아니라 여러 사람의 장비에 있는 여러 Client다.

현재 구조는 이 방식을 두 곳에서 지탱하지 못한다.

태스크에는 소유를 주장할 수단이 없다. 편집 lease는 `documentId`에만 걸리고 대상 문서가 실제로 존재해야 하므로 태스크에는 걸 수 없다. 태스크가 Client별 샤드에 저장되어 서로 다른 파일에 쓰이는 탓에 두 실행이 같은 태스크를 집어도 파일 충돌조차 나지 않고 조용히 중복 작업한다. 감시자를 한 대만 돌릴 때는 드러나지 않고 두 번째를 띄우는 순간 나타난다.

작업 공간에도 격리가 없다. 저장소 루트의 worktree는 하나이므로 한 실행이 브랜치를 바꾸면 같은 순간 작업 중인 다른 실행의 파일이 통째로 바뀐다. 브랜치를 나누는 것만으로는 해결되지 않는다.

결정하지 않으면 감시자를 한 대로 제한해야 하고, 그 제한은 구조가 아니라 운영 관례로만 유지되므로 언젠가 깨진다.

## 결정 기준

- 여러 장비에 걸친 조율이 성립할 것. 한 프로세스나 한 장비 안에서만 동작하는 잠금은 채택하지 않는다.
- 새로 검증해야 하는 메커니즘의 수가 적을 것. 이미 계약이 정의되고 사용 중인 수단을 우선한다.
- 실패가 드러날 것. 격리나 클레임이 성립하지 않는 상황에서 조용히 넘어가지 않는다.
- 실행 주체가 죽어도 자동으로 회수될 것. 사람이 손으로 풀어야 하는 상태를 만들지 않는다.
- 사람의 문서 작업 흐름을 바꾸지 않을 것.

## 선택지

| 선택지 | 장점 | 단점 | 위험 |
|---|---|---|---|
| worktree 격리 + 공유 태스크 클레임 | 코드 충돌과 중복 실행을 각각 맞는 수단으로 막는다. 두 수단 모두 Git이 이미 보장한다 | 클레임에 원격 왕복이 필요하다 | 원격이 닿지 않으면 클레임할 수 없다 |
| 공유 worktree에서 실행 | 구현할 것이 없다 | 실행을 둘 이상 돌릴 수 없다 | 감시자 증설이 구조적으로 막힌다 |
| 프로세스 단위 큐로 직렬화 | 왕복이 없고 빠르다 | 한 장비 안에서만 유효하다 | 다른 장비의 실행을 전혀 보지 못한다 |
| lease를 태스크로 확장 | 만료 회수가 계약에 이미 있다 | 재생·만료·경합 로직을 새로 검증해야 한다 | 검증 부담이 도입 시점을 늦춘다 |

## 결정

**코드 작업은 실행마다 전용 worktree와 브랜치로 격리하고, 태스크는 공유 브랜치에 두어 Git push 경합을 클레임으로 사용한다.** 2026-08-14, MEMBER-001 결정.

격리와 공유의 방향이 반대인 것이 핵심이다. 코드는 서로 보이지 않아야 충돌하지 않고, 태스크는 서로 보여야 중복을 막을 수 있다. 태스크까지 격리하면 클레임이 성립하지 않는다.

### 코드 격리

실행마다 전용 브랜치를 현재 코드 브랜치에서 분기하고 별도 worktree에 펼친다. 저장소 루트의 체크아웃은 건드리지 않는다. 실행이 끝나면 브랜치 이름, base 대비 앞선 커밋 수, 워킹트리의 미저장 변경 여부를 반환한다. 이 세 값은 실행 주체의 보고가 아니라 Git으로 재확인할 수 있는 사실이므로 완료 주장을 검증하는 근거가 된다.

병합은 자동으로 하지 않는다. 사람이 브랜치를 검토하고 병합한다. 격리는 병합 비용을 없애는 수단이 아니라 검토 지점까지 미루는 수단이다.

worktree를 만들 수 없는 환경에서는 공유 작업 공간으로 물러서지 않고 오류로 중단한다. 격리되지 않은 실행이 격리된 것처럼 보이는 상태를 허용하지 않는다.

### 태스크 클레임

클레임은 태스크 하나당 파일 하나로 기록하고 태스크 상태 변경과 같은 커밋에 담아 push한다. push가 성공하면 클레임을 얻고, 거부되면 최신 이력을 받아 다시 확인한다. 다른 실행이 이미 잡았으면 포기하고 다른 태스크로 넘어간다.

ref 갱신의 성패는 원격이 판정하므로 이 경합은 장비 경계를 넘는다. 태스크마다 파일이 다르므로 서로 다른 태스크를 잡는 실행은 방해받지 않고, 같은 태스크를 잡을 때만 충돌한다. 클레임을 태스크 샤드 안에 두면 다른 태스크를 잡아도 같은 샤드면 충돌하므로 샤드와 분리한다.

클레임에는 실행 주체와 만료 시각을 남긴다. 만료가 지나면 다른 실행이 회수할 수 있다. push 직후 중단된 실행이 태스크를 영구히 점유하지 못하게 하는 장치이며, 이것이 없으면 클레임은 사람이 손으로 푸는 상태가 된다.

### 태스크 출처 고정

태스크에 생성 시점의 문서 브랜치 revision을 기록한다. 문서가 먼저 확정되고 태스크가 나오는 순서를 지키더라도, 실행 브랜치가 며칠 사는 동안 원본 요구사항이 움직일 수 있다. 이 값이 없으면 병합 시점에 그 구현이 어느 시점의 명세를 따랐는지 판정할 근거가 없다.

실행 시점의 도구와 시각은 태스크에 두지 않는다. 태스크는 하나지만 실행은 반복되므로 태스크 필드에 담으면 마지막 시도만 남는다. 시도별 기록은 별도 append-only 이벤트가 담당하며 그 형식은 이 문서의 범위 밖이다.

### 태스크 종류 구분

태스크에 산출물이 문서인지 코드인지를 나타내는 종류를 둔다. 값은 두 가지이며, 이 필드의 임무는 분류가 아니라 실행 주체를 가르는 것이다. 값이 늘어나면 어느 쪽으로 분류할지 다투게 되는데 그 구분은 실행 주체를 바꾸지 않는다.

종류가 없는 태스크는 문서 작업으로 취급한다. 기존 태스크에는 이 필드가 없으므로, 반대로 정하면 표시되지 않은 태스크를 실행 주체가 집어 문서를 고칠 수 있다. 판단할 수 없을 때 사람에게 가는 쪽이 안전한 기본값이다.

문서 작업 태스크는 프로젝트 문서 브랜치에서 사람이 수행하며 격리하지 않는다. 사람이 같은 문서를 병렬로 고쳐야 하는 경우는 정규 문서의 하위 번호를 만들지 않고 비정규 노트로 제안한 뒤 정본 오너가 승격한다.

## 결과

- 긍정적 결과: 실행 주체를 여러 장비에서 늘려도 코드 충돌과 중복 실행이 각각 막힌다. 두 수단 모두 Git이 이미 보장하므로 새로 검증할 저장 형식이 클레임 파일 하나로 줄어든다. 완료 주장이 Git으로 재확인 가능한 값으로 표현된다. 문서 작업 흐름은 그대로 유지된다.
- 부정적 결과: 클레임에 원격 왕복이 필요하므로 로컬만으로는 실행을 시작할 수 없다. 로컬 우선 원칙의 예외 지점이며 오프라인에서는 단일 실행으로 제한된다. 클레임 획득에 수 초가 걸리므로 짧은 작업을 대량으로 처리하는 용도에는 맞지 않는다. 원격 저장소가 조율의 단일 장애점이 된다.
- 후속 작업: 클레임 파일의 필드와 만료 규칙, 태스크의 revision·종류 필드, 실행 이벤트 형식을 각각 요구사항과 검증으로 정의한다. worktree를 만들 수 없는 환경의 오류 처리를 명시한다. 기존 태스크의 종류 필드 부재를 문서 작업으로 해석하는 규칙을 마이그레이션에 남긴다.
- 재검토 조건: 오프라인 실행이 필요해지거나, 클레임 왕복이 처리량의 병목이 되거나, 실행이 사람 검토 없이 병합되어야 하는 요구가 생기면 다시 판단한다.
