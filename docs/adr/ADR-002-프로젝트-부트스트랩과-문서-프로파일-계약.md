# 프로젝트 부트스트랩과 문서 프로파일 계약

## 맥락

기존 Rundol CLI는 신규 Workspace 생성과 원격 Workspace 연결을 각각 `rdl init`, `rdl attach`로 분리한다. 사용자는 명령을 선택하기 전에 저장소에 Rundol ref가 있는지 직접 알아야 하며, 로컬 manifest나 worktree가 일부만 남은 상태를 init의 정상 재진입으로 복구할 수 없다.

문서 체계도 모든 유형을 지원하지만 프로젝트 성격에 따른 선택 정책이 없다. `PRD`, `ARC`, `GLS`는 `docs/` 루트에, 다른 유형은 하위 폴더에 생성되어 동일 유형의 물리 위치가 하나의 규칙으로 설명되지 않는다.

프로젝트 규모만으로 문서세트를 결정하거나 모든 템플릿을 미리 생성하면 불필요한 문서와 placeholder가 늘어난다. 반대로 문서 선택을 AI 스킬의 비구조화된 판단에만 맡기면 CLI와 사람, 다른 AI 클라이언트가 같은 결론을 재현할 수 없다.

결정은 다음 두 요구사항을 함께 만족해야 한다.

- `REQ-001`: 기존 상태를 먼저 발견하고 연결·복구하거나 없을 때만 새로 만드는 멱등적 부트스트랩
- `REQ-002`: 프로젝트 특성에 따른 명시적 문서 정책, 선택적 문서 생성과 canonical 경로

## 결정 기준

1. 기존 로컬·원격 정본을 신규 프로젝트로 오인하거나 덮어쓰지 않아야 한다.
2. 사람용 guided 흐름과 자동화용 비대화형 흐름이 같은 상태와 정책 결과를 만들어야 한다.
3. 프로젝트 문서 정책은 정본 문서와 같은 Git 이력에서 변경·복구할 수 있어야 한다.
4. 정책을 확인하기 위해 별도 중앙 서비스나 공급자별 AI 설정이 필요하지 않아야 한다.
5. 모든 문서를 미리 생성하지 않고도 누락된 필수 문서와 다음 행동을 결정할 수 있어야 한다.
6. 신규 문서의 물리 경로가 유형별로 결정적이어야 하며 기존 문서는 비파괴적으로 이전할 수 있어야 한다.
7. 기존 `rdl attach`, 문서 ID, 실제 파일명 Wiki link와 프로젝트별 branch 소유권을 가능한 한 보존해야 한다.

## 선택지

| 선택지 | 장점 | 단점 | 위험 |
|---|---|---|---|
| 생성과 연결 명령을 계속 분리 | 구현 변경이 작고 현재 CLI와 동일하다. | 사용자가 저장소 상태를 먼저 해석해야 하고 init 재진입이 복구 수단이 되지 못한다. | 기존 원격 프로젝트를 새 프로젝트로 오인하거나 잘못된 명령을 선택할 수 있다. |
| 프로젝트 규모만 선택해 고정 문서세트 생성 | 질문 수가 적고 구현이 단순하다. | 작은 고위험 서비스와 큰 단순 도구를 구분하지 못하며 빈 문서를 대량 생성한다. | 형식 준수만 남고 실제 위험·설계 관점이 누락된다. |
| AI 스킬이 매번 문서세트를 자유롭게 판단 | 프로젝트 설명을 유연하게 해석할 수 있다. | 같은 입력도 클라이언트·모델별 결과가 달라지고 CLI 검증 기준이 없다. | 정책 drift와 불필요한 전체 문서 로딩이 발생한다. |
| 상태 발견 bootstrap과 구조화된 문서 정책 결합 | 사람과 자동화가 같은 상태·정책 계약을 사용하고 기존 정본을 먼저 보호한다. | 상태 모델, profile schema, migration과 테스트가 추가된다. | 초기 구현 범위가 커지므로 단계별 호환 전략이 필요하다. |

문서 정책 저장 위치는 다음 대안을 비교했다.

| 위치 | 장점 | 단점 |
|---|---|---|
| Workspace의 `project-<key>.yaml` | 프로젝트 연결 전에도 중앙 Registry에서 조회할 수 있다. | 프로젝트 문서와 정책이 다른 branch에 있어 변경 원자성과 소유권이 분리된다. |
| 별도 프로젝트 로컬 YAML | 기계 판독이 쉽고 project branch가 소유한다. | 프로젝트 계약 파일이 늘고 `project.md`와 일부 의미가 중복된다. |
| `project.md` frontmatter | 기존 고정 진입점과 같은 branch·commit에서 정책을 소유하고 사람과 도구가 함께 읽을 수 있다. | 중첩 YAML parsing과 schema migration을 구현해야 한다. |

## 결정

2026-08-13에 다음 계약을 채택한다.

### 상태 발견 기반 부트스트랩

1. `rdl init`을 Rundol 저장소의 기본 부트스트랩 진입점으로 사용한다.
2. init은 쓰기 전에 로컬 manifest·ref·worktree와 선택 remote의 `rundol/workspace`, 프로젝트 Registry와 프로젝트 ref를 발견한다.
3. 발견 결과는 `created`, `attached`, `repaired`, `already-connected`, `needs-selection`, `conflict` action으로 정규화한다.
4. 원격 프로젝트가 하나이면 연결하고, 여러 개이면 guided 선택 또는 비대화형 `needs-selection`을 사용한다.
5. `--json` 또는 비대화형 실행은 stdin을 기다리지 않는다. 자연어 인터뷰는 명시적인 `--guided`에서만 수행한다.
6. 기존 Rundol이 없고 신규 의도가 명확할 때만 Workspace와 프로젝트를 생성한다.
7. `rdl attach`는 명시적인 저수준 연결 명령으로 유지하되 init과 동일한 발견·연결 내부 서비스를 사용한다.
8. 발견과 attach는 push하지 않으며 인증·DNS·TLS 실패를 원격 ref 부재로 해석하지 않는다.

### 프로젝트 문서 프로파일

1. `lean`, `product`, `service`, `platform`, `assured`를 버전이 있는 내장 profile로 제공한다.
2. profile은 초기 기본값이고 UI, data, API, component, operations, security·regulation, terminology 특성이 유형별 정책을 조정한다.
3. 최종 문서 정책은 모든 정규 유형을 `required`, `recommended`, `onDemand`, `disabled` 중 정확히 하나로 분류한다.
4. 정책은 `project.md` frontmatter가 소유한다. 별도 로컬 config나 Workspace Registry에 같은 정책을 복제하지 않는다.
5. frontmatter에는 최소한 profile 이름·schema version·선택 특성과 유형별 정책을 저장한다.

```yaml
documentProfile:
  schemaVersion: 1
  name: service
  traits:
    - api
    - data
    - operations
  policy:
    required: [PRD, REQ, API, RUN]
    recommended: [ARC, MOD, TST]
    onDemand: [SCR, ADR, GLS]
    disabled: []
```

6. Git commit 이력이 정책 변경 이력을 소유한다. 별도 질문·응답 전문을 정본으로 중복 저장하지 않고, 선택 특성과 최종 정책이 결정 근거가 된다.
7. profile 선택은 문서를 일괄 생성하지 않는다. CLI는 누락된 required·recommended 유형과 생성 명령을 결과로 제공한다.
8. 정책 변경은 기존 문서를 삭제하지 않는다. disabled로 바뀐 기존 문서는 검토 대상으로 남긴다.
9. 거버넌스 스킬은 인터뷰와 추천 근거를 담당하고 CLI는 schema 검증, 정책 저장과 결정적 결과 생성을 담당한다.

### 문서 경로와 이전

1. `project.md`만 프로젝트 루트에 둔다.
2. 신규 정규 문서는 `REQ-002`가 정의한 유형별 canonical 하위 폴더에만 생성한다.
3. 기존 root 또는 legacy 폴더 문서는 계속 읽되 `rdl check --structure`에서 이전 대상으로 보고한다.
4. 경로 이전은 별도 dry-run과 apply 단계로 수행한다. init, attach, profile 변경 중에는 문서를 자동 이동하지 않는다.
5. migration은 실제 파일명 Wiki link와 frontmatter related를 함께 갱신하고, 전체 strict 검사가 실패하면 원래 경로와 byte로 복원한다.
6. 동일 ID가 두 위치에 있으면 자동 병합하거나 한쪽을 선택하지 않고 중복 정본 오류를 반환한다.

### 단계적 구현

다음 순서로 호환 경계를 확장한다.

1. 공통 Rundol 상태 발견기와 action 결과
2. idempotent init과 attach 내부 경로 통합
3. `project.md` documentProfile schema와 비대화형 profile 구성
4. guided 인터뷰와 거버넌스 스킬 연동
5. 신규 문서 canonical 경로 적용
6. legacy 구조 진단과 비파괴 migration

각 단계는 이전 단계의 저장 형식과 CLI 결과를 회귀 테스트한 뒤 진행한다.

## 결과

- 긍정적 결과:
  - 사용자는 저장소 상태를 미리 해석하지 않고 `rdl init`에서 생성·연결·복구 경로를 얻는다.
  - 기존 Rundol 정본이 신규 seed보다 항상 먼저 고려된다.
  - 사람, CLI와 AI 클라이언트가 같은 문서 policy schema를 사용한다.
  - 문서 유형이 많은 프로젝트도 작업과 관련된 2~5개 문서를 우선 컨텍스트로 선택할 수 있다.
  - 같은 유형의 신규 문서는 항상 같은 경로에 생성된다.
- 부정적 결과:
  - init의 상태 모델과 테스트 조합이 증가한다.
  - `project.md` frontmatter parser가 중첩 schema와 migration을 지원해야 한다.
  - 기존 root 문서에 대해 한동안 legacy 읽기와 canonical 쓰기를 함께 지원해야 한다.
  - init 직후 required 문서가 없으면 strict 검사가 누락을 보고할 수 있으므로 다음 행동 안내가 필요하다.
- 후속 작업:
  - `ARC-001`에 bootstrap service, profile evaluator와 migration 경계를 반영한다.
  - `MOD-001`에 documentProfile schema와 상태 불변식을 반영한다.
  - `TST-001`에 상태 발견, profile 결정성, 경로 이전과 rollback 시나리오를 추가한다.
  - `DOCUMENT-STANDARD.md`와 CLI 문서를 canonical 경로·정책 의미에 맞게 개정한다.
  - GitHub Epic #1을 단계적 구현 이슈로 분리한다.
- 재검토 조건:
  - project policy를 연결 전에 반드시 조회해야 하는 기능이 생겨 Workspace Registry 복제가 불가피해질 때
  - `project.md` frontmatter의 중첩 schema가 주요 Markdown 도구와 정보 손실 없이 왕복되지 않을 때
  - 문서 유형 또는 profile 수가 증가해 정적 policy 집합으로 표현하기 어려워질 때
  - canonical 경로 migration이 Git 이력·Wiki link를 안정적으로 보존하지 못할 때
