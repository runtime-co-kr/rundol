# 화면 전이 소유권과 파생 뷰 배달 경계

## 맥락

`diagram-v1`은 `MOD`의 `관계` 섹션에 `erDiagram`을 두고 표를 정본으로 삼는 규약을 확정했다. 문서 하나 안의 다이어그램은 이것으로 계약되었지만 두 가지가 남았다.

첫째, 화면 간 전이에 소유 문서가 없다. `SCR`은 `진입`에 들어오는 경로를 산문으로 적을 뿐 나가는 전이와 대상 화면의 식별자를 선언하지 않는다. 그래서 어떤 화면에서 어디로 갈 수 있는지 알려면 사람이 모든 `SCR`의 `진입`을 역방향으로 읽어야 하고, 화면 흐름 그래프를 계산으로 만들 수 없다. `TST`의 시나리오에서 전이를 역산하는 방법은 대표 경로만 밟기 때문에 아무 시나리오도 지나지 않은 간선이 그래프에서 사라지고, 무엇이 빠졌는지조차 알 수 없다.

둘째, 여러 문서를 합친 다이어그램을 사람이 읽을 자리가 없다. 데이터 구조를 검토하려면 여러 `MOD`의 `erDiagram`을 함께 봐야 하고 화면 흐름도 마찬가지다. 그러나 이 뷰를 사람이 작성해 저장소에 두면 각 문서의 표와 갈라지고, 어느 쪽이 맞는지 판정할 규칙이 없다. 이는 별도 인덱스·카탈로그·추적표를 정본으로 만들지 않는 원칙이 금지하는 것과 같은 구조다.

Board 렌더링만으로 두 번째 문제를 해결하려 하면 세 번째 문제가 생긴다. `Obsidian`을 편집 클라이언트로 쓰는 사용자는 문서를 파일로 읽으며, Board를 열지 않는다. 문서 하나 안의 Mermaid 블록은 `Obsidian`이 그대로 렌더링하므로 문제가 없지만, Board 안에서만 계산되는 합성 뷰는 이 사용자에게 도달하지 않는다. 검사 결과인 추적성과 달리 다이어그램은 문서를 읽는 흐름 안에 있어야 값어치가 있는 읽기 보조물이다.

## 결정 기준

- 사람이 편집할 수 있는 같은 사실의 사본이 둘 이상 생기면 안 된다.
- 화면 흐름 그래프는 표본이 아니라 각 문서의 선언에서 빠짐없이 계산되어야 한다.
- 파생 산출물은 삭제한 뒤 정본 파일에서 같은 결과로 다시 만들 수 있어야 한다.
- 과거 commit에서도 그 시점의 파생 산출물을 재현할 수 있어야 한다.
- CLI, Board와 `Obsidian` 사용자가 같은 정본에서 같은 그림에 도달해야 한다.
- 새 규약은 기존 문서를 자동으로 이동·삭제하거나 의미를 바꾸지 않아야 한다.

## 선택지

### 화면 전이의 소유 문서

| 선택지 | 장점 | 단점 | 위험 |
|---|---|---|---|
| 출발 `SCR`이 나가는 전이를 선언 | 문서 단위로 완결되어 누락을 검사할 수 있음 | `SCR`에 섹션이 하나 늘어남 | 화면 내부 상태 변화와 경계가 흐려질 수 있음 |
| `TST` 시나리오에서 역산 | 새 선언이 필요 없음 | 밟지 않은 간선이 사라지고 누락을 알 수 없음 | 불완전한 그래프를 완전한 것으로 오해 |
| 프로젝트 계층에 흐름 문서를 신설 | 한 곳에서 전체를 봄 | `SCR`과 갈라지는 두 번째 정본 | 화면 변경 시 아무도 그림을 고치지 않음 |

### 합성 뷰의 배달

| 선택지 | 장점 | 단점 | 위험 |
|---|---|---|---|
| 저장하지 않고 요청 시 계산 | 편집 지점이 없어 갈라질 수 없음 | `Obsidian` 사용자에게 도달하지 않음 | 도구에 따라 볼 수 있는 정보가 달라짐 |
| Git 추적 파일로 생성 | 모든 도구가 읽음 | 사람이 고칠 수 있고 commit에 남음 | 두 번째 정본과 무인덱스 원칙 위반 |
| Git 비추적 생성 파일 | 모든 도구가 읽고 저장소에 남지 않음 | stale 관리와 재생성 시점이 필요함 | 오래된 파일을 최신으로 오해 |

## 결정

2026-08-14, 프로젝트 책임자는 다음과 같이 결정했다.

- 화면 간 전이는 출발 `SCR`이 소유하고 `전이` 섹션에서 트리거, 조건과 대상 `SCR` 식별자를 선언한다.
- 다른 `SCR`로 이동하면 `전이`, 같은 화면 안에서 표시가 바뀌면 `상태`가 정본이다. 한 사실을 두 섹션에 적지 않는다.
- `SCR`은 `전이` 섹션에 Mermaid `flowchart`를 두며 이 블록은 표에서 파생한 보조 뷰다. 트리거·조건·대상의 정본은 `전이` 표다.
- 여러 문서를 합친 다이어그램은 사람이 작성하지 않는다. 각 문서의 선언에서 계산하며 그 결과를 정본으로 취급하지 않는다.
- 합성 결과는 저장소에 commit하지 않는다. Board는 요청 시 렌더링하고, `Obsidian` Vault에는 Git 비추적 생성 파일로 배달한다.
- 생성 파일은 점으로 시작하지 않는 Vault 경로에 둔다. `Obsidian`이 점으로 시작하는 폴더를 인덱싱하지 않아 기존 `.rundol/` 파생 영역은 이 목적에 쓸 수 없다.
- 생성 파일은 정규 문서가 아니다. 문서 목록, 추적성 계산과 필수 메타데이터 검사에 포함하지 않는다.
- 합성기는 결정적이다. 노드와 간선을 식별자 사전순으로 정렬하고, 생성 시각처럼 매번 달라지는 값은 본문에 넣지 않는다.
- 생성 파일은 frontmatter에 입력 문서 식별자와 그 시점 commit을 기록한다. 현재 정본과 어긋나면 `rdl check`가 경고한다.
- 어긋남은 기록한 commit이 아니라 다이어그램 본문으로 판정한다. commit만 움직인 경우는 어긋난 것이 아니고, 사람이 생성 파일을 손으로 고친 경우는 어긋난 것이다. commit 기준으로 보면 문서를 고치고 commit하지 않은 동안을 최신으로 오해하고, 손으로 고친 생성 파일을 잡지 못한다.
- `rdl check`는 합성을 직접 수행해 문서 하나만으로는 보이지 않는 결함을 보고한다. 합성을 시도하는 것 자체가 정합성 검사다.
- 프로젝트 연결 시점에 생성 파일을 만들되, `.gitignore`에 항목이 없는 기존 프로젝트는 건너뛴다. 연결이 추적 파일을 말없이 바꾸면 clone 직후 워킹트리가 더러워지고 사용자가 그 변경을 의도하지 않았다. 명시적인 생성 명령 한 번이 항목을 추가하며 이후 연결부터 자동 생성한다.
- 같은 입력으로 두 번 생성한 결과가 바이트 단위로 같은지 회귀 테스트로 보증한다.

## 결과

- 긍정적 결과: 화면 흐름 그래프가 각 `SCR`의 선언에서 빠짐없이 계산되고, 존재하지 않는 화면을 가리키는 전이와 어떤 시나리오도 밟지 않는 간선을 검사할 수 있다.
- 긍정적 결과: 합성 뷰에 편집 지점이 없으므로 정본과 갈라질 수 없다. 정본이 Git에 있고 합성기가 결정적이므로 과거 commit에서도 그 시점의 그림을 재현한다.
- 긍정적 결과: CLI, Board와 `Obsidian` 사용자가 같은 계산 결과에 도달하며 배달 경로만 다르다.
- 부정적 결과: 생성 파일은 clone 직후 존재하지 않으므로 연결·갱신 시점에 만들어야 하고, 정본이 바뀌면 stale 상태를 감지해 알려야 한다. 요청 시 계산만 하는 방식에는 없던 비용이다.
- 부정적 결과: `SCR` 작성자는 `전이`와 `상태`의 경계를 판단해야 하며, 초기에는 같은 사실을 양쪽에 적는 실수가 나올 수 있다.
- 부정적 결과: `.gitignore`에 항목이 없는 기존 프로젝트는 연결만으로는 생성 파일을 얻지 못하고 명시적인 생성 명령이 한 번 필요하다. 연결이 추적 파일을 바꾸지 않기 위해 받아들인 비용이다.
- 후속 작업: `SCR` 템플릿, 문서 표준, 거버넌스 스킬과 `catalog.diagrams`의 용어를 일치시킨다.
- 후속 작업: Board에 프로젝트 단위 합성 뷰 화면을 만든다. 문서 하나 안의 Mermaid는 Board가 이미 렌더링하므로 `SCR`의 `전이`는 지금도 보이지만, 여러 문서를 합친 뷰는 아직 CLI와 Vault 생성 파일로만 도달한다.
- 재검토 조건: 화면 외의 노드를 같은 그래프에 요구하거나, 생성 파일을 commit해야 하는 배포 요구가 생기거나, `Obsidian`이 점으로 시작하는 폴더를 인덱싱하게 되면 이 결정을 다시 검토한다.
