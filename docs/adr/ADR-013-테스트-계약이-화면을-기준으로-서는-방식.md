# 테스트 계약이 화면을 기준으로 서는 방식

## 맥락

Rundol을 웹 개발 프로젝트에서 쓰는 것을 전제로 하면, 테스트 문서는 화면을 기준으로 서는 편이 자연스럽다. 사용자가 실제로 밟는 경로가 화면에 있고, 입력값과 기대값의 재료도 SCR의 `바인딩`과 `상태`에 있다. [[ADR-006-화면-전이-소유권과-파생-뷰-배달-경계|ADR-006]]이 정한 경계도 이미 그 방향이다 — 화면은 전이를 소유하고, 한 경로를 끝까지 밟은 기대 결과는 전이가 아니라 TST 시나리오다. 관계는 설계되어 있고 강제만 없다.

가장 단순한 강제는 TST의 필수 관계를 REQ에서 SCR로 바꾸는 것이다. 그런데 그렇게 하면 세 가지가 즉시 깨진다.

Rundol 자신이 첫 번째다. 이 프로젝트의 `documentProfile`은 TST를 required로 두고 SCR을 disabled로 둔다. disabled 유형은 생성이 거부되므로 유효한 TST를 만들 방법이 없어지고, 기존 TST 문서 전부가 위반이 된다. 자기 자신에게 적용할 수 없는 계약이 된다.

프로필도 깨진다. SCR이 보장되는 프리셋은 `product`와 `assured`뿐이고, `lean`·`service`·`platform`에서는 onDemand다. 웹 서비스 프로젝트가 이름만 보고 `service`를 고르면 같은 상태가 된다.

마지막이 가장 중요하다. **웹 프로젝트에도 화면 없는 기능이 있다.** 인증과 세션, 권한 판정, 결제 웹훅, 배치, 데이터 마이그레이션, 알림 발송, 공개 API. 이것들의 정본은 SCR이 아니라 REQ·API·MOD·RUN이다. SCR을 유일한 기준으로 삼으면 이 기능들은 검증 계약을 매달 곳이 없어지고, 곧 테스트 집계에서 사라진다. 테스트 현황을 보려고 만드는 규칙이 테스트 대상을 줄이는 결과가 된다.

여기에 원자성 문제가 겹친다. 테스트 문서에 같은 기능이 중복으로 들어가지 않게 하는 것이 이 작업의 요구사항 중 하나인데, 화면은 조합 단위다. 로그인 화면 하나가 인증·세션 발급·입력 검증·오류 표시를 함께 쓰고, 그 세션 기능은 회원가입과 비밀번호 재설정 화면에도 나타난다. 테스트 문서를 화면 단위로 조직하면 기능 하나를 바꿀 때 화면 문서 여럿을 고쳐야 한다 — 피하려던 상황이 그대로 재현된다.

## 결정 기준

- 화면이 있는 기능은 화면을 근거로 검증되어야 한다.
- 화면이 없는 기능이 검증 대상에서 빠지면 안 된다.
- 원자성의 단위는 조합 단위가 아니라 변경 단위여야 한다.
- Rundol이 자기 자신에게 적용할 수 없는 계약은 만들지 않는다.
- 이미 계산하고 있는 것을 다시 만들지 않는다.

## 선택지

| 선택지 | 장점 | 단점 | 위험 |
|---|---|---|---|
| TST의 필수 관계를 SCR로 교체 | 규칙이 한 줄이고 화면 기준이 명확하다 | 화면 없는 기능이 검증 대상에서 빠지고 프리셋 3개와 자기호스팅이 깨진다 | 테스트 집계가 조용히 줄어들고, 줄어든 사실을 대시보드가 보여주지 못한다 |
| 관계는 그대로 두고 관행으로 권고 | 아무것도 깨지지 않는다 | 강제가 없어 화면이 있는데도 REQ만 보고 쓴 TST를 막지 못한다 | 웹 프로젝트에서 기대한 효과가 나오지 않는다 |
| 기능에 화면 정본이 있을 때만 SCR 참조를 요구 | 화면 있는 기능은 강제되고 없는 기능은 REQ로 남는다 | 규칙이 조건부라 설명이 한 줄 더 필요하다 | SCR을 늦게 쓰는 프로젝트에서 나중에 경고가 한꺼번에 뜬다 |

## 결정

**TST의 필수 관계는 REQ로 유지하고, 그 TST가 선언한 기능 ID를 구현하는 SCR이 존재할 때에 한해 해당 SCR을 `related`에 요구한다.**

판정 근거는 이미 계산되고 있다. 기능 추적성이 `기능 ID → {REQ, SCR, MOD, API, TST}` 인덱스를 만들고 있으므로, 그 인덱스에 SCR 항목이 있는지만 보면 된다. 새 저장소도, 새 선언도 필요 없다.

**집계 축은 기능 ID로 유지한다.** 커버리지의 분모는 선언된 기능 ID이고 화면 수가 아니다. 이 축을 바꾸면 화면 없는 기능이 분모에서 빠지고, 테스트 대시보드가 실제보다 나은 숫자를 보여주게 된다.

**원자성도 기능 ID 축에 둔다.** 화면에서 출발한 TST가 기능 여럿을 검증하는 것은 허용하되, 문서 안에서 기능별 계약을 갈라 놓는다. TST의 grouping 정책이 `declared`인 것이 정확히 이 형태를 위한 것이고, 같은 기능 ID가 TST 여럿에 흩어지는 것은 기존 검사가 이미 잡는다.

**"이 프로젝트는 웹이다"는 관계가 아니라 trait로 표현한다.** `ui` trait가 SCR을 required로 올리도록 프리셋을 바꾼다. 관계 규칙은 전역이고 trait는 프로젝트별 선택이므로, 웹 프로젝트만 화면 정본을 강제받고 나머지는 영향을 받지 않는다.

**새 진단은 단계 도입한다.** 일반 검사에서 경고이고 `--implementation` 준비도 게이트에서 오류다. 기존 문서 정리가 끝난 뒤 상시 오류 승격을 검토한다.

## 결과

- 긍정적 결과: 화면이 있는 기능의 TST는 화면을 근거로 서게 되고, 화면 없는 기능은 검증 대상에 그대로 남는다. 프로필 계약과 문서 유형 관계를 개정하지 않으므로 기존 프로젝트에 마이그레이션이 없다. Rundol 자신도 계속 자기 계약을 통과한다. 커버리지 분모가 기능 ID 하나로 유지되어 대시보드가 화면 있는 기능과 없는 기능을 한 숫자로 셀 수 있다.
- 부정적 결과: 강제 규칙이 조건부라 "TST는 SCR을 참조한다"처럼 한 문장으로 말할 수 없다. SCR을 나중에 작성하는 프로젝트에서는 SCR이 생기는 시점에 경고가 한꺼번에 나타난다.
- 후속 작업: 입력·기대값은 문서를 쓰는 주체가 채우고, 그 주체는 대개 AI다. 새 생성 명령은 필요 없다 — `RDL-IMPL-006`이 이미 자리표시자를 거부하므로 값이 비어 있을 수는 없다. 부족한 것은 **무엇을 근거로 채우는가**이고, 이 결정이 만든 SCR 참조가 그 근거를 문서 옆에 붙여 놓는다. 어느 절에서 무엇을 가져올지는 스킬의 작성 지침이 정한다. 다만 검사는 빈칸을 거부할 뿐 모호한 문장을 거부하지 못한다 — "유효한 값을 입력하면 성공한다"는 통과하면서 테스트로는 쓸모가 없다. 이 간극이 실제로 남는지는 사용 문서를 측정해 판단한다. 테스트 실행 결과를 어디에 둘지는 이 결정의 범위 밖이며 별도로 정한다.
- 재검토 조건: 화면 있는 기능인데 SCR을 참조하지 않는 것이 정당한 사례가 반복해서 나오면, 조건을 기능 유형별로 더 좁힌다. 반대로 웹 프로젝트에서 이 경고가 사실상 항상 참이 되면, `ui` trait를 가진 프로필에 한해 상시 오류로 승격한다.
