# 런돌(Rundol) 제품 요구사항

## 제품 한 문장

Rundol은 ISO 수준의 설계 산출물과 태스크를 같은 Git 저장소에 정본으로 두고, 그 설계에서 나온 작업을 사람 워커와 AI 워커에게 **같은 계약으로 할당하고 같은 형식으로 보고받아 같은 판정으로 검수하는** 로컬 우선 프로젝트 운영 솔루션이다.

제품의 중심은 문서 작성 도구도, 태스크 보드도, 실행 엔진도 아니다. **설계와 실행 사이의 근거를 계산으로 유지하는 통제 계층**이다. 사람과 AI는 이 계층 아래에서 동일 계층의 워커로 취급한다.

## 문제와 배경

소프트웨어 프로젝트의 중요한 맥락은 코드 저장소, 문서 도구, 이슈 트래커, 메신저와 개인 메모에 흩어진다. 요구사항과 결정 근거가 구현과 분리되고, 태스크의 완료 상태는 검증 증거와 연결되지 않으며, 담당자와 의사결정권이 문서마다 다르게 표현된다. 시간이 지나거나 참여자가 바뀌면 프로젝트가 왜 현재 모습이 되었는지 복원하기 어렵다.

AI 개발 도구가 프로젝트 변경에 참여하면서 이 문제는 더 커진다. 각 도구가 서로 다른 지침과 부분적인 문맥을 사용하면 같은 저장소에서도 문서 구조, 책임 참조, 완료 기준과 변경 기록이 달라진다. AI가 빠르게 파일을 만들 수 있다는 사실만으로 그 변경의 정당성, 추적성 또는 안전성이 보장되지는 않는다.

기존 프로젝트 관리 SaaS는 협업 화면과 업무 흐름을 제공하지만, 별도 서버와 계정 체계에 의존하고 프로젝트 자료를 제품 저장소의 변경 이력과 분리한다. 반대로 단순한 Markdown 템플릿은 자료를 소유하기 쉽지만 구조와 관계의 무결성, 책임 참조와 완료 조건을 자동으로 보장하지 못한다.

Rundol이 해결할 핵심 문제는 문서 작성 자체가 아니다. 프로젝트 운영에 필요한 맥락을 사용자가 소유하는 파일과 Git 이력으로 남기면서도, 그 맥락이 일관되고 연결되어 있으며 검증 가능한 상태를 유지하게 하는 것이다.

## 제품 비전

프로젝트를 새 환경에서 다시 열었을 때 별도 서비스나 숨겨진 데이터베이스 없이도 다음 질문에 답할 수 있어야 한다.

- 이 프로젝트는 왜 존재하며 무엇을 달성하려 하는가?
- 현재 범위와 명시적으로 제외된 범위는 무엇인가?
- 누가 어떤 역할과 결정권을 가지는가?
- 어떤 요구사항과 결정이 현재 구현을 설명하는가?
- 어떤 태스크가 진행 중이며 완료를 증명하는 조건은 무엇인가?
- 어떤 변경이 누구 또는 어떤 Client에 의해 만들어졌는가?
- 원격과 충돌하거나 검토가 필요한 항목은 무엇인가?
- 자료를 다른 도구나 다른 환경에서도 그대로 읽고 복구할 수 있는가?

Rundol의 장기 비전은 프로젝트 운영 맥락을 특정 UI나 공급자에 가두지 않고, 사람과 자동화 도구가 공동으로 사용할 수 있는 검증 가능한 프로젝트 정본으로 만드는 것이다.

## 제품 원칙

### 사용자가 소유하는 정본

정규 데이터는 Markdown, JSON, YAML과 Git commit으로 보존한다. 메모리 index, Board snapshot과 로컬 실행 상태는 삭제 후 다시 만들 수 있는 파생 데이터로 취급한다.

### 로컬 우선

문서 조회, 편집, 태스크 관리와 검증은 원격 서비스 없이 동작해야 한다. 네트워크는 사용자가 선택한 Git remote와 동기화할 때만 필수다.

### 명시적인 책임

역할, 팀원, 이해관계자, 담당자, 검토자와 의사결정권을 익명 상태나 암묵적 관행으로 남기지 않는다. 한 사람이 여러 역할을 맡더라도 책임 경계는 구분한다.

### 검증 가능한 완료

문서와 태스크의 상태는 선언만으로 신뢰하지 않는다. 필수 메타데이터, 관계, 수용 조건, 테스트 증거와 동기화 상태를 자동으로 검사할 수 있어야 한다.

### 기능 단위의 완전한 계약

한 문서에 여러 기능을 둘 수는 있지만 기능 명세를 범위나 통합 행으로 묶지 않는다. 각 기능 ID는 단독 문서와 같은 수준의 입력·출력·규칙·상태·권한·예외·수용 기준과 독립 테스트 증거를 가져야 한다. 추적성은 직접 ID와 링크에서 계산하며 별도 인덱스 문서를 정본으로 만들지 않는다.

### 도구 독립성

CLI, Board, IDE, Obsidian과 AI 클라이언트는 서로 다른 저장소를 만들지 않고 같은 프로젝트 파일을 읽고 변경해야 한다.

### 안전한 변경과 복구

동시 변경, 잘못된 참조와 엄격 검사 실패가 기존 정본을 조용히 덮어쓰지 않아야 한다. 모든 중요한 변경에는 실패 시 복원 경로가 있어야 한다.

## 사용자

### 1차 대상

제품 결정의 기준이 되는 사용자는 하나다. 어떤 기능을 넣고 뺄지는 이 사용자의 편익으로만 판정한다.

| 사용자 | 달성하려는 일 | 현재의 핵심 불편 | Rundol이 제공할 가치 |
|---|---|---|---|
| **설계와 태스크를 통제하고 사람·AI 워커를 함께 운영하는 프로젝트 책임자** | ISO 수준 산출물을 유지하면서, 그 설계에서 나온 작업을 사람과 AI에게 할당하고 완료를 증거로 검수한다. | 산출물 작성 부담이 크고, 사람에게는 구두·메신저로 AI에게는 프롬프트로 지시가 갈라지며, 완료 보고 형식이 제각각이라 검수 기준이 두 벌이 된다. 세션이 바뀌면 같은 맥락을 다시 설명한다. | 설계 초안을 AI가 만들고 사람은 승인만 한다. 할당과 보고가 하나의 계약이므로 워커 종류와 무관하게 같은 판정으로 검수한다. 요구 조항과 작업의 덮임을 계산으로 확인한다. |

### 2차 대상

아래 사용자는 1차 대상의 편익이 증거로 확인된 뒤에 다룬다. 지금은 기능 판단의 근거로 쓰지 않으며, 이들만을 위한 기능은 추가하지 않는다.

| 사용자 | 언제 다루는가 |
|---|---|
| 개발자·설계자 | 워커 계약이 서면 자연히 포함된다. 별도 기능을 만들지 않는다. |
| 검토자·품질 담당자 | 보고 검수기가 순수 함수로 선 뒤 검토 표면을 논의한다. |
| AI 개발 클라이언트 운영자 | 1차 대상의 AI 워커 경로가 곧 이 사용자의 경로다. |
| 폐쇄망·로컬 환경 운영자 | 로컬 우선 원칙으로 이미 충족되며, 별도 요구는 수요 확인 후 검토한다. |

## 핵심 사용자 여정

### 새 프로젝트 시작

1. 사용자는 기존 Git 저장소에서 Workspace와 첫 프로젝트를 초기화한다.
2. Rundol은 Workspace Registry와 프로젝트 전용 Git 브랜치·worktree를 만든다.
3. 사용자는 프로젝트 헌장에 미션, 목표, 범위, 역할, 팀원, 이해관계자와 완료 정의를 기록한다.
4. strict 검사가 프로젝트 운영 계약의 구조와 참조를 확인한다.

### 기존 프로젝트 참여

1. 사용자는 원격 Git 저장소를 clone한 뒤 원하는 프로젝트를 연결한다.
2. Rundol은 Workspace Registry에서 프로젝트를 발견하고 로컬 worktree를 구성한다.
3. 사용자는 문서, 태스크와 책임 구조를 일반 파일 또는 Board에서 즉시 조회한다.
4. 로컬 파생 상태가 없더라도 정본 파일과 Git 이력에서 다시 생성한다.

### 요구사항에서 완료까지

1. 사용자는 제품 요구사항을 독립 기능 ID의 REQ, 관점별 설계 문서와 태스크에 연결한다.
2. 각 기능은 해당 문서 유형의 전체 계약과 같은 기능 ID를 검증하는 TST를 가진다.
3. 태스크에는 담당자, 관련 REQ·TST, 선행 작업과 관찰 가능한 수용 조건을 기록한다.
4. 구현과 검증 과정에서 상태와 수용 조건을 갱신한다.
5. 완료 전 implementation·strict 검사가 기능별 완전성, 책임, 연결, 수용 조건과 테스트 증거를 확인한다.
6. 검증된 변경만 프로젝트 브랜치에 저장하고 원격과 동기화한다.

### 사람과 AI의 공동 작업

1. 클라이언트는 작업 전에 Rundol 스킬과 권장 실행 주체를 확인한다.
2. CLI가 소유해야 하는 식별자, 경로, Git 작업은 CLI가 수행한다.
3. 사람이 판단해야 하는 내용은 사람 또는 LLM이 작성하되 동일한 프로젝트 계약을 따른다.
4. 실제 실행 주체와 관련 산출물을 기록하고 strict 검사로 결과를 검증한다.

### 충돌과 복구

1. 사용자는 원격 변경을 fetch하고 현재 branch와의 관계를 확인한다.
2. 자동 병합 가능한 변경은 병합한 뒤 전체 프로젝트를 검증한다.
3. 해결되지 않은 충돌은 관련 commit과 대상 정보를 pending 상태로 보존한다.
4. 사용자가 명시적으로 해결 전략을 선택한 뒤 검증된 결과만 저장·push한다.

## 목표와 성공 지표

지표는 선언이 아니라 계측이다. `현재 기준`은 실제로 측정한 값과 측정일을 적으며, 아직 계측 수단이 없는 항목은 목표값을 적기 전에 계측을 먼저 만든다.

### 1차 편익 지표

1차 대상의 편익을 직접 재는 지표다. 이 표의 값이 개선되지 않으면 나머지 지표가 모두 100%여도 제품이 실패한 것으로 판정한다.

지표 이름은 세고 싶은 것이 아니라 실제로 세는 것을 가리킨다. 재고 싶은 것은 "사람이 몇 번 개입했는가"지만 셀 수 있는 것은 "사람이 실행한 행위가 몇 건인가"다. 한 번 마음먹고 명령을 셋 치면 개입은 한 번이고 행위는 셋이므로 두 값은 같지 않다. 재고 싶은 이름을 붙여 두면 그 차이가 지워진 채로 편익 판단에 들어가므로, 셀 수 있는 것의 이름을 정확히 쓴다. 또한 이 계측은 명령을 거치지 않은 개입 — 보드나 편집기에서 직접 손댄 경우 — 을 보지 못하므로 실제 개입의 하한이며, 편익이 좋아 보이는 쪽으로 틀린다. 이 수치로 편익을 주장할 때는 하한이라는 사실을 함께 말한다.

| 목표 | 지표 | 현재 기준 | 목표값 | 측정 방법 |
|---|---|---:|---:|---|
| 워커 왕복의 자율성 확보 | 태스크 하나를 닫기까지 사람이 실행한 행위 수(중앙값) | 계측 미도입 | 2회 이하 | `rdl debug summary`의 `medianHumanActions`. 실행 주체가 `cli`·`hybrid`인 행위를 태스크별로 센다 |
| 설계 산출물 작성 부담 감소 | 설계 문서 1건당 사람이 직접 편집한 턴 수(중앙값) | 계측 미도입 | 3회 이하 | 문서 개정 이벤트의 작성 주체별 집계 |
| 워커 종류 무관성 확보 | 사람 워커와 AI 워커의 보고 형식 위반율 차이 | 계측 미도입 | 10%p 이내 | 보고 검수 결과를 워커 종류별로 집계 |
| 세션 교체 비용 감소 | 새 세션이 첫 유효 변경에 도달하기까지의 사람 발화 턴 수 | 계측 미도입 | 70% 감소 | 할당 컨텍스트 도입 전후 비교 측정 |

| 요구 조항의 작업 덮임 확보 | 기능 ID 중 이를 덮는 태스크가 있는 비율 | 계측 미도입 | 100% | 기능 ID와 태스크 링크의 양방향 덮임 계산 |
| 근거 없는 작업 차단 | 완료 태스크 중 기능 ID에 걸리지 않은 비율 | 계측 미도입 | 0% | 상향 추적 계산 |
| 제품 브랜치 격리 | 초기화·연결 후 제품 브랜치에 추가되는 Rundol 운영 파일 수 | 0 (2026-08-20 실측) | 0 유지 | 초기화 전후 제품 브랜치 추적 파일 비교 |
| 로컬 우선 운영 | 핵심 로컬 시나리오 중 외부 서비스가 필요한 비율 | 0% | 0% 유지 | 네트워크 차단 환경에서 문서·태스크·Board·strict 실행 |
| 안전한 동기화 | 충돌 또는 검사 실패가 원격 정본을 조용히 덮어쓴 건수 | 0 | 0 유지 | 동기화 회귀 테스트와 pending 충돌 기록 감사 |
| 새 환경에서의 복구 가능성 확보 | clone부터 프로젝트 조회·검증까지 성공한 지원 환경 비율 | 계측 미도입 | 100% | 격리 환경 attach·refresh·strict E2E 테스트 |
| 배포 신뢰성 | 지원 OS·Node 조합의 설치 및 핵심 시나리오 통과율 | 계측 미도입 | 100% | CI matrix와 release 설치 회귀 테스트 |

strict 통과율이 0%인 이유는 문서 계약을 `lean`에서 `assured`로 올리면서 `SCR`이 필수가 되었고 해당 유형이 아직 없기 때문이다. 계약을 낮춰 지표를 맞추지 않으며, `SCR` 작성으로 해소한다.

## 품질 요구

### 데이터 무결성

- 정규 데이터 변경은 원자적으로 기록하거나 실패 시 이전 byte로 복원해야 한다.
- 깨진 식별자, 책임 참조, 문서 링크와 태스크 의존성을 strict 검사에서 탐지해야 한다.
- 파생 index와 snapshot을 삭제해도 정본 파일에서 같은 논리적 상태를 재생성할 수 있어야 한다.

### 호환성과 이식성

- 지원하는 Windows, macOS와 Linux 환경에서 동일한 파일·Git 계약을 유지해야 한다.
- schema와 저장 형식 변경에는 명시적 migration과 이전 ref 보존 절차가 있어야 한다.
- 일반 텍스트 도구만으로도 정규 데이터를 읽고 백업할 수 있어야 한다.

### 성능

- 일반적인 프로젝트 규모에서 Board snapshot, 태스크 조회와 strict 검사가 대화형 사용을 방해하지 않아야 한다.
- 대규모 태스크·이벤트 데이터의 허용 규모와 성능 기준을 재현 가능한 benchmark로 관리해야 한다.
- 장시간 동기화 감시는 중복 실행, 메모리 누수와 변경 유실 없이 동작해야 한다.

### 보안과 개인정보

- Board는 기본적으로 loopback 주소에만 바인딩하고 변경 API에 세션 토큰과 base revision을 요구해야 한다.
- Git credential, API key, session token, 프롬프트와 문서 본문을 진단 로그에 기록하지 않아야 한다.
- Client ID와 문서 임대는 작업 출처와 협업 의도를 나타내며 인증·권한 수단으로 오해되지 않아야 한다.
- 프로젝트 문서에 포함된 개인정보의 보존과 원격 복제 범위는 저장소 관리자가 통제할 수 있어야 한다.

### 접근성

- 핵심 Board 흐름은 키보드만으로 탐색하고 조작할 수 있어야 한다.
- 상태 변화, 오류와 저장 결과는 시각 정보에만 의존하지 않고 접근 가능한 이름과 알림으로 제공해야 한다.
- 좁은 화면과 확대 환경에서도 문서 조회, 태스크 조작과 주요 탐색이 가능해야 한다.

## 제약과 가정

- 실행 환경에는 지원 범위의 Node.js, npm과 linked worktree를 지원하는 Git이 설치되어 있다고 가정한다.
- 로컬 기능은 네트워크 없이 동작하지만 원격 동기화에는 사용자가 구성한 Git remote와 인증이 필요하다.
- Git commit 이력은 변경 감사와 복구의 핵심 근거이며, force push와 이력 재작성은 Rundol이 자동으로 수행하지 않는다.
- 프로젝트 운영 자료는 제품 코드와 다른 branch가 소유하며 제품 브랜치에 Rundol 전용 로더나 정규 데이터를 강제로 추가하지 않는다.
- 한 사람이 여러 역할을 맡을 수 있지만 역할, 멤버와 이해관계자 유형 자체는 생략하지 않는다.
- 일정과 예산은 이 PRD에서 확정하지 않는다. 릴리스 결정은 수용 기준과 품질 게이트의 증거를 기준으로 한다.

## 출시 수용 기준

- 새 저장소와 기존 원격 저장소에서 Workspace·프로젝트 수명주기 시나리오가 재현된다.
- 모든 정규 문서와 태스크가 strict 검사에서 오류와 경고 없이 통과한다.
- 요구사항, 설계, 태스크와 테스트 증거의 추적 관계가 실제 파일과 식별자로 확인된다.
- 지원 OS·Node 조합에서 설치, `doctor`, 핵심 CLI, Board와 strict 검사가 통과한다.
- 네트워크 차단 상태에서 로컬 문서·태스크·Board 기능을 사용할 수 있다.
- 원격 분기, 충돌, 오래된 revision과 검사 실패가 기존 정본을 덮어쓰지 않는다.
- Board의 핵심 흐름이 지원 viewport와 키보드·접근성 자동 검사에서 통과한다.
- 대규모 데이터와 장시간 동기화의 허용 기준, 측정 결과와 재현 방법이 기록된다.
- 통합·개별 패키지의 버전, CHANGELOG, tag, tarball과 checksum이 서로 일치한다.

## 제품 의사결정 기준

새 기능이나 변경은 다음 순서로 평가한다.

1. 사용자가 프로젝트 정본을 더 잘 소유하고 복구할 수 있는가?
2. 책임, 추적성 또는 완료 증거를 더 명확하게 만드는가?
3. 로컬 우선과 Git 기반 운영을 훼손하지 않는가?
4. 사람과 AI가 같은 계약을 사용할 수 있는가?
5. 실패 시 기존 정본을 보호하고 복구할 수 있는가?
6. 자동 검사 또는 재현 가능한 증거로 품질을 입증할 수 있는가?

이 기준을 충족하지 못하거나 별도 중앙 서비스, 강한 잠금, AI 실행 플랫폼처럼 제품 경계를 바꾸는 제안은 PRD 개정과 ADR 검토 없이 포함하지 않는다.
