# 런돌 설치와 동기화 및 장애 복구 운영

## 목적과 적용 범위

이 런북은 Rundol CLI와 Node 실행 파일을 설치·갱신하거나, Workspace와 프로젝트를 원격 저장소에 동기화하거나, 설치·Git·문서 검증 장애를 복구하는 운영자에게 적용한다. 저장소 서버, npm registry, 운영체제 자체의 복구는 해당 서비스 운영 절차를 따르며 이 문서에서는 Rundol 측 확인과 안전한 완화까지만 다룬다.

운영 원칙은 다음과 같다.

1. 장애 조치 전에 현재 경로, 버전, Git HEAD와 작업 트리 상태를 증거로 남긴다.
2. 문서와 태스크 변경을 버리지 않으며 강제 push, 무검증 덮어쓰기와 기존 tag 이동을 사용하지 않는다.
3. Workspace Registry를 프로젝트보다 먼저 동기화한다.
4. 자동 병합이 불가능하면 pending 충돌로 보존하고 사람이 명시적으로 해결한다.
5. 복구 후에는 원래 실패한 명령뿐 아니라 strict 검사와 doctor까지 다시 실행한다.

## 대상과 책임

| 역할 | 책임 | 에스컬레이션 조건 |
|---|---|---|
| 사용자 | 증상·발생 시각·실행 명령을 기록하고 읽기 전용 진단을 수행한다. | 데이터 손실 가능성, 반복 실패 또는 권한 변경이 필요할 때 운영자에게 전달한다. |
| 프로젝트 운영자 | Workspace와 프로젝트 상태를 확인하고 동기화·충돌 해결·복구를 수행한다. | 공통 Workspace 장애, 원격 이력 불일치 또는 여러 사용자 영향 시 책임자에게 전달한다. |
| 릴리스 관리자 | package, tag, CHANGELOG, tarball과 설치 smoke test를 관리한다. | tag·package 불일치, checksum 불일치 또는 배포 후 회귀 시 배포를 중단한다. |
| 프로젝트 책임자 | 데이터 보존 방식, 롤백과 재배포 여부를 승인한다. | 복구가 기존 이력 변경이나 사용자 데이터 변환을 요구할 때 최종 판단한다. |

## 사전 조건과 안전 수칙

- 지원 기준은 Node.js 14 이상, npm 6 이상, Git 2.20 이상이다.
- 운영 대상의 Workspace root, project key, remote 이름과 현재 사용자 권한을 확인한다.
- credential, PAT와 인증서 개인 키를 명령 출력이나 증거 파일에 포함하지 않는다.
- `rdl sync`는 기본적으로 push까지 수행한다. 원격 변경을 피해야 하는 진단 단계에서는 `--no-push`를 사용한다.
- TLS 검증 비활성화, 광범위한 전역 Git 설정 변경, `git reset --hard`와 강제 push는 복구 방법으로 사용하지 않는다.
- clean install에서 launcher를 정리할 때는 `npm prefix --global`로 확인한 현재 prefix 안의 Rundol 파일만 대상으로 한다.

## 기준 상태와 초기 증거 수집

PowerShell 기준으로 다음을 실행해 시간, runtime, 실제 실행 파일, 설치 prefix와 진단 결과를 보관한다. 명령이 없는 경우에도 다음 단계로 넘어가지 말고 실패한 줄과 stderr를 기록한다.

```powershell
Get-Date -Format o
node --version
npm --version
git --version
where.exe rdl
where.exe rundol
where.exe rundol-node
npm prefix --global
npm root --global
rdl --version
rdl doctor --json
```

Workspace가 정상적으로 열리는 환경에서는 다음 결과도 수집한다.

```powershell
rdl workspace show --json
rdl workspace check --json
rdl check --project <project-key> --strict --json
git -C <project-worktree> status --short --branch
git -C <project-worktree> log -1 --oneline
```

증거에는 실행 시각, 운영체제, 명령, 종료 코드, stdout·stderr, Workspace root, project key와 현재 commit을 포함한다. secret이 포함될 수 있는 remote URL은 사용자 정보와 query를 제거한 뒤 저장한다.

## 설치와 갱신

### 배포 전 점검

릴리스 관리자는 보호된 main의 검증된 commit에서 다음을 순서대로 실행한다.

```powershell
npm run version:check
npm test
npm run test:packages
npm run test:install
npm run release:check
```

모든 package version, CHANGELOG 항목과 예정 tag `v<version>`이 일치해야 한다. 실패가 하나라도 있으면 tag 생성과 registry publish를 중단한다. 정식 tag는 main의 검증된 병합 commit에 annotated tag로 만들며 기존 tag를 이동하거나 재사용하지 않는다.

### 사용자 설치

통합 package 설치를 기본 경로로 사용한다.

```powershell
npm install --global rundol
rdl --version
rundol-node --version
rdl doctor --json
rdl skill install
rdl doctor --json
```

CLI와 Node가 분리되어야 하는 환경에서는 다음을 사용한다.

```powershell
npm install --global @rundol/cli @rundol/node
rdl --version
rundol-node --version
rdl doctor --json
```

monorepo Git URL을 npm 전역 설치 대상으로 직접 사용하지 않는다. 폐쇄망에서는 연결 환경에서 만든 검증된 tarball 묶음과 checksum을 반입하고 `@rundol/core`, `@rundol/protocol`, `@rundol/cli`·`@rundol/node`, `rundol` 의존 순서로 사설 registry에 게시하거나 설치 가능하게 제공한다.

## 정상 동기화 절차

### 수동 동기화

1. 작업 중인 편집을 끝내고 strict 검사를 수행한다.
2. push 권한 또는 네트워크가 불확실하면 먼저 `--no-push`로 병합 가능성을 확인한다.
3. 결과의 project별 action, commit과 pending 충돌 여부를 확인한다.
4. 정상일 때 기본 sync로 원격에 게시한다.

```powershell
rdl check --project <project-key> --strict --json
rdl sync --project <project-key> --no-push --json
rdl sync --project <project-key> --json
```

`rdl sync`는 Workspace 설정 동기화, 로컬 저장, project fetch, 이력 판정·병합, materialize, strict 검증과 선택적 push 순서로 처리한다. 여러 프로젝트 전체 sync는 하나의 원자적 트랜잭션이 아니므로 project별 결과를 각각 확인한다.

### 반복 동기화

```powershell
rdl sync watch --project <project-key> --interval 60 --json
```

watch는 한 인스턴스만 실행한다. 유지보수나 충돌 해결 전에는 watch를 정상 종료하고 수동 sync로 최종 상태를 확인한다. 짧은 간격의 반복 실패가 원격 서비스에 부하를 주지 않도록 원인 해소 전 재시작하지 않는다.

## 관찰과 장애 등급

| 신호 | 정상 | 경고 | 심각 | 확인 위치 |
|---|---|---|---|---|
| Doctor | `summary.errors`가 0 | skill stale, PATH 후보 중복 | package 필수 파일·runtime 오류 | `rdl doctor --json` |
| 문서 검증 | 오류·경고 0 | strict가 아닌 검사만 통과 | strict 오류 또는 구조 손상 | `rdl check --strict --json` |
| Git 동기화 | clean 또는 의도한 local-ahead | behind, modified, 일시적 remote 실패 | diverged, conflict, push 거부 | sync JSON, Board Operations |
| Client 임대 | 소유자·만료 시각 확인 가능 | 만료 임박 또는 stale client | 다른 client가 유효 임대를 보유한 문서 편집 | Board Snapshot, lease 응답 |
| 설치 | version 일치, launcher 1세트 | 중복 launcher 또는 skill 구버전 | 실행 파일 없음, dangling link, package 손상 | `where.exe`, npm prefix, doctor |
| 릴리스 | version·tag·checksum 일치 | smoke test 미완료 | 불일치 package 배포 또는 checksum 불일치 | CI 결과, package manifest |

심각 상태에서는 자동 sync와 배포를 중지한다. 데이터 손실 우려, 여러 프로젝트의 Workspace 불일치, credential 노출 또는 잘못된 release가 확인되면 즉시 프로젝트 책임자와 릴리스 관리자에게 알린다.

## 장애 대응 절차

### A. Strict 검사 실패

1. `rdl check --project <project-key> --strict --json` 결과를 저장한다.
2. 오류가 가리키는 문서 ID, frontmatter, 링크와 파일명을 확인한다.
3. 원본을 별도 위치에 복사해 보존한 뒤 최소 범위만 수정한다.
4. strict 검사를 다시 실행하고 통과 후 `rdl save --project <project-key> --json`으로 저장한다.
5. 실패 상태에서는 fetch, merge와 push를 진행하지 않는다.

### B. Remote 인증·DNS·TLS·HTTP 오류

```powershell
rdl doctor --git-url <sanitized-git-url> --json
git -C <project-worktree> remote -v
```

| 분류 | 확인과 완화 |
|---|---|
| authentication | 계정 권한과 credential helper를 확인하고 새 credential은 승인된 저장소를 통해 갱신한다. 명령행에 PAT를 직접 넣지 않는다. |
| dns | 사내 DNS·VPN·proxy 연결과 호스트 해석을 확인한다. 저장소 URL을 임의 IP로 바꾸지 않는다. |
| tls | 시스템 시간, 인증서 체인과 사내 CA 구성을 확인한다. SSL 검증을 끄지 않는다. |
| http-reset | 명령 범위에서만 HTTP/1.1 fallback을 시험하고 성공 여부를 증거로 남긴다. 전역 Git 설정은 변경하지 않는다. |
| not-found | URL의 group·repository 경로와 읽기 권한을 확인한다. 존재하지 않는 branch를 새 이력으로 게시하지 않는다. |

원격이 복구될 때까지 로컬 변경은 현재 project worktree와 branch에 보존한다. 네트워크 복구 후 `--no-push` sync, strict 검사, 기본 sync 순서로 재개한다.

### C. Git 이력 분기와 pending 충돌

1. watch와 Board의 추가 편집을 중지한다.
2. 현재 HEAD, upstream, `git status --short --branch`와 sync 실패 JSON을 보존한다.
3. `rdl conflict list --project <project-key> --json`으로 pending 항목, ours·theirs commit과 대상 필드를 확인한다.
4. 문서·태스크 의미를 비교해 항목별로 유지할 값을 결정한다. 최신 시각만으로 승자를 정하지 않는다.
5. 승인된 방향을 명시해 `rdl conflict resolve`를 수행한다. 정확한 인수는 현재 `rdl --help`와 충돌 목록의 식별자를 따른다.
6. `rdl check --strict`, `rdl save`, `rdl sync --no-push`를 차례로 실행한다.
7. diff와 merge commit을 검토한 후 기본 sync로 게시하고 pending 목록이 비었는지 확인한다.

충돌 레코드는 복구 증거이므로 원인을 확인하기 전에 `conflict clear`로 지우지 않는다. 공통 base가 없거나 자동 병합 결과를 설명할 수 없으면 작업을 중단하고 프로젝트 책임자에게 에스컬레이션한다.

### D. 설치 손상 또는 PATH 불일치

다음 증상은 오래된 shim, 다른 Node 배포의 prefix 또는 삭제된 임시 clone을 가리키는 package link에서 주로 발생한다.

```text
Cannot find module '<prefix>\node_modules\rundol\bin\rdl.js'
```

먼저 실제 경로를 비교한다.

```powershell
where.exe node
where.exe npm
where.exe rdl
Get-Command rdl -All | Select-Object CommandType, Source
npm prefix --global
npm root --global
```

현재 npm prefix가 의도한 경로임을 확인한 뒤에만 다음 clean install을 수행한다.

```powershell
$rundolPrefix = npm prefix --global
npm uninstall --global rundol @rundol/cli @rundol/node

Remove-Item "$rundolPrefix\rdl.cmd" -Force -ErrorAction SilentlyContinue
Remove-Item "$rundolPrefix\rdl.ps1" -Force -ErrorAction SilentlyContinue
Remove-Item "$rundolPrefix\rundol.cmd" -Force -ErrorAction SilentlyContinue
Remove-Item "$rundolPrefix\rundol.ps1" -Force -ErrorAction SilentlyContinue
Remove-Item "$rundolPrefix\rundol-node.cmd" -Force -ErrorAction SilentlyContinue
Remove-Item "$rundolPrefix\rundol-node.ps1" -Force -ErrorAction SilentlyContinue

npm install --global rundol
rdl --version
rundol-node --version
rdl doctor --json
```

새 shell에서 `where.exe rdl`, version과 doctor를 다시 확인한다. 여러 Node 배포가 있으면 PATH가 선택한 `node`, `npm prefix --global`과 `rdl` launcher가 같은 설치 계열인지 맞춘다. unmanaged AI skill은 자동 삭제하지 않으며 검토와 승인 없이 `rdl skill install --force`를 사용하지 않는다.

### E. Board 또는 Client 쓰기 실패

1. HTTP 상태와 오류 본문, project key, entity ID와 base revision을 기록한다. token 값은 기록하지 않는다.
2. `401`이면 token 전달 경로를, `404`이면 project·entity 식별자를 확인한다.
3. `409`이면 최신 snapshot을 다시 읽고 revision 또는 lease 소유권을 확인한다. stale revision을 강제로 덮어쓰지 않는다.
4. `413`이면 요청 크기를 줄인다. 현재 공통 JSON parser 한계와 문서 본문 정책 한계가 다르므로 큰 문서는 CLI 편집·분할을 사용하고 구현 gap으로 추적한다.
5. `422`이면 strict 진단을 수정한 뒤 재시도한다.
6. 성공 후 snapshot revision 변경, 파일 diff와 strict 통과를 확인한다.

### F. 잘못된 릴리스 또는 설치 회귀

1. registry publish와 추가 tag 생성을 중단하고 영향 version·commit·checksum을 공지한다.
2. tag와 배포물을 삭제하거나 이동하지 않는다. 같은 version으로 다른 내용을 다시 배포하지 않는다.
3. 직전 검증 version 설치를 안내하되 Workspace와 프로젝트 데이터 형식의 하위 호환성을 먼저 확인한다.
4. 수정은 새 PATCH 또는 prerelease version, 새 CHANGELOG 항목과 새 tag로 준비한다.
5. `npm run release:check`, tarball 설치, `rdl doctor`와 fixture strict 검사를 통과한 뒤 재배포한다.

## 롤백과 데이터 복구

| 상황 | 롤백 기준 | 복구 방법 | 성공 확인 |
|---|---|---|---|
| 새 CLI 설치 실패 | 실행 파일이 없거나 doctor error 발생 | 기존 검증 version을 새로 설치한다. 사용자 Workspace는 삭제하지 않는다. | version, doctor, 기존 project strict 검사 |
| sync 전 로컬 변경 | 아직 원격 게시 전 | project branch와 worktree를 보존하고 수정·재검증한다. | diff가 설명 가능하고 strict 통과 |
| 자동 병합 실패 | pending 충돌 생성 | pending 레코드의 ours·theirs를 검토해 명시적으로 해결한다. | pending 0건, merge commit, strict 통과 |
| 잘못된 원격 게시 | 다른 사용자가 이미 가져갈 수 있음 | 이력을 재작성하지 않고 새 보정 commit으로 수정한다. | 새 HEAD가 원격과 일치하고 감사 이력 유지 |
| 잘못된 release | tag 또는 package가 외부에 노출 | 기존 version을 변경하지 않고 새 version으로 수정 배포한다. | 새 tag·version·checksum 및 smoke test 일치 |

문서·태스크 복구에서 파일 삭제나 branch 재작성 전에 원본 branch, commit과 working tree diff를 복구 가능한 위치에 보존한다. 복구 완료 판정은 단순히 명령 종료 코드가 0인 것만으로 하지 않고 materialized 파일, semantic index, Git 상태와 원격 상태가 일치하는지 확인한다.

## 복구 완료 검증

아래 항목을 모두 만족해야 장애를 종료한다.

- [ ] `rdl doctor --json`의 error가 0건이다.
- [ ] `rdl workspace check --json`이 통과한다.
- [ ] 대상 프로젝트의 `rdl check --strict --json`이 오류·경고 없이 통과한다.
- [ ] `git status --short --branch`에 설명되지 않은 변경이나 충돌이 없다.
- [ ] sync 결과와 원격 tracking ref의 ahead·behind가 의도한 상태다.
- [ ] pending 충돌과 만료되지 않은 비정상 lease가 없다.
- [ ] Board·Client 장애였다면 최신 snapshot 읽기와 승인된 최소 쓰기 1건이 성공한다.
- [ ] 설치 장애였다면 새 shell에서 version, 실제 launcher 경로와 doctor가 일치한다.
- [ ] 릴리스 장애였다면 새 version·tag·checksum·CHANGELOG와 설치 smoke test가 일치한다.
- [ ] 발생 원인, 조치, 검증 증거와 후속 예방 작업을 기록했다.

## 알려진 운영 제약

- 여러 프로젝트를 한 번에 sync해도 전체가 하나의 원자적 트랜잭션으로 롤백되지는 않는다.
- Board의 watch 상태 표시는 아직 외부 CLI 상태와 완전히 연결되지 않았으므로 실제 process와 로그를 함께 확인한다.
- 문서 편집의 512KiB 정책과 공통 HTTP JSON parser의 64KiB 제한이 일치하지 않아 큰 문서는 API로 저장할 수 없다.
- OS·runtime 전체 조합과 사설 registry·proxy·폐쇄망은 대상 환경별 실행 증거가 필요하다.
- Rundol은 Git server, registry, DNS, VPN, 인증서 발급과 credential 수명주기를 대신 운영하지 않는다.
