# 패키지 릴리스 런북

## 대상과 책임

| 대상 | 소유자 | 승인·에스컬레이션 |
|---|---|---|
| version·CHANGELOG·release MR | 프로젝트 책임자 | main 보호 규칙에 따른 reviewer |
| immutable `v<version>` tag | 프로젝트 책임자 | tag 생성 권한 보유 maintainer |
| npm trusted publisher | 프로젝트 책임자 | npm 조직 관리자 |
| GitHub Actions release workflow | 프로젝트 책임자 | repository Actions 관리자 |

## 릴리스 불변조건

- root는 `@rundol/monorepo`, `private: true`, 배포 `bin`·`files` 없음이다.
- `packages/*`의 모든 package version은 root version과 같다.
- package name은 유일하며 unscoped `rundol`은 `packages/rundol`에 정확히 한 번 존재한다.
- root와 workspace package에 `postinstall`을 두지 않는다.
- version은 SemVer이고 `CHANGELOG.md`에 정확한 `## [<version>]` 항목이 있다.
- tag가 있으면 정확히 `v<package.json version>`이어야 한다.
- npm token을 repository secret이나 파일에 저장하지 않고 trusted publishing OIDC를 사용한다.

## 사전 준비

1. 보호된 main을 직접 수정하지 않고 release branch/MR에서 version과 CHANGELOG를 갱신한다.
2. 변경 성격에 따라 patch/minor/major를 선택한다. 검증 전 배포는 `-alpha.N`, `-beta.N`, `-rc.N` prerelease를 사용한다.
3. root와 `packages/core`, `protocol`, `board`, `node`, `cli`, `rundol` manifest의 version을 동일하게 맞춘다.
4. 내부 dependency version도 동일 release version인지 확인한다.

## 검증 게이트

```powershell
npm run version:check
npm run release:check
```

`version:check`는 SemVer, root 경계, package name 중복, version 정렬, postinstall 부재, CHANGELOG와 `CI_COMMIT_TAG` 일치를 검사한다. `release:check`는 이를 먼저 실행한 뒤 전체 테스트와 tarball 설치 테스트를 실행한다.

검증 결과에는 다음이 포함되어야 한다.

- Node 20·22 CI에서 version check와 전체 test 통과
- CLI distribution build 성공
- 배포 package tarball 5개(core, protocol, cli, node, rundol)를 의존 순서로 pack·설치
- 설치된 `rdl`, `rundol`, `rundol-node` version 일치
- 설치본 `rdl doctor --json` errors 0
- 설치본이 임시 clone symlink가 아님

## tag와 게시

1. release MR이 main에 병합되고 동일 commit의 CI가 통과했는지 확인한다.
2. maintainer가 대상 commit에 변경 불가능한 annotated `v<version>` tag를 만든다.
3. tag를 동일 이름 remote tag로 push한다.
4. `.github/workflows/release.yml`이 `CI_COMMIT_TAG`를 전달해 `npm run release:check`를 다시 수행하는지 확인한다.
5. workflow가 core → protocol → board → node → cli → rundol 순으로 `npm publish --provenance --access public`을 실행하는지 확인한다.
6. 이미 registry에 같은 version이 있으면 해당 package는 skip되며 나머지 단계가 안전하게 계속되는지 확인한다.

workflow 권한은 repository contents read와 `id-token: write`만 사용한다. 새 package를 추가하면 npm에서 `runtime-co-kr/rundol` repository의 `release.yml`을 trusted publisher로 먼저 등록한다.

## 게시 후 검증

깨끗한 임시 prefix에서 공개된 `rundol@<version>`을 설치하고 다음을 실행한다.

```powershell
rdl --version
rundol --version
rundol-node --version
rdl doctor --json
```

세 version이 release version과 같고 doctor errors가 0이어야 완료다. npm package 페이지의 provenance와 모든 workspace package version도 확인한다.

## 장애 대응

| 증상 | 대응 | 재개 조건 |
|---|---|---|
| version 불일치 | 모든 manifest와 internal dependency를 같은 새 version으로 수정 | `version:check` 통과 |
| CHANGELOG 누락 | 정확한 version section과 사용자 영향 기록 | `version:check` 통과 |
| tag 불일치 | tag를 이동하지 말고 잘못된 미게시 tag는 정책에 따라 제거 후 올바른 새 tag; 게시됐다면 새 patch 준비 | package version과 새 tag 일치 |
| OIDC 권한 실패 | npm trusted publisher repository·workflow 설정과 `id-token: write` 확인 | token 없이 dry-run/check 성공 |
| 일부 package만 게시 | 같은 tag workflow 재실행; 이미 게시된 version은 skip | 전체 package 존재와 version 일치 |
| 설치 smoke test 실패 | 게시본을 덮어쓰지 않고 원인 수정 후 새 patch version | 새 version 전체 gate 통과 |

## 롤백과 복구

npm과 Git tag의 게시 이력은 불변으로 취급한다. 이미 게시한 version을 다시 쓰거나 tag를 이동하지 않는다. 치명적 결함은 npm 정책이 허용하는 deprecate 안내를 추가하고 수정한 새 patch version을 전체 절차로 배포한다. 사용자 데이터나 Rundol project branch를 release 복구 과정에서 변경하지 않는다.
