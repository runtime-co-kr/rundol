# 개입 대기 런 조회

## 배경

런은 세션보다 오래 산다. 원장이 append-only이고 fold를 읽을 때마다 다시 계산하므로, 프로세스가 어디에서 끊겨도 다음 읽기가 커서와 정지 사유를 복원한다. 그런데 **그 사실을 물어볼 자리가 없었다.**

`rdl run list`는 프로젝트 하나를 강제하고 fold 전문을 돌려준다. "이 프로젝트에 런이 무엇이 있는가"에는 맞지만 "지금 내가 무엇을 해야 하는가"에는 쓸 수 없다. 프로젝트가 여럿이면 하나씩 전환해야 하고, 돌려받은 fold에서 개입이 필요한 것을 사람이 다시 골라야 한다.

그 결과 정지한 런은 누군가 우연히 들여다볼 때까지 정지한 채로 남는다. 원장은 정확하지만 아무도 그것을 읽지 않는다.

## 요구사항

- 사용자와 에이전트가 프로젝트를 전환하지 않고 작업공간 전체에서 개입이 필요한 런을 한 번에 확인할 수 있다.
- 각 항목이 왜 그 갈래에 들어갔는지와 다음에 실행할 명령을 함께 받는다.
- 개입할 런이 없을 때는 아무것도 출력하지 않는다.
- 조회가 원장을 바꾸지 않는다.

## 사전조건

- Rundol Workspace가 연결되어 있고 프로젝트 등록이 읽힌다. 연결되지 않은 경로에서의 호출은 오류가 아니다.
- 런 원장 또는 공유 런 샤드가 존재한다. 둘 다 없으면 개입 대기가 없는 것과 같다.

## 동작 규칙

1. `--project`를 주지 않으면 Workspace에 등록된 모든 프로젝트를 훑는다. 주면 그 결과에 거는 필터로 동작하며, 등록되지 않은 프로젝트 키는 인자 오류다.
2. 런 식별자는 프로젝트 로컬 원장과 Workspace 공유 샤드의 합집합으로 모은다. 로컬만 세면 다른 기계가 시작한 런이 새 클론에서 보이지 않는다.
3. 각 런을 세 갈래 가운데 하나로 판정한다. 이미 유효한 driver lease나 살아 있는 drive 프로세스 잠금이 쥐고 있으면 `driving`, 사람만 풀 수 있으면 `waiting`, 기계가 이어 밀 수 있으면 `drivable`이다.
4. 정지 사유는 원장이 접어 준 값을 그대로 나른다. 이 조회는 사유 목록을 다시 정의하지 않는다.
5. 시도 예산은 다시 세지 않는다. 원장이 예산 소진을 정지로 접으므로 상한에 걸린 런은 `waiting`으로 나타난다.
6. 해결되지 않은 operation 충돌은 런의 상태가 무엇이든 먼저 드러낸다. 원장이 완료 이후에도 그 목록을 비우지 않는 이유가 충돌의 증거를 잃지 않기 위해서이므로, 이 조회가 그것을 떨어뜨리면 안 된다.
7. 한 런을 읽지 못해도 나머지는 계속 판정한다. 읽지 못한 런은 그 사실이 결과에 남는다.
8. 조회는 읽기만 한다. 원장 조정, 잠금 획득, 리스 갱신 가운데 어느 것도 하지 않는다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 개입이 필요한 런이 없음 | 조회 | 사람 출력 없음, 종료 코드 0 |
| Workspace를 찾지 못함 | 조회 | 사람 출력 없음, 빈 결과, 종료 코드 0 |
| Workspace는 있으나 읽지 못함 | 조회 | 종료 코드 2와 오류 출력 |
| 등록되지 않은 프로젝트 키를 줌 | 조회 | 인자 오류, 종료 코드 2 |
| 런 하나의 원장이 손상됨 | 조회 | 그 런만 읽기 실패로 표시, 나머지는 정상 판정, 종료 코드 0 |
| 사람 게이트에 선 런 | 조회 | `waiting`, 사유 `human-gate`, 승인 명령 제시 |
| 정지한 런 | 조회 | `waiting`, 사유는 원장의 정지 사유 그대로 |
| 병합까지 살아남은 런 | 조회 | 어느 갈래에도 넣지 않음 |
| 유효한 리스 또는 살아 있는 잠금이 있는 런 | 조회 | `driving`, 기계 판독 출력에만 나타남 |

## 수용 기준

- [ ] `--project` 없이 실행하면 등록된 모든 프로젝트의 런이 대상이 된다.
- [ ] 결과가 `waiting`, `drivable`, `driving` 세 갈래로 갈리고 각 항목이 사유를 밝힌다.
- [ ] 개입할 런이 없으면 사람 출력이 비어 있고 종료 코드가 0이다.
- [ ] 기계 판독 출력이 훅과 드라이버가 함께 쓸 수 있는 고정 형태로 나온다.
- [ ] 조회 전후로 런 원장과 공유 샤드의 내용이 바뀌지 않는다.
- [ ] 손상된 런이 있어도 나머지 런의 판정이 나오고 손상 사실이 결과에 드러난다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 부작용 없음 | 조회가 파일을 만들거나 바꾸지 않는다 | 조회 전후 원장 파일의 내용과 수정 시각 비교 |
| 침묵 | 개입 대기가 없을 때 사람 출력이 정확히 비어 있다 | 표준 출력이 빈 문자열인지 확인 |
| 고립 | 런 하나의 손상이 다른 런의 판정을 막지 않는다 | 원장 하나를 훼손한 뒤 나머지 판정 확인 |

## 제외 범위

- 런을 실제로 미는 실행과 그 트리거. 이 조회는 무엇을 밀지 고를 뿐 밀지 않는다.
- 런 목록 전체 조회와 원장 이력 조회. 그것은 다른 물음이며 다른 명령이 답한다.
- 개입 대기를 사람에게 밀어 보내는 알림 경로. 이 조회는 물으면 답할 뿐 찾아가지 않는다.

## 기능별 설계 계약

### FN-001

#### 입력

- 선택적 프로젝트 키. 주면 열거 결과에 거는 필터이고, 주지 않으면 등록된 모든 프로젝트가 대상이다.
- 선택적 기계 판독 출력 요구.
- 탐색 시작 경로. 주지 않으면 현재 위치에서 Workspace를 찾는다.

#### 출력

- 갈래별 런 목록. 각 항목은 프로젝트 키, 런 식별자, 절차 이름, 커서 스텝, 판정 사유, 다음 명령을 갖는다.
- 읽지 못한 런의 목록. 각 항목은 프로젝트 키, 런 식별자, 실패 사유를 갖는다.
- 판정에 쓰인 작업공간 경로. Workspace를 찾지 못한 경우에는 비어 있다.

#### 업무 규칙

- 갈래 판정은 원장이 접어 준 값만으로 결정한다. 절차 정의를 다시 해석하지 않는다.
- 실행 중인 사슬이 있으면 다른 갈래보다 먼저 판정한다.
- 해결되지 않은 operation 충돌은 상태보다 먼저 판정한다.
- 정지 사유와 시도 예산의 정본은 원장이며 이 기능은 그것을 다시 계산하지 않는다.

#### 상태와 전이

- 이 기능은 런의 상태를 읽기만 하고 어떤 전이도 일으키지 않는다.
- 같은 런이 시각에 따라 다른 갈래로 보일 수 있다. 실행 중인 사슬이 끝나면 `driving`이던 런이 `waiting` 또는 `drivable`이 된다.

#### 권한과 승인

- 조회는 Client 자격을 요구하지 않는다. 원장을 바꾸지 않으므로 귀속시킬 행위가 없다.
- 결과가 제시하는 명령은 각자의 자격 규칙을 그대로 따른다. 승인은 사람 유형 Client가, 실행은 에이전트 또는 서비스 유형 Client가 수행한다.

#### 정상·오류·취소

- 정상: 판정에 성공하면 갈래 목록을 돌려주고 성공으로 끝난다. 개입 대기가 없는 것도 정상이다.
- 오류: 인자가 잘못되었거나 Workspace를 찾았으나 읽지 못하면 실패로 끝난다.
- 취소: 조회는 중간 상태를 만들지 않으므로 도중에 끊겨도 되돌릴 것이 없다.

#### 감사 기록

- 이 기능은 원장에 아무 기록도 남기지 않는다. 무엇이 주의를 요구하는지 묻는 행위가 원장을 바꾸면 보는 것과 고치는 것이 같은 일이 된다.

#### 수용 기준

- [ ] 프로젝트를 지정하지 않은 호출이 등록된 모든 프로젝트를 대상으로 삼는다.
- [ ] 세 갈래 판정이 원장 fold의 값만으로 결정된다.
- [ ] 실행 중인 사슬이 있는 런을 기계가 이어 밀 대상으로 제시하지 않는다.
- [ ] 개입 대기가 없을 때 사람 출력이 비어 있다.
- [ ] 조회가 원장 파일의 내용과 수정 시각을 바꾸지 않는다.
- [ ] 각 항목이 그대로 실행할 수 있는 다음 명령을 포함한다.
