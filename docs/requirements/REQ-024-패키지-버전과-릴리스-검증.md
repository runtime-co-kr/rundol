# 패키지 버전과 릴리스 검증

## 배경

여러 공개 package와 통합 배포 package를 함께 릴리스할 때 버전 불일치, 순환되지 않은 내부 의존성, 잘못된 tag와 설치 불가능한 tarball은 사용자 설치를 깨뜨린다.

## 요구사항

- 루트와 모든 workspace package는 동일한 유효 SemVer를 사용하고 내부 `@rundol/*` 의존성도 그 버전에 맞춰야 한다.
- 릴리스 검사는 package 경계, CHANGELOG 항목, 선택적 `v<version>` tag, 전체 테스트와 실제 tarball 설치를 검증해야 한다.
- tag 기반 GitHub Actions 릴리스는 trusted publishing으로 의존 순서에 따라 공개 package를 게시해야 한다.

## 사전조건

- 루트는 `@rundol/monorepo`, `private: true`, workspaces `packages/*`이고 배포용 bin/files를 갖지 않아야 한다.
- 릴리스 버전의 `CHANGELOG.md` 항목과 주석 tag가 준비되어야 한다.

## 동작 규칙

1. SemVer는 선행 0을 금지하고 표준 prerelease/build metadata를 허용한다.
2. 모든 workspace manifest 버전은 루트 버전과 같고 package 이름은 유일하며 비공개 루트 밖의 `rundol` 이름은 정확히 한 번만 존재한다.
3. 루트와 workspace package에 postinstall을 두지 않는다.
4. release check는 `version:check → npm test → test:install` 순서로 실행한다.
5. 설치 검증은 core, protocol, cli, node, rundol tarball을 만들고 내부 의존성을 앞서 만든 tarball로 치환하여 실제 prefix에 설치한다.
6. 게시 순서는 core → protocol → board → node → cli → rundol이며 이미 같은 버전이 registry에 있으면 건너뛴다.
7. CI는 Node 20의 Linux·Windows·macOS와 Node 22 Linux에서 version check와 전체 테스트를 수행한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| manifest·CHANGELOG·tag 일치 | release check | 검증 통과 |
| SemVer/버전/이름/CHANGELOG/tag 불일치 | version check | issue 수집, 실패 종료 |
| tarball 설치 또는 CLI 실행 실패 | install test | 릴리스 차단 |
| npm에 같은 package@version 존재 | publish | 해당 package skip |
| 선행 package 미게시 | publish | 후속 package 게시 중단 |

## 수용 기준

- [ ] `checkVersion(root, v<version>)`이 valid이고 잘못된 tag는 invalid다.
- [ ] 모든 package manifest 버전과 핵심 내부 의존성 버전이 루트와 일치한다.
- [ ] 생성된 5개 설치 tarball로 통합 package를 설치한 뒤 `rdl`, `rundol`, `rundol-node`가 같은 버전을 출력한다.
- [ ] release workflow는 OIDC 권한으로 전체 release check 후 지정된 의존 순서로 게시한다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 재현성 | package tarball에서 symlink가 아닌 실제 배포 디렉터리 설치 | install 테스트 |
| 공급망 보안 | npm token 없이 OIDC provenance 사용 | release workflow 검사 |
| 재실행 안전성 | 이미 게시된 동일 버전은 skip | workflow 조건 검사 |

## 제외 범위

- 사용자 PATH, Git 접근 오류, AI 스킬 상태와 손상 설치 복구는 REQ-023에서 다룬다.

## 기능별 설계 계약

### FN-001

#### 입력

- 저장소 root, 루트·workspace `package.json`, `CHANGELOG.md`, 선택적 `CI_COMMIT_TAG`, CI matrix와 npm registry 상태.

#### 출력

- `{ valid, version, tag, issues }`, 패키지·설치 테스트 결과, 성공 시 npm에 게시된 공개 package 집합.

#### 업무 규칙

- 모든 구조·버전·tag 검증과 테스트가 통과해야 publish 단계에 진입하며 게시 순서는 내부 의존 그래프를 따른다.

#### 상태와 전이

- 준비된 version → 검증됨 → package별 게시/이미 게시됨으로 전이한다. 어느 검증 실패도 게시 전이로 진행하지 않는다.

#### 권한과 승인

- release workflow만 tag push에서 `id-token: write`를 사용하며 source checkout 권한은 read로 제한한다.

#### 정상·오류·취소

- 정상은 모든 검사와 설치를 통과한 뒤 미게시 package를 게시한다. issue·테스트·설치·게시 실패는 즉시 후속 게시를 중단한다.

#### 감사 기록

- Git tag, CHANGELOG 항목, CI 로그, npm provenance와 package별 publish/skip 로그가 릴리스 증거다.

#### 수용 기준

- `test/release.test.js`, `test/packages.test.js`, `test/install.test.js`와 `.github/workflows/ci.yml`, `release.yml`의 검증·설치·게시 계약이 모두 충족된다.
