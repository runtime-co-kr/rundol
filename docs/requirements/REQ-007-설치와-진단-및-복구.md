# 설치와 진단 및 복구

## 배경

런돌은 Node.js와 Git이 설치된 여러 운영체제, 사설 registry와 폐쇄망에서 사용된다. npm 전역 prefix와 PATH가 서로 다르거나 오래된 shim·임시 Git clone link가 남으면 설치가 성공한 것처럼 보여도 CLI 파일을 찾지 못할 수 있다. Git 원격 실패 역시 인증, DNS, TLS, HTTP 전송 또는 저장소 주소 문제에 따라 해결 방법이 다르다.

사용자는 설치 방식과 무관하게 동일한 실행 파일과 버전을 확인하고, 부분 손상 상태에서도 진단 결과와 구체적인 복구 조치를 얻을 수 있어야 한다. 복구 과정은 사용자 데이터와 정상 설치를 불필요하게 삭제하거나 TLS 검증 같은 보안 설정을 약화해서는 안 된다.

## 요구사항

- REQ-007-FR-01: 사용자는 통합 `rundol` npm 패키지로 CLI와 Node 실행 파일을 함께 설치할 수 있어야 한다.
- REQ-007-FR-02: 사용자는 `@rundol/cli`와 `@rundol/node`를 독립 패키지로 설치할 수 있어야 한다.
- REQ-007-FR-03: 사용자는 사설 registry 또는 검증된 release tarball 묶음으로 폐쇄망에 설치할 수 있어야 한다.
- REQ-007-FR-04: 시스템은 Node.js·npm·Git 버전, 패키지 필수 파일, PATH 실행 파일, 설치 script 격리, AI 스킬과 Workspace 상태를 진단해야 한다.
- REQ-007-FR-05: 사용자는 선택 Git URL의 비대화형 읽기 접근을 검사하고 실패 유형별 조치를 확인할 수 있어야 한다.
- REQ-007-FR-06: 진단 결과는 사람용 설명과 자동화 가능한 JSON 요약·검사 목록을 제공해야 한다.
- REQ-007-FR-07: 사용자는 오래된 shim, dangling link, PATH 불일치와 손상 패키지를 식별하고 공식 clean install 절차로 복구할 수 있어야 한다.
- REQ-007-FR-08: 사용자는 CLI 설치와 별도로 거버넌스 스킬을 명시적으로 설치·갱신할 수 있어야 한다.
- REQ-007-FR-09: 설치 회귀 검사는 실제 사용자 홈과 전역 환경을 변경하지 않는 격리 prefix에서 수행되어야 한다.

## 사전조건

- 지원 환경에는 Node.js 14 이상, npm 6 이상과 Git 2.20 이상을 설치할 수 있어야 한다.
- npm registry 설치에는 대상 registry에 대한 네트워크, 인증과 패키지 접근 권한이 있어야 한다.
- 폐쇄망 설치에는 연결 환경에서 생성·검증된 tarball, checksum과 반입 승인이 있어야 한다.
- 전역 설치·제거에는 선택한 npm global prefix에 대한 사용자 쓰기 권한이 있어야 한다.
- 원격 진단에는 검사할 Git URL이 제공되어야 하며 대화형 credential prompt 없이 실행할 수 있어야 한다.
- clean install 전에 `npm prefix --global`, `npm root --global`과 PATH의 실제 실행 파일 위치를 확인해야 한다.

## 동작 규칙

1. 통합 설치는 `rdl`, `rundol`, `rundol-node` 실행 파일을 제공하고 `rdl`과 `rundol`은 같은 CLI 버전을 반환해야 한다.
2. 개별 설치는 `@rundol/cli`가 `rdl`·`rundol`, `@rundol/node`가 `rundol-node`를 제공해야 한다.
3. monorepo Git URL을 npm 전역 설치 대상으로 직접 사용하는 방식은 지원하지 않는다. 소스 commit 검증에는 그 commit에서 생성한 release tarball을 사용한다.
4. 폐쇄망 패키지는 `core → protocol → cli·node → rundol` 의존 순서로 pack 또는 publish해야 한다.
5. 통합 tarball이 내부 의존성을 bundle하지 않으면 모든 `@rundol/*` 의존 package를 먼저 사설 registry 또는 설치 가능한 tarball로 제공해야 한다.
6. 핵심 npm 패키지는 AI 스킬 설치를 `postinstall`에서 실행하지 않아야 한다. 스킬 설치는 `rdl skill install`로 분리한다.
7. doctor는 일반 명령 모듈 일부가 손상되어도 가능한 범위에서 먼저 실행되어 누락 파일을 진단해야 한다.
8. doctor는 각 check에 id, status, message, 요구 버전과 가능한 remediation을 제공하고 ok·warning·error·info를 집계해야 한다.
9. PATH 검사는 `rdl`과 `rundol` 후보를 모두 찾아 중복·오래된 shim 조사에 사용할 실제 경로를 반환해야 한다.
10. package 검사는 package manifest, CLI entrypoint, 핵심 source와 governance skill source 같은 필수 파일 존재를 확인해야 한다.
11. skill 검사는 대상 AI 클라이언트별 missing, unmanaged, stale, current 상태를 구분해야 한다. unmanaged 디렉터리는 `--force` 없이는 덮어쓰지 않는다.
12. 현재 위치에 Workspace가 없다는 사실은 설치 실패가 아닌 info 상태로 보고해야 한다.
13. Git URL 진단은 credential prompt를 비활성화하고 URL·오류 출력에서 사용자명·비밀번호·PAT 형태의 비밀을 마스킹해야 한다.
14. 원격 실패는 authentication, http-reset, dns, tls, not-found, 기타 git-remote로 분류해야 한다.
15. HTTP/2 reset은 명령 범위의 HTTP/1.1 fallback을 시험할 수 있으나 사용자 전역 Git 설정을 변경하지 않는다.
16. TLS 실패 해결을 위해 SSL 검증 비활성화를 권장하지 않고 인증서 체인과 사내 CA 구성을 안내해야 한다.
17. clean install은 현재 prefix의 런돌 패키지와 해당 prefix의 오래된 launcher만 제거한 뒤 공식 패키지를 다시 설치해야 한다.
18. 여러 Node 배포판이 있으면 설치에 사용한 npm prefix와 PATH에서 선택되는 실행 파일이 같은 경계를 가리켜야 한다.
19. PATH 변경 후에는 새 shell에서 version과 doctor를 다시 실행해 복구를 확인해야 한다.
20. 설치 테스트는 임시 npm cache·prefix·AI client home을 사용하고 종료 시 실제 사용자 환경을 변경하지 않아야 한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 지원 버전과 registry 접근 가능 | 통합 패키지 설치 | 세 실행 파일이 같은 release 버전을 반환하고 doctor 오류가 0건이다. |
| 개별 cli·node 패키지 설치 | version 확인 | `rdl`과 `rundol-node`가 설치 package 버전을 반환한다. |
| 검증된 전체 tarball 묶음 | 폐쇄망 설치 | 외부 public registry 없이 의존성을 해결하고 version·doctor를 통과한다. |
| 내부 dependency 없는 단일 통합 tarball | 설치 | 의존 package를 찾지 못하면 명확히 실패하며 불완전 설치를 성공으로 표시하지 않는다. |
| monorepo Git URL 직접 전역 설치 | 설치 시도 | 지원하지 않는 방식으로 문서화하며 release tarball 사용을 안내한다. |
| Node·npm·Git 최소 버전 미달 | doctor | 해당 check를 error로 표시하고 요구 버전과 설치 조치를 제공한다. |
| 핵심 source 파일 누락 | doctor | 다른 일반 명령을 불러오기 전에 package error와 재설치 조치를 반환한다. |
| PATH에 CLI 없음 | doctor | warn과 global prefix PATH 추가·shell 재시작 조치를 반환한다. |
| 여러 CLI shim 존재 | doctor | 모든 실제 후보 경로를 반환해 사용자가 오래된 항목을 식별할 수 있게 한다. |
| 스킬 누락·구버전·unmanaged | doctor | 상태별 warn과 일반 install 또는 명시적 force 조치를 구분한다. |
| Workspace 밖에서 실행 | doctor | info를 반환하며 전체 진단을 실패로 만들지 않는다. |
| 유효한 Git URL과 권한 | doctor git-url | git-remote check가 ok이며 비밀을 출력하지 않는다. |
| 인증·DNS·TLS·저장소 없음 | 원격 진단 | 서로 다른 kind와 구체적인 remediation을 반환한다. |
| HTTP reset 후 HTTP/1.1 성공 | 원격 진단 | warn과 명령 범위 fallback 조치를 반환한다. |
| dangling launcher 존재 | clean install | 현재 prefix의 launcher와 package만 제거하고 공식 package로 복구한다. |
| PATH가 다른 Node prefix를 선택 | 복구 확인 | 실제 command·prefix 불일치를 식별하고 새 shell에서 같은 prefix로 정렬한다. |

## 수용 기준

- [ ] 통합 tarball 설치 후 `rdl`, `rundol`, `rundol-node`가 모두 같은 버전을 반환한다.
- [ ] 개별 tarball 설치 후 CLI와 Node 실행 파일이 정상 실행된다.
- [ ] 설치된 `rundol` package가 삭제 예정 임시 clone을 가리키는 symlink·junction이 아니다.
- [ ] 설치 package에 핵심 설치를 실패시킬 `postinstall`이 없고 스킬이 자동 설치되지 않는다.
- [ ] 명시적 skill install 후 지원 AI client의 대상 경로에 관리 marker와 동일한 SKILL 파일이 생긴다.
- [ ] doctor가 Node·npm·Git 최소 버전과 package·postinstall·PATH·skill·Workspace 상태를 각각 보고한다.
- [ ] 핵심 일반 명령 source 하나를 제거한 설치 fixture에서도 doctor가 package error JSON을 반환한다.
- [ ] Workspace 밖 실행이 info이고 지원 환경의 doctor summary errors는 0건이다.
- [ ] PATH가 비어 있거나 중복 shim인 fixture에서 실제 후보 경로와 remediation을 확인할 수 있다.
- [ ] authentication, http-reset, dns, tls, not-found 오류 fixture가 정확한 kind로 분류된다.
- [ ] HTTP/1.1 fallback 성공이 warn으로 보고되고 전역 Git config가 변경되지 않는다.
- [ ] URL credential과 알려진 PAT 패턴이 JSON·stderr·로그에서 마스킹된다.
- [ ] TLS 오류 remediation이 SSL 검증 비활성화를 안내하지 않는다.
- [ ] 사설 registry 또는 전체 tarball 묶음의 폐쇄망 설치가 public network 없이 성공한다.
- [ ] 내부 dependency가 누락된 설치가 명확히 실패하고 doctor 성공으로 오인되지 않는다.
- [ ] clean install 후 PATH 실행 파일, npm prefix와 package root가 같은 설치 경계를 가리킨다.
- [ ] 복구 후 새 shell에서 version·doctor·fixture strict check가 성공한다.
- [ ] 설치 회귀 테스트가 실제 사용자 global prefix와 AI client skill 디렉터리를 변경하지 않는다.
- [ ] 테스트 종료 후 임시 prefix·cache가 정리되며 실패 시 선택적으로 진단 보존 경로를 제공한다.
- [ ] Windows, macOS와 Linux 지원 matrix에서 통합·개별 설치 및 doctor 회귀가 통과한다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 재현성 | 같은 release tarball과 지원 runtime에서 동일 executable·version·필수 파일을 설치한다. | tarball checksum과 설치 후 파일 목록·version을 OS matrix에서 비교한다. |
| 진단성 | 사용자가 하나의 doctor 결과로 실패 구성요소와 다음 조치를 식별할 수 있다. | 대표 설치·PATH·remote 오류 fixture의 check·remediation 완전성을 검사한다. |
| 보안 | 진단이 credential을 노출하거나 TLS 검증·전역 설정을 약화하지 않는다. | secret redaction과 Git config 전후 diff 테스트를 수행한다. |
| 복구성 | 부분 손상 상태에서도 doctor가 실행되고 clean install로 정상 상태를 복원한다. | 필수 파일·launcher 손상 주입 후 doctor와 재설치 시나리오를 실행한다. |
| 격리성 | 설치 테스트와 스킬 설치 테스트가 실제 사용자 환경에 부작용을 남기지 않는다. | 테스트 전후 global prefix·home·PATH·skill tree hash를 비교한다. |
| 호환성 | 지원 Node.js·npm·Git 및 주요 OS에서 동일 CLI 계약을 제공한다. | 최소·현재 버전과 OS 조합 CI matrix를 운영한다. |
| 성능 | remote 검사를 제외한 doctor가 일반 환경에서 2초 이내 완료된다. | clean·broken fixture에서 20회 측정한 95백분위를 사용한다. |

## 제외 범위

- Node.js, npm, Git 자체의 설치 프로그램과 운영체제 package manager를 제공하지 않는다.
- npm registry, 사설 registry와 Git server의 계정·권한·인증서를 발급하지 않는다.
- 지원하지 않는 monorepo Git URL 직접 전역 설치의 정상 동작을 보장하지 않는다.
- 사용자의 모든 Node 배포판, PATH와 shell profile을 자동 삭제·재작성하지 않는다.
- 사용자 확인 없이 unmanaged AI skill 디렉터리를 덮어쓰지 않는다.
- TLS 검증 비활성화, credential 평문 저장과 광범위한 전역 Git 설정 변경을 복구 방법으로 사용하지 않는다.
- Workspace 데이터·문서·태스크의 논리 복구와 Git 충돌 해결은 각 수명주기·동기화 요구사항에서 다룬다.
- release 버전 결정과 tag·CHANGELOG 정책은 별도 릴리스 요구사항에서 다룬다.
