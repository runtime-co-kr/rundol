# 문서와 프로젝트 거버넌스 관리

## 배경

프로젝트마다 필요한 문서의 깊이와 관점은 다르다. 개인 실험에 운영 런북과 외부 API 계약을 강제하면 문서가 형식적인 빈 양식으로 남고, 작은 프로젝트라는 이유로 데이터·보안·운영 위험을 생략하면 실제 변경 근거와 검증 가능성이 사라진다. 프로젝트 규모만으로 문서세트를 결정할 수도 없다. 작은 결제 서비스는 강한 검증이 필요하고, 큰 내부 자동화 저장소는 상대적으로 단순할 수 있다.

Rundol은 모든 프로젝트에 모든 유형을 강제하지 않으면서도, 필요한 문서가 무엇인지 사람과 AI가 같은 기준으로 판단할 수 있어야 한다. 초기화 시 프로젝트 특성을 인터뷰하거나 명시적인 프로파일을 선택하고, 그 결과를 버전 관리 가능한 문서 정책으로 보존해야 한다.

문서가 생성된 뒤에는 동일 유형이 항상 같은 물리 경로에 위치하고, 하나의 사실을 하나의 정본만 소유하며, 제품 목표부터 요구사항·설계·검증·운영 증거까지 실제 파일명으로 추적할 수 있어야 한다.

## 요구사항

- REQ-002-FR-01: 각 프로젝트는 미션, 목표, 범위, 역할, 멤버, 이해관계자, 책임, 위험과 완료 정의를 제공하는 단일 `project.md`를 가져야 한다.
- REQ-002-FR-02: 사용자는 guided 인터뷰, 내장 프로파일 또는 문서 유형별 수동 설정으로 프로젝트 문서 정책을 구성할 수 있어야 한다.
- REQ-002-FR-03: 시스템은 문서 유형별 정책을 `required`, `recommended`, `onDemand`, `disabled` 중 하나로 저장하고 사람이 읽을 수 있는 근거를 함께 제공해야 한다.
- REQ-002-FR-04: guided 인터뷰는 프로젝트 규모뿐 아니라 제품 성과, UI, 영속 데이터, 외부 인터페이스, 컴포넌트 경계, 운영, 보안·규제와 도메인 용어 특성을 평가해야 한다.
- REQ-002-FR-05: 사용자는 자동화 가능한 비대화형 옵션으로 guided 인터뷰와 동등한 문서 정책을 재현할 수 있어야 한다.
- REQ-002-FR-06: 사용자는 프로젝트 생성 후에도 문서 정책을 다시 확인하고 수동으로 변경할 수 있어야 하며, 변경이 기존 문서를 자동 삭제해서는 안 된다.
- REQ-002-FR-07: 사용자는 필요한 문서를 표준 ID, canonical 경로, frontmatter와 본문 템플릿으로 생성할 수 있어야 한다.
- REQ-002-FR-08: 시스템은 정책 누락, canonical 경로 이탈, 메타데이터, 책임 참조, 태그, 추적 링크와 중복 정본을 구조화된 진단으로 검사해야 한다.
- REQ-002-FR-09: 사용자는 기존 혼합 경로의 문서를 링크와 Git 이력을 보존하는 검토 가능한 절차로 canonical 경로에 이전할 수 있어야 한다.
- REQ-002-FR-10: CLI와 Rundol 거버넌스 스킬은 동일한 문서 정책 schema와 문서 유형 의미를 사용해야 한다.
- REQ-002-FR-11: 사람과 AI 클라이언트는 작업과 관련된 문서만 선택적으로 조회할 수 있어야 하며, 모든 정규 문서를 매 작업의 필수 컨텍스트로 강제하지 않아야 한다.
- REQ-002-FR-12: 사용자는 CLI, Board, IDE와 Obsidian에서 동일한 Markdown 정본을 정보 손실 없이 읽고 편집할 수 있어야 한다.

## 사전조건

- 대상 프로젝트가 Workspace Registry에 등록되고 프로젝트 worktree가 연결되어 있어야 한다.
- 프로젝트 루트에는 해당 프로젝트 키와 일치하는 `project.md`가 있어야 한다.
- guided 인터뷰를 완료하거나 비대화형 프로파일을 선택하는 주체는 프로젝트 목적과 운영 위험을 설명할 수 있어야 한다.
- 문서 생성 시 지원 유형, 한글 중심 제목과 `project.md`에 등록된 활성 담당자 ID를 제공해야 한다.
- 상위 근거가 필요한 문서는 실제로 존재하는 관련 산출물 ID를 제공해야 한다.
- 기존 문서 이전 전에는 대상 프로젝트 worktree가 병합 충돌 상태가 아니어야 한다.

## 동작 규칙

1. `project.md`는 문서 프로파일과 무관하게 항상 존재하는 프로젝트 고정 진입점이며 `project:<key>` ID를 사용한다.
2. 프로젝트 헌장의 역할·멤버·이해관계자와 책임 경계는 프로젝트 규모가 작아도 생략하지 않는다. 한 사람이 여러 역할을 맡을 수는 있다.
3. 정규 문서 유형은 `PRD`, `REQ`, `ARC`, `SCR`, `MOD`, `API`, `ADR`, `TST`, `RUN`, `GLS`다. `NTE`는 `inbox/`에 위치하는 비정규 임시 노트이며 문서 정책 완전성 검사 대상이 아니다.
4. 문서 정책의 네 상태는 서로 배타적이어야 하며 하나의 정규 유형이 두 상태에 동시에 속할 수 없다.
5. `required` 문서는 정책 준수 시점에 하나 이상의 유효한 문서가 존재해야 한다. 누락은 strict 오류다.
6. `recommended` 문서 누락은 위험과 생성 근거를 포함한 경고다. 사용자는 근거를 기록하고 `onDemand` 또는 `disabled`로 명시적으로 변경할 수 있다.
7. `onDemand` 문서는 생성 조건이 발생할 때만 만든다. 해당 유형이 없다는 이유만으로 진단하지 않는다.
8. `disabled`는 현재 프로젝트 범위에서 새 문서를 만들지 않는다는 명시적 결정이다. 이미 존재하는 문서는 삭제하지 않고 정책 불일치 경고와 검토 대상으로 남긴다.
9. 내장 프로파일은 최소한 `lean`, `product`, `service`, `platform`, `assured`를 제공하고 각 버전의 유형별 기본 정책을 결정적으로 조회할 수 있어야 한다.
10. 프로젝트 규모, 팀원 수와 기간은 프로파일 추천의 보조 신호로만 사용한다.
11. 제품 또는 서비스 성과를 합의해야 하면 `PRD`, 구현·검증할 동작이 있으면 `REQ`를 선택한다.
12. 사용자 화면·상호작용은 `SCR`, 영속 데이터·불변식·마이그레이션은 `MOD`, 외부 HTTP·CLI·이벤트 계약은 `API`의 생성 근거다.
13. 여러 컴포넌트·배포 단위 또는 중요한 품질 속성은 `ARC`, 별도 검증 계획·증거는 `TST`, 배포·관측·복구 책임은 `RUN`의 생성 근거다.
14. 되돌리기 어렵거나 여러 문서에 영향을 주는 결정이 발생할 때 `ADR`을 만들며, 초기 프로파일 선택만으로 빈 ADR을 생성하지 않는다.
15. 여러 참여자가 다르게 해석할 프로젝트 고유 용어가 있을 때 `GLS`를 사용한다. 일반 사전이나 문서 유형 목록을 반복하지 않는다.
16. 보안·규제·감사·안전 위험은 관련 REQ의 비기능 기준과 TST 증거 수준을 강화해야 하며 단순히 프로젝트 크기를 높이는 방식으로 처리하지 않는다.
17. 프로파일 선택은 정책만 저장하며 모든 유형의 빈 문서를 일괄 생성하지 않는다. 시스템은 누락된 required 문서와 다음 생성 명령을 결과로 제공한다.
18. guided 모드는 질문과 추천 근거를 보여주고 사용자의 최종 선택을 기록한다. 비대화형 모드는 stdin을 기다리지 않고 프로파일과 특성 override만으로 같은 정책을 산출한다.
19. 정책 변경은 이전 정책, 새 정책, 변경 주체와 변경 이유를 검토 가능한 이력으로 남기며 기존 문서와 링크를 자동 삭제하지 않는다.
20. 일반 산출물 ID는 `<3자리 코드>-<3자리 이상 번호>`, 파일명은 `<ID>-<한글 중심 제목>.md`를 사용한다.
21. 새 정규 문서는 다음 canonical 경로에만 생성한다.

| 유형 | canonical 경로 |
|---|---|
| `PRD` | `docs/prd/` |
| `REQ` | `docs/requirements/` |
| `ARC` | `docs/architecture/` |
| `SCR` | `docs/screens/` |
| `MOD` | `docs/model/` |
| `API` | `docs/api/` |
| `ADR` | `docs/adr/` |
| `TST` | `docs/tests/` |
| `RUN` | `docs/runbooks/` |
| `GLS` | `docs/glossary/` |

22. 모든 정규 문서는 `id`, `type`, `kind`, `title`, `description`, `owner`, `state`, `tags`, `aliases`, `related` 필드를 유지해야 한다.
23. `owner`와 `reviewers`는 `project.md`의 `MEMBER-*`, `stakeholders`는 `STAKEHOLDER-*` block을 실제 Wiki link로 참조해야 한다.
24. related와 본문의 문서 링크는 alias가 아닌 실제 파일명을 대상으로 하며 section과 block 링크는 실제 heading 또는 block ID를 가리켜야 한다.
25. 하나의 사실은 하나의 정본 문서만 소유한다. `project.md`는 사람과 의사결정 체계, PRD는 제품 성과, REQ는 검증할 동작을 소유하고 관점 문서는 내용을 복사하지 않고 REQ를 실현한다.
26. `rdl doc create`는 프로젝트 전체에서 기존 ID와 파일을 탐색한 후 ID를 예약하고 canonical 경로에만 새 문서를 생성한다.
27. legacy 위치의 문서는 읽기와 검사의 대상으로 유지하되 새 문서 생성 위치의 근거로 사용하지 않는다.
28. 문서 이전은 먼저 dry-run으로 이동 대상, 목적지, 링크 변경과 충돌을 제시해야 한다. 적용 시 모든 이동과 링크 갱신이 성공하거나 원래 byte와 경로로 복원되어야 한다.
29. 동일 ID 또는 같은 정본 역할의 문서가 legacy와 canonical 경로에 함께 있으면 자동 병합하지 않고 중복 정본 오류를 반환한다.
30. 거버넌스 스킬은 프로젝트 인터뷰와 본문 의미 작성을 담당하고, CLI는 정책 저장, ID·경로 선택, 파일 생성·이전과 검증을 결정적으로 수행한다.
31. 작업 컨텍스트는 기본적으로 `project.md`, 관련 PRD·REQ와 작업 관점 문서를 포함하고, 무관한 문서는 필요할 때만 추가한다.
32. 문서 변경은 strict 검증을 통과한 경우에만 Rundol의 저장 흐름으로 commit할 수 있어야 한다.

## 상태와 예외

| 현재 상태 또는 상황 | 입력 또는 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 신규 프로젝트이며 정책 없음 | guided 초기화 | 인터뷰 결과, 추천 근거와 최종 문서 정책을 저장한다. |
| 신규 프로젝트이며 자동화 환경 | profile·특성 옵션으로 초기화 | stdin을 기다리지 않고 같은 입력에 같은 정책을 만든다. |
| 기존 프로젝트이며 정책 없음 | configure 또는 check | 문서를 삭제·이동하지 않고 `legacy-unconfigured` 상태와 설정 경로를 제공한다. |
| required 유형 문서가 없음 | strict 검사 | 유형, 근거와 생성 명령을 포함한 오류를 반환한다. |
| recommended 유형 문서가 없음 | 검사 | 추천 근거와 override 방법을 포함한 경고를 반환한다. |
| onDemand 또는 disabled 유형 문서가 없음 | 검사 | 누락 진단을 만들지 않는다. |
| disabled 유형 문서가 이미 있음 | 검사 | 파일을 보존하고 정책 검토 경고를 반환한다. |
| 사용자가 정책을 변경함 | reconfigure | 기존 문서를 삭제하지 않고 정책과 변경 근거만 갱신한다. |
| 유효한 유형·제목·담당자 제공 | `rdl doc create` | 고유 ID와 canonical 경로·메타데이터를 가진 초안 파일을 생성한다. |
| 등록되지 않은 담당자 또는 related | 문서 생성 | 파일을 만들지 않고 유효한 후보와 오류를 반환한다. |
| 같은 유형 문서가 legacy 경로에 있음 | 새 문서 생성 | 기존 ID를 고려해 중복 ID를 만들지 않고 canonical 경로에 새 ID를 생성한다. |
| 동일 ID가 두 경로에 있음 | check 또는 migration | 중복 정본 오류를 반환하고 자동 선택하지 않는다. |
| legacy 문서가 canonical 위치와 충돌하지 않음 | migration dry-run | 이동·링크 변경 계획과 검증 범위를 반환하고 파일을 변경하지 않는다. |
| migration 중 파일·링크 검증 실패 | apply | 모든 변경을 원래 byte와 경로로 복원하고 실패 진단을 반환한다. |
| 문서가 canonical 경로 밖에 있음 | structure 검사 | 삭제 후보가 아닌 이전 대상으로 보고한다. |
| 본문 링크 대상 파일·heading·block이 없음 | strict 검사 | 파일, 줄, artifact ID와 target을 포함한 오류를 반환한다. |
| 프로젝트 변경 없음 | save | 새 commit을 만들지 않고 변경 없음 결과를 반환한다. |
| 프로젝트 문서가 모두 유효함 | save | 변경을 프로젝트 branch의 검증된 commit으로 저장한다. |

## 수용 기준

- [ ] guided 인터뷰가 제품 성과, UI, 데이터, API, 컴포넌트, 운영, 보안·규제와 용어 특성을 묻고 유형별 추천 근거를 제공한다.
- [ ] 같은 profile과 특성 override를 사용한 비대화형 실행은 플랫폼과 실행 순서에 관계없이 같은 문서 정책을 만든다.
- [ ] 정책의 모든 정규 유형은 정확히 하나의 상태에 속하고 중복·미지원 유형은 저장 전에 거부된다.
- [ ] profile 선택만으로 `project.md` 이외의 빈 정규 문서를 일괄 생성하지 않는다.
- [ ] required 누락은 strict 오류, recommended 누락은 경고이며 onDemand·disabled 누락은 진단하지 않는다.
- [ ] reconfigure가 기존 문서와 Git 이력을 삭제하지 않고 변경 전후 정책과 이유를 보존한다.
- [ ] 신규 프로젝트의 `project.md`가 필수 거버넌스 영역과 ROLE·MEMBER·STAKEHOLDER block을 유지한다.
- [ ] 각 정규 문서 유형을 생성하면 고유 ID, canonical 경로, 한글 중심 파일명과 필수 frontmatter가 만들어진다.
- [ ] 등록되지 않은 owner와 존재하지 않는 related를 사용한 생성 요청은 파일과 ID 예약을 남기지 않는다.
- [ ] `rdl check --structure`가 canonical 경로 밖의 정규 문서를 이전 대상으로 구분해 보고한다.
- [ ] migration dry-run은 파일을 변경하지 않고 모든 이동·링크 변경·충돌을 제시한다.
- [ ] migration apply 후 실제 파일명 Wiki link와 frontmatter related가 새 위치에서도 모두 해석된다.
- [ ] migration 실패 시 대상 프로젝트의 파일 경로와 byte가 작업 전과 동일하게 복원된다.
- [ ] legacy와 canonical 경로의 동일 ID를 자동 병합하거나 임의 선택하지 않는다.
- [ ] CLI와 Rundol 스킬이 같은 profile 이름, 문서 유형, 정책 상태와 생성 조건을 해석한다.
- [ ] 작업별 컨텍스트 조회가 project, 관련 PRD·REQ와 필요한 관점 문서를 반환하고 무관한 전체 문서세트를 기본 포함하지 않는다.
- [ ] strict 검사 실패 상태에서는 save가 commit을 만들지 않는다.
- [ ] 유효한 변경을 save한 후 프로젝트 worktree가 깨끗하고 새 commit에서 문서와 정책을 다시 읽을 수 있다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 추적성 | 제품 목표부터 REQ·설계·검증·운영 증거까지 실제 파일명으로 탐색할 수 있다. | 문서 graph에서 끊어진 링크와 고립된 required 산출물을 검사한다. |
| 단순성 | 일반 작업은 전체 문서세트가 아니라 project와 관련 문서 2~5개로 시작할 수 있다. | 대표 태스크별 컨텍스트 선택 결과의 문서 수와 관련성을 검토한다. |
| 결정성 | 같은 profile·특성 입력과 파일 집합은 같은 정책, ID와 진단을 만든다. | 파일 열거 순서와 운영체제를 바꾼 반복 결과를 비교한다. |
| 데이터 안전성 | 정책 변경과 migration 실패가 기존 문서, 링크와 Git 이력을 삭제하지 않는다. | 단계별 실패 주입 후 경로, file hash와 HEAD를 비교한다. |
| 성능 | 문서 1천 건 프로젝트의 정책·경로·링크 strict 검사가 일반 개발 환경에서 5초 이내 완료된다. | 표준 대규모 fixture에서 20회 측정한 95백분위 값을 사용한다. |
| 상호운용성 | UTF-8 Markdown을 IDE, Obsidian, CLI와 Board에서 정보 손실 없이 왕복한다. | 한글·Wiki link·Mermaid fixture의 byte와 파싱 결과를 비교한다. |
| 진단성 | 오류가 정책 상태, 문서 유형, 파일, 줄과 가능한 해결 명령을 포함한다. | 모든 정책·구조 진단의 JSON 필드를 검사한다. |
| 확장성 | 새 profile 추가가 기존 project policy와 문서 의미를 조용히 변경하지 않는다. | profile schema version과 이전 버전 fixture의 재해석 방지 테스트를 수행한다. |

## 제외 범위

- 문서 정책 저장 위치와 schema의 구체적인 Git 소유 경계는 아키텍처 결정과 데이터 모델에서 확정한다.
- guided 인터뷰의 자연어 표현과 특정 AI provider의 프롬프트 구현은 공통 요구사항으로 고정하지 않는다.
- 조직별 문서 본문 문체, 승인 절차와 업무 용어 자체를 하나의 양식으로 강제하지 않는다.
- 문서 의미의 사실성, 요구사항의 사업 타당성과 사람의 최종 승인 여부를 자동 판정하지 않는다.
- 범용 워드프로세서 수준의 페이지 레이아웃과 바이너리 첨부 편집을 제공하지 않는다.
- 문자 단위 실시간 공동 편집과 강한 잠금을 제공하지 않는다.
- 태스크 상태·완료 조건과 태스크 shard 저장의 상세 규칙은 별도 요구사항에서 다룬다.
- 원격 fetch·merge·push와 의미적 충돌 해결은 동기화 요구사항에서 다룬다.
