# 문서와 프로젝트 거버넌스 관리

## 배경

프로젝트 문서가 자유 형식 파일로만 관리되면 목표와 구현 사이의 연결, 최종 책임자, 검토 대상과 완료 조건이 쉽게 누락된다. 사람과 AI 클라이언트가 각각 다른 제목·경로·링크 관례를 사용하면 문서를 찾기 어렵고 자동 검증과 영향 분석도 신뢰할 수 없다.

런돌은 프로젝트마다 하나의 고정 헌장을 두고, 제품 목표부터 요구사항·설계·검증·운영까지 유형별 정규 문서를 연결한다. 내용 자체를 획일화하지 않으면서도 필수 메타데이터, 책임 구조, 실제 파일을 가리키는 Wiki link와 추적 방향은 공통 계약으로 유지해야 한다.

## 요구사항

- REQ-002-FR-01: 각 프로젝트는 미션, 목표, 범위, 사람, 책임, 위험과 완료 정의를 제공하는 단일 `project.md`를 가져야 한다.
- REQ-002-FR-02: 사용자는 지원 문서 유형을 표준 ID, 경로, frontmatter와 본문 템플릿으로 생성할 수 있어야 한다.
- REQ-002-FR-03: 문서 담당자·검토자·이해관계자는 프로젝트 헌장에 등록된 실제 주체와 연결되어야 한다.
- REQ-002-FR-04: 하위 문서는 제품 목표·요구사항·설계·검증 근거를 실제 문서 파일명 기반 Wiki link로 추적할 수 있어야 한다.
- REQ-002-FR-05: 시스템은 문서 구조, 메타데이터, 파일명, 책임 참조, 태그와 Wiki link를 프로젝트 단위 또는 선택 범위로 검사해야 한다.
- REQ-002-FR-06: 사용자는 CLI, Board, IDE와 Obsidian에서 동일한 Markdown 정본을 읽고 편집할 수 있어야 한다.
- REQ-002-FR-07: 문서 변경은 엄격 검증을 통과한 경우에만 프로젝트 브랜치에 저장할 수 있어야 한다.
- REQ-002-FR-08: 시스템은 오류를 코드, 범주, 파일, 줄, 문서 ID와 대상 링크가 포함된 구조화된 진단으로 제공해야 한다.

## 사전조건

- 대상 프로젝트가 Workspace Registry에 등록되고 프로젝트 worktree가 연결되어 있어야 한다.
- 프로젝트 루트에 해당 프로젝트의 `project.md`가 있어야 한다.
- 문서 생성 시 유형, 한글 중심 제목과 `project.md`에 등록된 활성 담당자 ID를 제공해야 한다.
- REQ, SCR, MOD, API, TST와 RUN 유형은 실제로 존재하는 상위 관련 문서 ID를 제공해야 한다.
- 편집 주체는 프로젝트 파일과 전용 Git 브랜치에 대한 로컬 쓰기 권한을 가져야 한다.
- Board 편집은 조회 시 받은 현재 문서 revision을 기준으로 시작해야 한다.

## 동작 규칙

1. `project.md`는 일반 산출물 ID를 사용하지 않는 고정 진입점이며 프로젝트 키에 대응하는 `project:<key>` ID를 가져야 한다.
2. 프로젝트 헌장은 미션, 검증 가능한 목표, 포함·제외 범위, 역할, 멤버, 이해관계자, RACI, 의사결정, 위험, 협업 리듬과 완료 정의를 모두 유지해야 한다.
3. 역할·멤버·이해관계자 분류는 프로젝트 규모와 무관하게 생략하지 않는다. 한 사람이 여러 역할을 맡는 것은 허용한다.
4. 정규 문서 유형은 PRD, GLS, ARC, REQ, SCR, MOD, API, ADR, TST, RUN과 NTE를 지원한다.
5. 정규 문서 ID는 `<3자리 유형>-<3자리 이상 번호>` 형식이며 프로젝트 안에서 ID와 alias가 고유해야 한다.
6. 문서 파일명은 `<ID>-<한글 중심 제목>.md` 형식을 사용하고 유형별 표준 하위 디렉터리에 저장한다.
7. 모든 정규 문서는 `id`, `type`, `kind`, `title`, `description`, `owner`, `state`, `tags`, `aliases`, `related` 필드를 유지해야 한다.
8. 태그에는 `rundol/`, `artifact/`, `domain/`, `feature/` namespace가 각각 하나 이상 있어야 한다.
9. owner와 reviewers는 `project.md`의 `MEMBER-*`, stakeholders는 `STAKEHOLDER-*` block을 실제 Wiki link로 참조해야 한다.
10. related와 본문의 문서 링크는 alias만 쓰지 않고 실제 물리 파일명을 대상으로 해야 한다. section과 block 링크는 실제 heading 또는 block ID가 있어야 한다.
11. 하나의 사실은 하나의 정본 문서에 정의하고 다른 문서는 링크로 참조한다. PRD는 제품 성과, REQ는 검증 가능한 동작, 상세 문서는 화면·모델·API·결정·테스트·운영 관심사를 소유한다.
12. 결정되지 않은 필드는 삭제하지 않고 `미정` 또는 `작성 필요`와 확인 책임을 남긴다. 정식 저장 전에는 해당 값을 해소하거나 후속 태스크로 추적한다.
13. 기본 검사는 미해결 본문 Wiki link를 경고로 보고하고, 엄격 검사는 같은 문제를 오류로 처리한다. canonical metadata와 책임 참조 오류는 항상 오류로 처리한다.
14. Board 편집은 frontmatter를 보존하고 `baseRevision`을 현재 revision과 비교해야 한다. 불일치 시 기존 내용을 덮어쓰지 않는다.
15. Board 저장 후 엄격 검증이 실패하면 파일을 편집 전 원본으로 복원하고 진단을 반환해야 한다.
16. `rdl save`는 프로젝트 전체를 엄격 검사한 뒤 변경이 있을 때만 `rdl: update workspace` 커밋을 생성한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 유효한 유형·제목·담당자 제공 | `rdl doc create` | 다음 ID와 표준 경로·메타데이터를 가진 초안 파일을 생성한다. |
| 관련 문서가 필수인 유형 | related 없이 생성 요청 | 파일을 만들지 않고 관련 문서 필요 오류를 반환한다. |
| 등록되지 않은 담당자 | 문서 생성·검증 | 책임 참조 오류를 반환하고 유효한 문서로 저장하지 않는다. |
| 지원하지 않는 유형 | 문서 생성 요청 | 허용 유형 목록을 확인할 수 있는 입력 오류를 반환한다. |
| 동일 유형 문서가 여러 경로에 존재 | 새 문서 생성 | 기존 최대 번호 다음의 고유 ID를 예약하고 중복을 만들지 않는다. |
| 파일명과 frontmatter ID 불일치 | strict 검사 | 해당 파일과 기대 형식을 포함한 오류를 반환한다. |
| alias가 실제 문서 ID와 중복 | 검사 | 모호한 문서 식별 오류를 반환한다. |
| 본문 링크가 alias만 가리킴 | strict 검사 | 실제 파일명을 사용하도록 오류와 대상을 제공한다. |
| 링크 대상 파일·heading·block 없음 | 기본 검사·strict 검사 | 기본에서는 경고, strict에서는 저장을 차단하는 오류가 된다. |
| Board의 base revision이 오래됨 | 문서 저장 요청 | `409 Conflict`와 최신 엔티티를 반환하고 파일을 변경하지 않는다. |
| Board 편집 결과 strict 검사 실패 | 문서 저장 요청 | 원본 파일을 복원하고 검증 오류를 반환한다. |
| 프로젝트 변경 없음 | `rdl save` | 새 commit을 만들지 않고 변경 없음 결과를 반환한다. |
| 프로젝트 문서가 모두 유효함 | `rdl save` | 변경을 프로젝트 branch에 하나의 검증된 commit으로 저장한다. |

## 수용 기준

- [ ] 신규 프로젝트의 `project.md`가 필수 10개 거버넌스 영역과 ROLE·MEMBER·STAKEHOLDER block을 포함한다.
- [ ] 지원되는 각 문서 유형을 생성하면 고유 ID, 표준 디렉터리, 한글 중심 파일명과 필수 frontmatter가 만들어진다.
- [ ] 등록된 담당자는 실제 `MEMBER-*` block 링크로 기록되고 미등록 담당자의 생성 요청은 파일을 남기지 않는다.
- [ ] 관련 문서가 필수인 유형은 유효한 related 없이는 생성되지 않는다.
- [ ] 생성된 related 링크는 alias가 아닌 실제 대상 파일명을 사용한다.
- [ ] 필수 frontmatter 필드 누락, ID·파일명 불일치, 필수 태그 누락과 중복 alias가 각각 구조화된 오류로 탐지된다.
- [ ] 프로젝트 헌장의 역할·멤버·이해관계자 필드 누락과 잘못된 RACI 참조가 엄격 검사에서 탐지된다.
- [ ] 존재하지 않는 파일·heading·block Wiki link는 strict 검사에서 저장 차단 오류가 된다.
- [ ] `rdl check <ARTIFACT-ID>`, `--links`, `--tasks`가 요청 범위에 맞춰 진단을 필터링한다.
- [ ] JSON 검사 결과에서 schema version, project, diagnostics와 오류·경고 집계를 파싱할 수 있다.
- [ ] Board가 최신 base revision의 유효한 Markdown 본문을 저장하고 frontmatter를 보존한다.
- [ ] 오래된 base revision 또는 strict 검사 실패 시 Board가 기존 파일 byte를 변경하지 않는다.
- [ ] IDE나 Obsidian에서 직접 편집한 유효한 파일이 refresh·check·save에서 동일 정본으로 인식된다.
- [ ] strict 검사 실패 상태에서는 `rdl save`가 commit을 만들지 않는다.
- [ ] 유효한 변경을 save한 후 프로젝트 worktree가 깨끗하고 새 commit에서 문서를 다시 읽을 수 있다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 추적성 | PRD부터 요구사항·설계·검증·운영 문서까지 실제 파일 링크로 탐색할 수 있다. | fixture의 문서 graph에서 끊어진 링크와 고립된 필수 산출물을 검사한다. |
| 무결성 | 엄격 검사 오류가 있는 문서는 프로젝트 commit으로 저장되지 않는다. | 오류 fixture마다 save 전후 HEAD와 파일 hash를 비교한다. |
| 결정성 | 같은 파일 집합의 검사 결과와 문서 ID 선택이 실행 순서와 무관하게 같다. | 파일 열거 순서를 변경한 반복 테스트 결과를 비교한다. |
| 성능 | 문서 1천 건 규모 프로젝트의 strict 검사가 일반 개발 환경에서 5초 이내 완료된다. | 표준 대규모 fixture에서 20회 측정한 95백분위 값을 사용한다. |
| 상호운용성 | UTF-8 Markdown을 IDE, Obsidian, CLI와 Board에서 정보 손실 없이 왕복할 수 있다. | 한글·Wiki link·Mermaid가 포함된 round-trip fixture의 byte와 파싱 결과를 비교한다. |
| 복구성 | 실패한 편집과 저장 시도 후 마지막 유효 문서를 보존한다. | 쓰기·검증·commit 단계에 실패를 주입하고 원본 hash와 HEAD를 확인한다. |
| 진단성 | 오류가 수정 대상과 원인을 한 번에 식별할 정보를 제공한다. | 모든 진단에 code, category, file과 가능한 line·artifactId·target이 있는지 검사한다. |

## 제외 범위

- 조직별 문서 본문 표현, 승인 절차와 업무 용어 자체를 표준화하지 않는다.
- 범용 워드프로세서 수준의 서식, 페이지 레이아웃과 바이너리 첨부 편집을 제공하지 않는다.
- 문서 의미의 사실성, 요구사항의 사업 타당성과 사람의 최종 승인 여부를 자동 판정하지 않는다.
- 문자 단위 실시간 공동 편집과 강한 잠금은 제공하지 않는다.
- 태스크 상태·완료 조건과 태스크 샤드 저장의 상세 규칙은 별도 요구사항에서 다룬다.
- 원격 fetch·merge·push와 충돌 해결의 상세 정책은 동기화 요구사항에서 다룬다.
- 프로젝트 헌장을 일반 문서 생성 명령으로 교체하거나 프로젝트마다 여러 개 만들 수 있도록 하지 않는다.
