# 패키지 버전과 릴리스 관리

## 배경

런돌은 core, protocol, CLI, Node, Board와 통합 package를 하나의 monorepo에서 배포한다. package별 버전이나 내부 의존성이 어긋나면 설치 조합에 따라 다른 동작이 나타나고, package version·CHANGELOG·Git tag가 불일치하면 사용자가 어떤 소스와 산출물을 설치했는지 재현하기 어렵다.

릴리스 번호는 배포 횟수가 아니라 호환성의 의미를 전달해야 한다. 정식 릴리스는 단순히 main에 병합되거나 package.json을 수정한 상태가 아니라, 전체 검증을 통과한 병합 commit에 이동하지 않는 annotated tag를 만들고 실제 tarball 설치까지 확인한 상태여야 한다.

## 요구사항

- REQ-009-FR-01: 유지관리자는 SemVer에 따라 변경의 호환성 의미를 나타내는 다음 버전을 선택할 수 있어야 한다.
- REQ-009-FR-02: 시스템은 루트와 모든 workspace package가 하나의 release version을 사용하도록 검증해야 한다.
- REQ-009-FR-03: 시스템은 package 이름·배포 경계·내부 의존성·설치 script 정책의 정합성을 검증해야 한다.
- REQ-009-FR-04: 각 release version은 사용자 영향 변경을 설명하는 CHANGELOG 항목과 대응해야 한다.
- REQ-009-FR-05: 정식 release Git tag는 `v<version>` 형식으로 package version과 정확히 일치해야 한다.
- REQ-009-FR-06: branch·MR에서는 버전 검사와 전체 테스트를, tag에서는 전체 release 검사를 자동 실행해야 한다.
- REQ-009-FR-07: release 검사는 통합·개별 package tarball을 격리 환경에 실제 설치하고 제공 executable을 검증해야 한다.
- REQ-009-FR-08: 사용자는 Git tag·commit과 checksum으로 특정 release 산출물을 재현·검증할 수 있어야 한다.
- REQ-009-FR-09: 잘못된 release는 기존 version·tag를 이동·재사용하지 않고 새 patch 또는 prerelease로 수정해야 한다.

## 사전조건

- release 대상 변경이 보호된 main에 병합 가능한 review와 테스트 상태여야 한다.
- 모든 workspace manifest, root manifest와 CHANGELOG를 수정할 권한이 있어야 한다.
- 전체 테스트와 tarball pack·설치를 실행할 지원 Node.js·npm·Git 환경이 있어야 한다.
- 정식 tag 생성·push에는 저장소 maintainer 권한이 있어야 한다.
- registry publish를 수행하는 경우 대상 version이 아직 게시되지 않았고 publish 권한이 있어야 한다.
- release commit은 작업 트리가 깨끗하고 version·CHANGELOG 변경을 포함해야 한다.

## 동작 규칙

1. version은 `MAJOR.MINOR.PATCH` SemVer 형식을 사용하고 정식 Git tag는 `vMAJOR.MINOR.PATCH`를 사용한다.
2. 1.0 이전에도 호환 버그 수정은 PATCH, 호환 기능 묶음은 MINOR, 호환성 파괴는 MINOR와 migration 명시로 구분한다.
3. 1.0 이후 호환 버그 수정은 PATCH, 호환 기능은 MINOR, 저장 format·CLI·API 호환성 파괴는 MAJOR를 올린다.
4. CI build 횟수와 날짜를 version 숫자로 사용하지 않고 검증 전 배포는 alpha·beta·rc prerelease를 사용한다.
5. 같은 기능의 반복 수정은 PATCH를 올리고 사용자가 인식할 새 기능 묶음에서만 MINOR를 올린다.
6. 루트 `@rundol/monorepo`는 private true이며 bin과 배포 files를 소유하지 않는다.
7. package name은 전체 workspace에서 고유해야 하고 unscoped `rundol` 이름은 통합 배포 package가 정확히 한 번만 소유한다.
8. core, protocol, cli, node, board와 rundol package version은 root release version과 모두 같아야 한다.
9. `@rundol/*` 내부 의존성은 대응 release의 정확한 version 또는 검증용 staged tarball을 가리켜야 한다.
10. 핵심 package와 workspace package는 사용자 환경을 암묵적으로 변경하는 `postinstall` script를 두지 않는다.
11. CHANGELOG에는 `[<version>]` 제목, release 날짜와 Added·Changed·Fixed 등 사용자 영향 분류를 기록해야 한다.
12. 호환성 파괴는 CHANGELOG와 migration 문서에 영향·전환 절차를 명시해야 한다.
13. `version:check`는 SemVer, monorepo 경계, 이름 고유성, 동일 version, postinstall 부재, CHANGELOG와 선택 CI tag 일치를 검사해야 한다.
14. `release:check`는 version check, 전체 test suite와 통합·개별 tarball 설치 회귀를 순서대로 모두 통과해야 한다.
15. tarball은 `core → protocol → cli·node → rundol` 의존 순서로 만들고 격리 prefix에서 실제 package dependency를 사용해 설치한다.
16. 통합 설치는 `rdl`, `rundol`, `rundol-node`, 개별 설치는 `rdl`과 `rundol-node` version을 검증해야 한다.
17. 일반 branch와 MR pipeline은 version check와 전체 테스트를 실행하고 열린 MR이 있으면 같은 commit의 중복 push pipeline을 만들지 않는다.
18. tag pipeline은 `CI_COMMIT_TAG`와 package version 일치를 포함한 release check를 실행해야 한다.
19. release MR을 main에 병합한 뒤 maintainer가 해당 병합 commit에 annotated tag를 만들고 push해야 한다.
20. tag는 이동·삭제 후 재사용하지 않고 같은 version에 다른 내용을 다시 배포하지 않는다.
21. 정식 배포 후 registry 또는 tarball 설치, version과 doctor를 smoke test해야 한다.
22. 자동 registry publish를 도입할 경우 같은 Git tag와 npm package version을 하나의 release pipeline에서 생성·검증해야 한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 호환 버그 수정 | 다음 version 결정 | PATCH를 증가시키고 다른 숫자는 유지한다. |
| 호환 기능 묶음 | 다음 version 결정 | MINOR를 증가시키고 PATCH를 0으로 설정한다. |
| 1.0 이후 호환성 파괴 | 다음 version 결정 | MAJOR를 증가시키고 migration을 문서화한다. |
| 검증 전 후보 배포 | version 결정 | 정식 version 재사용 대신 alpha·beta·rc prerelease를 사용한다. |
| root version이 SemVer 아님 | version check | 오류와 잘못된 version을 반환한다. |
| workspace package version 불일치 | version check | package 이름과 실제·기대 version을 포함한 오류를 반환한다. |
| package name 중복 또는 rundol 소유권 위반 | version check | 중복 이름·경계 오류를 반환한다. |
| CHANGELOG release 항목 없음 | version check | 기대 `[version]` 항목을 포함한 오류를 반환한다. |
| CI tag와 package version 불일치 | tag pipeline | release check를 실패시키고 배포하지 않는다. |
| branch·MR commit | CI | version check와 전체 테스트를 실행하고 tag 전용 설치 검사는 생략할 수 있다. |
| 정식 tag commit | CI | 전체 release check와 tarball 설치 회귀를 실행한다. |
| 통합 tarball 설치 | install test | 세 executable이 release version을 반환하고 doctor가 통과한다. |
| 개별 cli·node tarball 설치 | install test | 각 executable이 release version을 반환한다. |
| 설치 결과가 임시 clone symlink | install test | 릴리스 실패로 처리한다. |
| 일부 release 검사 실패 | tag·publish 전 | tag 생성·registry publish를 중단한다. |
| tag 없는 main merge | release 판단 | 통합 상태일 뿐 정식 release로 간주하지 않는다. |
| 잘못된 정식 release 발견 | 수정 배포 | 기존 tag를 이동하지 않고 새 PATCH version을 준비한다. |

## 수용 기준

- [ ] 정상·prerelease·build metadata SemVer와 잘못된 leading zero·형식 fixture를 정확히 구분한다.
- [ ] root와 모든 workspace package가 동일 release version을 사용하지 않으면 version check가 실패한다.
- [ ] package name 중복과 unscoped `rundol` 이름의 0개·2개 이상 소유가 탐지된다.
- [ ] root private 경계, bin·files 부재와 workspace 배포 경계 위반이 탐지된다.
- [ ] 모든 내부 `@rundol/*` dependency가 대응 release version과 일치한다.
- [ ] 어떤 package에든 postinstall이 추가되면 release check가 실패한다.
- [ ] 현재 version의 CHANGELOG 항목이 없으면 version check가 실패한다.
- [ ] CI tag `v<version>`은 통과하고 접두사·숫자가 다른 tag는 실패한다.
- [ ] branch와 MR pipeline이 version check 및 전체 테스트를 실행한다.
- [ ] 열린 MR이 있는 동일 commit에서 중복 branch pipeline이 생성되지 않는다.
- [ ] tag pipeline이 version check·전체 테스트·설치 회귀를 모두 실행한다.
- [ ] pack 결과가 core, protocol, cli, node와 통합 rundol의 5개 tarball을 포함한다.
- [ ] 통합 tarball 설치에서 `rdl`, `rundol`, `rundol-node` version이 모두 release version과 같다.
- [ ] 개별 tarball 설치에서 CLI와 Node 실행 파일이 정상 동작한다.
- [ ] 설치 package가 임시 clone을 가리키는 symlink·junction이 아니며 필수 파일을 포함한다.
- [ ] 설치 smoke test의 doctor summary errors가 0이고 fixture strict check가 통과한다.
- [ ] release test가 실제 사용자 global prefix·npm cache·AI skill home을 변경하지 않는다.
- [ ] annotated tag가 main의 검증된 release commit을 가리키며 package version과 일치한다.
- [ ] 동일 version의 산출물 checksum이 변경되거나 tag가 이동하면 release 무결성 오류로 처리한다.
- [ ] 실패한 release를 새 patch 또는 prerelease로 수정하고 이전 tag·산출물을 덮어쓰지 않는다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 재현성 | 같은 tag에서 생성한 package 목록·version·내용 checksum이 동일하다. | 격리된 두 build의 tarball canonical content와 checksum을 비교한다. |
| 무결성 | package·CHANGELOG·tag·내부 dependency가 하나의 release version을 가리킨다. | version check와 설치 후 manifest·tag 검사를 수행한다. |
| 호환성 | version 증가가 사용자 관찰 가능 계약 변화와 일치한다. | release MR에서 변경 분류와 CLI·API·format diff를 검토한다. |
| 격리성 | release 검사가 개발자와 CI runner의 실제 global 환경을 변경하지 않는다. | 실행 전후 prefix·cache·home tree와 환경 변수를 비교한다. |
| 추적성 | 산출물에서 version, tag, source commit과 CHANGELOG를 역추적할 수 있다. | 설치 package manifest와 release metadata를 Git ref와 대조한다. |
| 보안 | 검증되지 않은 script와 변경 가능한 ref를 정식 배포 근거로 사용하지 않는다. | package script audit과 tag immutability 정책을 검사한다. |
| 성능 | release check가 CI 표준 runner에서 15분 이내 완료된다. | 최근 20개 tag pipeline의 95백분위 실행 시간을 측정한다. |

## 제외 범위

- npm registry 자체 운영, 계정·token 발급과 결제 정책을 제공하지 않는다.
- 자동 registry publish는 현재 제공하지 않으며 도입 시 별도 보안·승인 설계를 요구한다.
- 지원하지 않는 monorepo Git URL 직접 전역 설치를 정식 배포 방식으로 사용하지 않는다.
- CI build 횟수·날짜를 package SemVer 숫자로 표현하지 않는다.
- 같은 version의 tag 이동, 산출물 교체와 재게시를 허용하지 않는다.
- release 검사를 통과하지 않은 branch·commit을 정식 안정 버전으로 선언하지 않는다.
- 변경의 사업 우선순위와 release 일정 자체는 제품 책임자의 의사결정 범위로 둔다.
- Workspace 프로젝트 문서의 버전과 npm 제품 package version을 같은 수명주기로 강제하지 않는다.
