# 보드 런 대기 조회와 사람 게이트 승인

## 배경

사람 게이트는 런을 멈추게 하도록 설계되었고, 그것을 지나는 유일한 경로는 human 유형 Client가 수행하는 승인이다. 그런데 그 경로가 명령줄에만 있어서, 승인해야 하는 사람이 터미널을 열고 런 ID와 Client ID를 옮겨 적어야 지나갈 수 있다. 게이트 앞에서 멈춘 런은 아무도 보지 않으면 그대로 남으므로, 승인의 지연은 절차의 지연이 된다.

Board는 이미 사람이 여는 화면이다. 사람만 풀 수 있는 것을 사람이 이미 보고 있는 곳에 두는 것이 이 요구의 전부다.

## 요구사항

- Board는 사람을 기다리는 런을 태스크와 분리된 면에서 보여 주어야 한다.
- Board는 화면에서 고른 활성 human Client 자격으로 사람 게이트를 승인할 수 있어야 한다.
- 승인 화면은 무엇을 승인하는지를 함께 보여야 한다 — 런의 목표, 대상 문서의 본문, 지나온 스텝.
- 승인은 무엇을 보고 승인했는지를 사유로 남겨야 한다.
- 조회는 런 원장을 바꾸지 않아야 한다.

## 사전조건

- Board 서버가 Workspace를 발견한 상태로 실행 중이어야 한다.
- 승인하려면 대상 프로젝트의 활성 멤버를 owner로 갖는 활성 human Client가 등록되어 있어야 한다.

## 동작 규칙

1. 대기 목록의 갈래와 사유는 런 원장의 갈래 판정을 그대로 읽고, Board가 다시 판정하지 않는다. 판정자가 둘이면 화면과 명령줄이 같은 런에 다른 답을 낸다.
2. 목록 조회는 런 원장에 아무것도 append 하지 않는다. 무엇이 주의를 요구하는지 묻는 행위가 상태를 바꾸면 그 물음을 자동으로 반복할 수 없다.
3. 승인 요청은 프로젝트, 런 ID, 승인자 Client ID, 사유를 모두 지녀야 한다. 하나라도 없으면 원장에 닿기 전에 거부한다.
4. 승인자 Client는 활성이고 유형이 human이어야 하며, 그 owner가 대상 프로젝트의 활성 멤버여야 한다. 이 판정은 명령줄 승인과 같은 함수가 내린다.
5. 승인 화면이 승인자로 제시하는 목록은 활성 human Client뿐이다. Board 서버가 자기 기기 Client에서 파생하는 작성자 신원은 승인자가 될 수 없다 — 그 신원은 유형이 human이 아니며, human으로 바꾸면 같은 기기의 실행 명령이 전부 막힌다.
6. Board 서버가 하네스 자식 프로세스로 실행 중이면 승인 요청을 거부한다. 조회는 계속 제공한다.
7. 승인 이외의 런 조작(구동·재개·정지·소유권 이전)은 Board가 제공하지 않는다.
8. 승인 화면이 보여 주는 대상 문서는 런이 시작할 때 지목한 것과 스텝이 만들어 낸 것을 모두 포함한다. 저작 절차는 런 도중에 문서를 만들므로 시작 이벤트만 보면 정작 승인할 문서가 빠진다.
9. 대상 문서를 프로젝트에서 찾지 못하면 그 사실을 말한다. 빈 화면은 "볼 것이 없다"와 "찾지 못했다"를 같아 보이게 한다.
10. 한 런의 내막 조회도 원장을 바꾸지 않는다. 승인하려고 살펴보는 행위와 승인하는 행위의 경계가 여기서 무너지면 안 된다.
11. 승인이 거부된 사유는 화면에 그대로 전달한다. 사람 게이트가 아닌 스텝, 검증이 본 커밋과 다른 HEAD, 비활성 소유권은 각각 다른 문제이므로 하나의 문장으로 뭉개지 않는다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 사람 게이트에서 멈춘 런이 있음 | 런 면 조회 | 런 ID·절차·커서 스텝·사유를 대기 갈래로 표시 |
| 대상 문서가 있는 런 | 승인 화면 열기 | 목표·지나온 스텝·대상 문서 본문을 문서 화면과 같은 방식으로 표시 |
| 대상 문서를 찾지 못함 | 승인 화면 열기 | 찾지 못했다는 사실을 표시하고 승인은 계속 가능 |
| 대상 문서가 없는 런 | 승인 화면 열기 | 목표와 스텝 이력만 표시 |
| 사람을 기다리는 런이 없음 | 런 면 조회 | 빈 상태를 표시하고 원장은 불변 |
| 활성 human Client와 사유가 갖춰짐 | 승인 요청 | run.forced(basis: human-approval) 기록, 커서 전진 |
| 승인자 Client가 human이 아님 | 승인 요청 | 거부, 상태 불변 |
| 승인자 owner가 프로젝트 활성 멤버가 아님 | 승인 요청 | 거부, 상태 불변 |
| 사유가 비어 있음 | 승인 요청 | 거부, 상태 불변 |
| 커서 스텝이 사람 게이트가 아님 | 승인 요청 | 거부, 상태 불변 |
| 검증이 본 커밋과 현재 HEAD가 다름 | 승인 요청 | 거부, 상태 불변 |
| 보드가 하네스 자식으로 실행 중 | 승인 요청 | 거부, 상태 불변 |
| 세션 토큰 불일치 | 승인 요청 | 403, 상태 불변 |

## 수용 기준

- [ ] 사람 게이트에서 멈춘 런이 Board의 런 면에 대기 갈래로 나타난다.
- [ ] 승인 화면이 런의 목표·지나온 스텝·대상 문서 본문을 보여 준다.
- [ ] 활성 human Client와 사유로 승인하면 원장에 사람 승인이 기록되고 커서가 전진한다.
- [ ] human이 아닌 Client로 승인을 시도하면 거부되고 원장이 변하지 않는다.
- [ ] 사유 없이 승인을 시도하면 거부되고 원장이 변하지 않는다.
- [ ] 런 면을 여러 번 조회해도 런 원장 이벤트 수가 변하지 않는다.
- [ ] 하네스 자식으로 실행한 Board는 조회는 제공하고 승인은 거부한다.

## 기능별 설계 계약

### FN-001

#### 입력

- 목록 조회: 프로젝트 key.
- 내막 조회: 프로젝트 key, 런 ID.
- 승인: 프로젝트 key, 런 ID, 승인자 Client ID, 사유, 세션 토큰. 스텝 ID는 선택이며 생략하면 현재 커서 스텝을 뜻한다.

#### 출력

- 내막 조회: 런의 상태·목표·태스크·절차·커서 스텝·지나온 스텝·대상 문서 ID 목록·사건 이력·승인 가능 자격.
- 목록 조회: 대기·구동 가능·구동 중 갈래별 런 목록. 각 항목은 런 ID, 절차 이름, 커서 스텝, 사유를 지닌다. 읽지 못한 런은 별도 목록으로 함께 낸다 — 하나의 손상이 나머지를 감추지 않아야 한다.
- 승인: 기록된 런 ID, 스텝 ID, 승인자 Client ID, 커밋, 사유.
- 승인 화면이 쓸 수 있는 활성 human Client 목록.

#### 업무 규칙

- 갈래 판정과 승인 판정은 모두 런 도메인 함수가 내린다. Board는 인자를 옮기고 결과를 그린다.
- 조회는 읽기만 하며 reconcile을 수행하지 않는다.
- 승인은 현재 커서 스텝에만 적용된다.

#### 상태와 전이

- 대기(사람 게이트) → 승인 기록 → 실행 중(다음 스텝) 또는 완료.
- 거부된 승인은 어떤 전이도 만들지 않는다.

#### 권한과 승인

- 승인자는 활성 human Client여야 하고 그 owner가 대상 프로젝트의 활성 멤버여야 한다.
- Board의 기기 작성자 신원은 승인자가 될 수 없다.
- 하네스 자식으로 실행 중인 Board 서버는 승인을 수행하지 않는다.

#### 정상·오류·취소

- 정상: 사람 승인이 원장에 기록되고 목록에서 그 런이 대기 갈래를 벗어난다.
- 오류: 자격·사유·스텝·커밋·소유권 위반은 각각의 사유를 그대로 전달하고 상태를 바꾸지 않는다.
- 취소: 승인 화면을 닫는 것은 아무것도 기록하지 않는다.

#### 감사 기록

- 승인은 런 원장에 사람 승인 근거를 지닌 사건으로 남는다. Board는 별도의 승인 기록을 만들지 않는다 — 표면마다 기록이 따로 생기면 "사람이 승인했는가"에 답하는 곳이 둘이 된다.

#### 수용 기준

- 사람 게이트에서 멈춘 런이 대기 갈래로 조회된다.
- 활성 human Client와 사유를 갖춘 승인이 원장에 기록되고 커서가 전진한다.
- 자격·사유·스텝·커밋·소유권 위반은 각각 거부되고 원장이 변하지 않는다.
