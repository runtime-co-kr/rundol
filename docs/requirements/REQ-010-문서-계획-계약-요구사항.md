# 문서 계획 계약 요구사항

## 배경

기존 `documentProfile`은 문서 유형의 활성 상태만 분류해, AI와 사용자가 어떤 문맥을 참고하고 생략된 내용은 어디에 남겨야 하는지 일관되게 알 수 없었다. Rundol은 별도 범용 지식 그래프나 강제 순서 엔진을 도입하지 않고 `project.md`의 작은 계약과 공용 evaluator로 이 문제를 해결한다.

이 문서는 계약 영역의 배경과 초기 계약 생성 기능을 나른다. 평가는 [[REQ-026-문서-계약-평가|REQ-026]], 프리셋 상속 해석은 [[REQ-027-프로필-프리셋-상속-해석|REQ-027]], 강제 수준 적용은 [[REQ-028-계약-강제-수준-적용|REQ-028]], revision 변경은 [[REQ-029-계약-revision-변경|REQ-029]]이 각각 기능 하나씩 나른다 — 문서 1개 = 기능 1개 계약에 따른 분리다.

## 요구사항

- 새 프로젝트는 schemaVersion 2 문서 계약을 항상 가진다.
- 계약은 정책 상태, 강제 수준과 revision을 표현한다. 그 밖의 것은 계약에 저장하지 않는다.
- 프로필 프리셋과 유형별 하부 요소는 `board.json` 상속이 정하며 프로젝트 계약이 들고 다니지 않는다.
- CLI, 스킬과 Board는 같은 evaluator 결과를 사용한다.
- 계약 변경은 기존 문서를 삭제하거나 이동하지 않고 영향과 revision을 반환한다.
- checkpoint 위반은 저장과 동기화를 차단하되 초기 bootstrap과 일반 태스크 생성은 막지 않는다.

## 사전조건

- Workspace와 대상 프로젝트가 정상적으로 연결돼 있어야 한다.
- `project.md`가 유효한 Rundol 프로젝트 charter여야 한다.
- 정규 문서 유형은 PRD, REQ, ARC, SCR, MOD, API, ADR, TST, RUN, GLS로 한정한다.

## 동작 규칙

1. 모든 유형은 required, recommended, onDemand, disabled 중 정확히 하나에 속한다.
1-1. 네 상태는 서로 다른 동작을 가진다. required는 없으면 위반, recommended는 없으면 경고, onDemand는 있든 없든 진단하지 않으며, disabled는 그 유형을 만들지 않겠다는 결정이라 `rdl doc create`가 거부하고 이미 존재하면 위반이다.
2. 유형별 하부 요소는 프로필 프리셋이 갖고 계약은 저장하지 않는다. `board.json`의 `profiles.<name>.sections.<TYPE>`이 유형 단위로 기본값을 대체하며, 지정하지 않은 유형은 내장 기본값을 그대로 쓴다.
2-1. 하부 요소는 작성 구조이지 검사 대상이 아니다. 제목 문자열의 존재만 볼 수 있는 검사는 내용 없는 제목을 통과시키고 제목 없이 충실히 쓴 문서를 실패로 만들므로, 어느 쪽도 보증하지 못한다.
3. disabled 유형에 대해 계약은 아무 부가 설정도 갖지 않는다. 흡수 대상이나 필수 구성요소를 요구하지 않는다.
3-1. 어떤 유형이 필요해지면 계약에서 그 유형의 상태를 먼저 바꾼다. 내용을 다른 유형 문서 안에 담아 대신하지 않는다.
4. `rdl contract next`는 모든 미작성 활성 유형을 ready로 반환하고 작성 순서 참고값을 함께 표시하며, blocked는 호환성을 위해 빈 배열로 유지한다. 이 참고값은 내장 상수에서 계산하며 계약에 저장하지 않는다.
5. `rdl doc create`는 invalid 계약과 disabled 유형만 파일 생성 전에 거부한다.
6. advisory 위반은 경고로, checkpoint 위반은 strict/save/sync 차단 오류로 처리한다. recommended 누락은 강제 수준과 무관하게 경고다.
7. Board 변경 API는 baseRevision을 요구하고 stale revision에 HTTP 409를 반환한다.
8. schemaVersion 1은 손실 없이 읽고 명시적 재설정 시 schemaVersion 2로 마이그레이션한다.

## 사용자 흐름

1. 사용자는 `rdl init` 또는 `rdl contract show`로 현재 계약 상태를 확인한다.
2. `rdl contract next`가 제시한 ready 문서와 작성 순서 참고값을 보되 프로젝트 진행에 필요한 문서부터 생성한다.
3. 문서를 만들면 그 유형의 하부 요소를 채운다. `rdl doc create`가 프리셋의 목록으로 뼈대를 만든다.
4. `rdl contract check`와 `rdl check --strict`로 계약과 산출물을 검증한다.
5. 필요하면 `rdl contract plan` 또는 Board Settings에서 영향을 확인한 뒤 계약을 변경한다.

## 화면 상태

Board Settings는 현재 profile, enforcement, revision, 유형별 policy 상태와 프리셋이 정한 하부 요소를 표시한다. 프로필을 고르면 아래 정책 상태를 그 프리셋 값으로 즉시 다시 칠하되 저장은 계약 저장 버튼이 한다. 사용자가 행을 직접 바꿔 어느 프리셋과도 달라지면 그 사실을 알리고 이름을 붙여 프리셋으로 저장할 길을 연다. 정상·위반·stale revision 상태를 구분하며 저장 성공 후 최신 snapshot을 다시 읽는다.

## 입력과 검증

| 입력 | 허용 값 | 검증과 거절 |
|---|---|---|
| profile | `board.json` 상속이 해석한 프리셋 이름 | 내장 5종과 팀이 정의한 프리셋을 모두 받는다. 목록 밖 이름은 거절한다. 프로파일을 바꾸면서 policy를 보내지 않으면 policy를 새 프로파일 기본값으로 다시 세운다. |
| enforcement | `advisory`·`checkpoint` | 목록 밖 값은 `checkpoint`로 되돌린다. |
| policy | 정규 유형 10종이 `required`·`recommended`·`onDemand`·`disabled` 중 정확히 한 곳에 | 빠지거나 겹친 유형은 프로파일 기본 상태로 채운다. policy를 보내면 프로파일 기본값보다 우선하므로, 화면에서 저장할 때 프로필은 출발점이지 결정자가 아니다. |
| baseRevision | 현재 계약 revision과 일치 | 없거나 어긋나면 HTTP 409와 현재 계약을 돌려주고 아무것도 쓰지 않는다. |

프리셋 자체(`profiles.<name>`의 라벨·정책·하부 요소)는 계약이 아니라 `board.json`이 검증한다. 프로필 이름은 저장값이므로 영문 소문자·숫자·하이픈만 허용하고, 내장에 없는 이름은 `policy`를 반드시 함께 요구한다. 정책 없는 커스텀 프로필은 조용히 기본 프로파일로 되돌아가 사용자가 만든 적 없는 계약이 저장되기 때문이다.

계약 저장은 전부 적용되거나 전부 적용되지 않는다. 검증에 걸린 입력이 하나라도 있으면 revision을 올리지 않는다.

## 접근성

계약 편집 필드는 label과 의미 있는 컨트롤 이름을 제공하고 키보드로 조작할 수 있어야 한다. 상태와 오류는 색상만으로 전달하지 않으며 기존 `aria-live` 메시지 영역으로 결과를 알린다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| legacy-unconfigured | show/check | 마이그레이션 필요 상태를 반환하고 기존 프로젝트를 자동 변경하지 않는다. |
| migration-required | profile 재설정 | v1 정책과 traits를 보존해 v2로 전환한다. |
| invalid 또는 unsupported-schema | 문서 생성 | 생성 전에 거부하고 수정 명령을 안내한다. |
| checkpoint 위반 | save 또는 sync | push 전에 실패한다. |
| advisory 위반 | check 또는 save | 경고를 반환하고 작업은 계속한다. |
| stale baseRevision | Board 계약 저장 | HTTP 409와 현재 계약을 반환한다. |

## 수용 기준

- [x] v2 스키마가 policy, enforcement, revision을 정규화하고 직렬화하며 그 밖의 것은 저장하지 않는다.
- [x] CLI의 init/project/doc/check/save/sync가 공용 evaluator를 사용한다.
- [x] Board snapshot/API/UI가 계약 조회·영향 검토·revision 기반 변경을 제공한다.
- [x] Rundol 스킬이 show → next → create → check 흐름을 안내하되 작성 순서 참고값 누락을 차단하지 않는다.
- [x] 팀이 `board.json`에 정의한 프리셋을 CLI와 Board가 같은 목록으로 제공하고 그 이름이 계약에 저장된다.
- [x] 프리셋이 정하지 않은 유형의 하부 요소는 내장 기본값을 그대로 쓴다.
- [x] 프로필을 고르면 정책 상태가 즉시 그 프리셋으로 바뀌고, 직접 바꾸면 커스텀임을 알린다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 결정성 | 같은 계약과 문서 집합은 같은 평가 JSON을 만든다. | 단위 테스트 deep equality |
| 호환성 | v1 계약과 미설정 프로젝트를 읽을 수 있다. | migration/legacy 회귀 테스트 |
| 안전성 | 계약 재설정은 기존 문서를 삭제하지 않는다. | 영향 검토 및 파일 존재 테스트 |
| 일관성 | CLI와 Board가 같은 revision·위반을 반환한다. | Board HTTP 통합 테스트 |

## 제외 범위

- 범용 지식 그래프, 시각적 그래프 편집기, 자동 문서 본문 생성
- 모든 프로젝트 단계와 조직 프로세스를 모델링하는 별도 workflow 엔진
- 계약 변경 시 기존 문서의 자동 삭제·이동·병합

## 기능별 설계 계약

### FN-001

#### 입력

- 새 프로젝트의 profile, traits와 선택적 정책 override

#### 출력

- schemaVersion 2, revision 1의 완전한 `documentProfile`

#### 업무 규칙

- 모든 정규 문서 유형을 정책 상태 하나에 정확히 배치한다. 그 밖의 부가 설정은 채우지 않는다.

#### 상태와 전이

- 미설정 상태에서 생성되면 `valid`가 되며 기존 유효 계약은 init 재실행으로 변경하지 않는다.

#### 권한과 승인

- CLI bootstrap 서비스만 초기 계약을 쓰며 프로젝트 책임자가 profile 선택을 승인한다.

#### 정상·오류·취소

- 유효 입력은 계약을 생성하고 알 수 없는 profile·trait·중복 정책은 파일을 쓰기 전에 거부한다.

#### 감사 기록

- 선택한 profile과 최초 revision은 project.md와 Git 커밋에 남는다.

#### 수용 기준

- 새 프로젝트는 미설정 상태 없이 동일 입력에 결정적인 schemaVersion 2 계약을 가진다.
