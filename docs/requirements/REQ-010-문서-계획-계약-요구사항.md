# 문서 계획 계약 요구사항

## 배경

기존 `documentProfile`은 문서 유형의 활성 상태만 분류해, AI와 사용자가 어떤 문맥을 참고하고 생략된 내용은 어디에 남겨야 하는지 일관되게 알 수 없었다. Rundol은 별도 범용 지식 그래프나 강제 순서 엔진을 도입하지 않고 `project.md`의 작은 계약과 공용 evaluator로 이 문제를 해결한다.

## 요구사항

- 새 프로젝트는 schemaVersion 2 문서 계약을 항상 가진다.
- 계약은 정책 상태, AI 추천 문맥, 생략 처리, 강제 수준과 revision을 표현한다.
- CLI, 스킬과 Board는 같은 evaluator 결과를 사용한다.
- 계약 변경은 기존 문서를 삭제하거나 이동하지 않고 영향과 revision을 반환한다.
- checkpoint 위반은 저장과 동기화를 차단하되 초기 bootstrap과 일반 태스크 생성은 막지 않는다.

## 사전조건

- Workspace와 대상 프로젝트가 정상적으로 연결돼 있어야 한다.
- `project.md`가 유효한 Rundol 프로젝트 charter여야 한다.
- 정규 문서 유형은 PRD, REQ, ARC, SCR, MOD, API, ADR, TST, RUN, GLS로 한정한다.

## 동작 규칙

1. 모든 유형은 required, recommended, onDemand, disabled 중 정확히 하나에 속한다.
2. `rules.<TYPE>.after`는 AI가 작성 품질을 높이기 위해 참고하면 좋은 문서 유형을 나타내며 생성·저장·동기화를 차단하지 않는다.
3. disabled 유형은 흡수 대상과 필수 구성요소 또는 적용 제외 사유를 가져야 한다.
3-1. 흡수 충족은 유형 단위로 판정한다. 대상 유형의 문서 하나가 모든 필수 구성요소를 가지면 그 유형의 생략은 충족이다.
3-2. 흡수 대상 유형의 문서별 구성요소 보유 현황을 함께 계산한다. 모두 보유, 일부만 보유, 전혀 없음 세 가지로 구분한다.
3-3. 필수 구성요소를 일부만 가진 문서는 진단한다. 그 주제를 다루기 시작했는데 계약이 요구한 나머지를 빠뜨린 상태이므로 기계적으로 미완성이라고 단정할 수 있다.
3-4. 구성요소를 전혀 갖지 않은 문서는 진단하지 않는다. 그 문서가 해당 주제를 다루지 않을 수 있어 기계가 필요 여부를 판정할 수 없다.
3-5. 일부 보유 진단은 경고이며 강제 수준과 무관하게 저장·동기화를 차단하지 않는다. 작성 중인 문서를 막지 않기 위해서다.
4. `rdl contract next`는 모든 미작성 활성 유형을 ready로 반환하고 추천 문맥 및 누락 추천 문맥을 함께 표시하며, blocked는 호환성을 위해 빈 배열로 유지한다.
5. `rdl doc create`는 invalid 계약과 disabled 유형만 파일 생성 전에 거부한다.
6. advisory 위반은 경고로, checkpoint 위반은 strict/save/sync 차단 오류로 처리한다. recommended 누락은 강제 수준과 무관하게 경고다.
7. Board 변경 API는 baseRevision을 요구하고 stale revision에 HTTP 409를 반환한다.
8. schemaVersion 1은 손실 없이 읽고 명시적 재설정 시 schemaVersion 2로 마이그레이션한다.

## 사용자 흐름

1. 사용자는 `rdl init` 또는 `rdl contract show`로 현재 계약 상태를 확인한다.
2. `rdl contract next`가 제시한 ready 문서와 추천 문맥을 참고하되 프로젝트 진행에 필요한 문서부터 생성한다.
3. disabled 문서의 내용은 evaluator가 지정한 대상 문서와 필수 구성요소에 작성한다.
4. `rdl contract check`와 `rdl check --strict`로 계약과 산출물을 검증한다.
5. 필요하면 `rdl contract plan` 또는 Board Settings에서 영향을 확인한 뒤 계약을 변경한다.

## 화면 상태

Board Settings는 현재 profile, enforcement, revision, 유형별 policy 상태, 읽기 전용 AI 추천 문맥, omission 대상과 필수 구성요소를 표시한다. 정상·위반·stale revision 상태를 구분하며 저장 성공 후 최신 snapshot을 다시 읽는다.

## 접근성

계약 편집 필드는 label과 의미 있는 컨트롤 이름을 제공하고 키보드로 조작할 수 있어야 한다. 상태와 오류는 색상만으로 전달하지 않으며 기존 `aria-live` 메시지 영역으로 결과를 알린다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| legacy-unconfigured | show/check | 마이그레이션 필요 상태를 반환하고 기존 프로젝트를 자동 변경하지 않는다. |
| migration-required | profile 재설정 | v1 정책과 traits를 보존해 v2로 전환한다. |
| invalid 또는 unsupported-schema | 문서 생성 | 생성 전에 거부하고 수정 명령을 안내한다. |
| checkpoint 위반 | save 또는 sync | push 전에 실패한다. |
| advisory 위반 | check 또는 save | 경고를 반환하고 작업은 계속한다. |
| stale baseRevision | Board 계약 저장 | HTTP 409와 현재 계약을 반환한다. |

## 수용 기준

- [x] v2 스키마가 policy, rules, omissions, enforcement, revision을 정규화하고 직렬화한다.
- [x] CLI의 init/project/doc/check/save/sync가 공용 evaluator를 사용한다.
- [x] Board snapshot/API/UI가 계약 조회·영향 검토·revision 기반 변경을 제공한다.
- [x] Rundol 스킬이 show → next → create/absorb → check 흐름을 안내하되 추천 문맥 누락을 차단하지 않는다.
- [x] Rundol 자체 프로젝트에서 PRD 다음 REQ를 생성하고 SCR 내용을 이 문서의 지정 섹션으로 흡수했다.
- [ ] 흡수 대상 유형의 문서별 구성요소 보유 현황을 모두 보유·일부만 보유·전혀 없음으로 계산한다.
- [ ] 구성요소를 일부만 가진 문서를 경고로 진단하고, 전혀 없는 문서는 진단하지 않는다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 결정성 | 같은 계약과 문서 집합은 같은 평가 JSON을 만든다. | 단위 테스트 deep equality |
| 호환성 | v1 계약과 미설정 프로젝트를 읽을 수 있다. | migration/legacy 회귀 테스트 |
| 안전성 | 계약 재설정은 기존 문서를 삭제하지 않는다. | 영향 검토 및 파일 존재 테스트 |
| 일관성 | CLI와 Board가 같은 revision·위반을 반환한다. | Board HTTP 통합 테스트 |

## 제외 범위

- 범용 지식 그래프, 시각적 그래프 편집기, 자동 문서 본문 생성
- 모든 프로젝트 단계와 조직 프로세스를 모델링하는 별도 workflow 엔진
- 계약 변경 시 기존 문서의 자동 삭제·이동·병합

## 기능별 설계 계약

### DCP-01

#### 입력

- 새 프로젝트의 profile, traits와 선택적 정책 override

#### 출력

- schemaVersion 2, revision 1의 완전한 `documentProfile`

#### 업무 규칙

- 모든 정규 문서 유형을 정책 상태 하나에 정확히 배치하고 모든 rules와 omissions 기본값을 채운다.

#### 상태와 전이

- 미설정 상태에서 생성되면 `valid`가 되며 기존 유효 계약은 init 재실행으로 변경하지 않는다.

#### 권한과 승인

- CLI bootstrap 서비스만 초기 계약을 쓰며 프로젝트 책임자가 profile 선택을 승인한다.

#### 정상·오류·취소

- 유효 입력은 계약을 생성하고 알 수 없는 profile·trait·중복 정책은 파일을 쓰기 전에 거부한다.

#### 감사 기록

- 선택한 profile과 최초 revision은 project.md와 Git 커밋에 남는다.

#### 수용 기준

- 새 프로젝트는 미설정 상태 없이 동일 입력에 결정적인 schemaVersion 2 계약을 가진다.

### DCP-02

#### 입력

- 현재 documentProfile과 프로젝트의 정규 문서 집합

#### 출력

- present, ready, 추천 문맥, omission 상태와 violations를 포함한 평가 JSON

#### 업무 규칙

- `after`는 추천 문맥이며 blocked 선행조건으로 변환하지 않고 같은 입력에는 같은 결과를 반환한다.

#### 상태와 전이

- 문서가 생성되면 present와 ready만 다시 계산하며 계약 revision은 바꾸지 않는다.

#### 권한과 승인

- CLI, 스킬과 Board는 공용 evaluator 결과만 사용하고 별도 판단 규칙을 만들지 않는다.

#### 정상·오류·취소

- 유효 계약은 평가하고 unsupported schema는 오류와 지원 범위를 반환하며 파일은 바꾸지 않는다.

#### 감사 기록

- 평가는 읽기 전용이며 변경 감사는 입력 문서와 계약의 Git 이력으로 추적한다.

#### 수용 기준

- CLI contract 결과와 Board snapshot의 revision·violations가 동일하다.

### DCP-03

#### 입력

- disabled 문서 유형과 `absorbedBy`, sections 또는 notApplicable 사유

#### 출력

- 생략 처리 충족 여부와 누락 대상·섹션 진단

#### 업무 규칙

- 생략은 자동 삭제가 아니며 설정된 대상 문서가 모든 필수 구성요소를 실제 제목으로 포함해야 한다.

#### 상태와 전이

- disabled에서 활성 상태로 바뀌면 omission 편집값은 저장 payload에서 제거된다.

#### 권한과 승인

- 프로젝트 책임자가 omission 변경을 승인하고 Board와 CLI는 같은 revision 충돌 규칙을 적용한다.

#### 정상·오류·취소

- 유효한 흡수 또는 적용 제외는 통과하고 대상 없음·빈 사유·누락 섹션은 진단한다.

#### 감사 기록

- omission 변경은 revision과 history에 기록되고 기존 문서 이동·삭제는 발생하지 않는다.

#### 수용 기준

- SCR 비활성 계약은 REQ의 사용자 흐름·화면 상태·입력과 검증·접근성 섹션으로 충족된다.

### DCP-04

#### 입력

- enforcement 값과 evaluator violations

#### 출력

- advisory 경고 또는 checkpoint 차단 결과

#### 업무 규칙

- recommended 누락은 항상 경고이며 required·disabled·omission 위반만 checkpoint 저장·동기화를 차단한다.

#### 상태와 전이

- 위반이 해소되면 별도 승인 없이 다음 검사에서 차단 상태가 해제된다.

#### 권한과 승인

- enforcement 변경은 계약 revision 기반 명시적 변경으로만 허용한다.

#### 정상·오류·취소

- bootstrap과 일반 태스크 생성은 허용하고 save·sync는 push 전에 실패해 원격을 변경하지 않는다.

#### 감사 기록

- enforcement와 위반 진단 코드는 계약·명령 결과와 Git 이력에 남는다.

#### 수용 기준

- checkpoint 위반 상태의 save와 sync는 커밋·push 전에 실패하고 advisory는 경고로 계속한다.

### DCP-05

#### 입력

- 현재 baseRevision과 변경할 profile, enforcement, policy, rules, omissions

#### 출력

- 증가한 revision, 변경 impact와 최신 평가 결과

#### 업무 규칙

- 변경은 기존 파일을 삭제·이동·병합하지 않으며 history를 전진시킨다.

#### 상태와 전이

- baseRevision 일치 시 revision이 1 증가하고 stale revision이면 현재 계약을 반환한다.

#### 권한과 승인

- CLI contract set 또는 token이 유효한 Board 요청만 계약을 변경한다.

#### 정상·오류·취소

- 유효 변경은 원자적으로 저장하고 stale·invalid 입력은 HTTP 409 또는 CLI 오류로 원본을 보존한다.

#### 감사 기록

- 이전 profile 이름과 새 revision이 history와 프로젝트 브랜치 커밋에 남는다.

#### 수용 기준

- 동시 변경은 조용히 덮어쓰지 않고 한 요청만 성공하며 나머지는 최신 revision을 받는다.
