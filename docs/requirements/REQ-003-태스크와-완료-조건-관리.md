# 태스크와 완료 조건 관리

## 배경

태스크가 제목과 상태만 가지면 왜 필요한 작업인지, 누가 책임지는지, 무엇을 확인해야 완료인지 판단할 수 없다. 상태를 임의로 `done`으로 바꾸거나 존재하지 않는 담당자·문서·선행 태스크를 참조하면 보드의 진행률과 프로젝트 완료 판단을 신뢰할 수 없다.

런돌의 태스크는 프로젝트 헌장에 등록된 사람, 실제 요구사항·설계·테스트 문서, 명시적인 수용조건과 외부 검토 증거를 연결해야 한다. 여러 Client가 동시에 태스크를 만들 때는 Git 충돌을 줄이면서도 전체 태스크를 하나의 논리적 목록으로 검증하고 탐색할 수 있어야 한다.

## 요구사항

- REQ-003-FR-01: 사용자는 제목, 요약, 하나 이상의 완료 조건과 선택적 담당자·검토자·이해관계자·우선순위·문서 링크를 가진 태스크를 생성할 수 있어야 한다.
- REQ-003-FR-02: 시스템은 프로젝트와 무관하게 충돌 가능성이 낮은 전역 고유 태스크 ID를 발급해야 한다.
- REQ-003-FR-03: 사용자는 허용된 상태 사이에서 태스크 상태를 변경하고 담당자를 배정하거나 해제할 수 있어야 한다.
- REQ-003-FR-04: 사용자는 개별 완료 조건의 완료 여부를 독립적으로 변경할 수 있어야 한다.
- REQ-003-FR-05: 시스템은 상태별 담당자, blocker, 검토 증거, 완료 조건과 테스트 문서 규칙을 검증해야 한다.
- REQ-003-FR-06: 시스템은 담당자·검토자·이해관계자, 관련 문서와 선행 태스크가 실제 프로젝트 정본에 존재하는지 검증해야 한다.
- REQ-003-FR-07: 여러 Client가 생성한 태스크 샤드를 하나의 논리적 태스크 목록으로 읽고 검색·필터·집계할 수 있어야 한다.
- REQ-003-FR-08: 기존 단일 태스크 저장소를 데이터 손실 없이 Client별 segment 저장소로 명시적으로 마이그레이션할 수 있어야 한다.
- REQ-003-FR-09: 모든 태스크 변경은 검증 후 operation 기록과 Git commit으로 추적할 수 있어야 한다.

## 사전조건

- 대상 프로젝트가 Workspace Registry에 등록되고 프로젝트 ref와 worktree가 연결되어 있어야 한다.
- 태스크 owner와 reviewers는 `project.md`의 `MEMBER-*`, stakeholders는 `STAKEHOLDER-*`에 등록되어 있어야 한다.
- 관련 문서 링크는 프로젝트에 존재하는 정규 문서 ID 또는 실제 section을 가리켜야 한다.
- 태스크 생성 시 비어 있지 않은 제목과 하나 이상의 관찰 가능한 완료 조건을 제공해야 한다.
- 태스크 상태 변경 대상과 완료 조건 ID가 현재 프로젝트 태스크 저장소에 존재해야 한다.
- 분할 저장을 사용하는 Client는 유효한 Client ID를 가지며 로컬 기본값은 프로젝트의 Git 비추적 런타임 상태에 보관되어야 한다.

## 동작 규칙

1. 태스크 ID는 `TASK-` 접두어를 가진 전역 고유 식별자이며 Client ID나 저장 segment 번호에 종속되지 않는다.
2. 신규 태스크의 초기 상태는 `todo`, 기본 우선순위는 `mid`, blocker는 `null`이어야 한다.
3. 허용 상태는 `todo`, `doing`, `waiting`, `review`, `done`으로 제한한다.
4. 우선순위는 `high`, `mid`, `low` 중 하나를 사용한다.
5. 모든 태스크는 `title`, `summary`, `owner`, `reviewers`, `stakeholders`, `status`, `priority`, `links`, `deps`, `acceptanceCriteria`, `blocker`, `createdAt`, `updatedAt`, `statusChangedAt`, `externalRefs`를 유지해야 한다.
6. `doing`, `review`, `done` 상태에는 등록된 owner가 필요하다. `todo`와 `waiting`에서는 owner가 없을 수 있다.
7. `waiting` 상태에는 `waitingFor`, `condition`, `since`가 있는 blocker가 필요하고, waitingFor는 등록된 멤버 또는 이해관계자여야 한다.
8. `waiting`이 아닌 태스크에는 blocker를 둘 수 없다.
9. `review` 상태에는 Pull Request, Merge Request 또는 검토 대상을 식별하는 externalRef가 하나 이상 필요하다.
10. `done` 상태에는 모든 acceptance criterion이 완료되어야 하며 최소 하나의 TST 문서를 링크해야 한다.
11. 모든 상태에서 acceptance criterion은 하나 이상 유지해야 하며 각 조건은 고유한 `AC-*` ID와 완료 여부를 가져야 한다.
12. links는 존재하는 문서 또는 section을, deps는 존재하는 태스크를 가리켜야 하며 태스크 의존성 순환을 허용하지 않는다.
13. 직접 수정 명령이 변경할 수 있는 태스크 필드는 현재 `status`와 `owner`로 제한한다. 완료 조건은 전용 acceptance 명령으로 변경한다.
14. 동일한 상태·owner·완료 여부를 다시 설정하면 파일과 commit을 변경하지 않는다.
15. 태스크 생성과 유효한 변경은 대상 샤드에 원자적으로 기록하고 operation을 `.rundol/state/pending/OP-*.json`에 남긴 뒤 프로젝트 ref에 즉시 커밋한다.
16. 신규 schema는 `tasks/<client-id>/<6자리 segment>.json`을 사용하며 segment당 기본 최대 500개 태스크를 저장한다.
17. 서로 다른 Client가 만든 태스크는 각 Client의 샤드에 기록하고, 기존 태스크 수정은 그 태스크가 존재하는 원본 샤드에서 수행한다.
18. 여러 샤드에서 같은 태스크 ID가 발견되면 중복 오류로 처리하고 임의의 한 항목을 선택하지 않는다.
19. `.rundol/state/tasks.json`은 조회 호환용 projection이며 정본으로 커밋하지 않고 언제든 샤드에서 재생성할 수 있어야 한다.
20. 단일 `tasks.json` 마이그레이션은 대상 샤드 경로가 비어 있을 때만 수행하고 기존 원본을 자동 삭제하지 않는다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 유효한 입력과 완료 조건 제공 | `rdl task add` | `todo` 태스크를 생성하고 샤드·operation·commit을 기록한다. |
| 완료 조건 없음 | task add | 태스크와 commit을 만들지 않고 입력 오류를 반환한다. |
| 등록되지 않은 owner·reviewer·stakeholder | 생성·검사 | 대상 ID를 포함한 책임 참조 오류를 반환한다. |
| `todo` 태스크 | status를 `doing`으로 변경 | 등록된 owner가 있으면 변경하고, 없으면 검증 오류로 원본을 보존한다. |
| 임의 상태의 태스크 | status를 `waiting`으로 변경 | 완전한 blocker가 함께 존재할 때만 유효하다. 현재 단순 status 명령으로 충족할 수 없으면 변경을 거부한다. |
| `waiting` 태스크 | 다른 상태로 변경 | blocker가 제거된 유효한 변경만 허용한다. |
| 구현 완료 태스크 | status를 `review`로 변경 | externalRef가 있으면 변경하고, 없으면 검증 오류를 반환한다. |
| 모든 완료 조건 완료 및 TST 링크 있음 | status를 `done`으로 변경 | 완료 상태와 상태 변경 시각을 기록하고 commit한다. |
| 미완료 조건 또는 TST 링크 없음 | status를 `done`으로 변경 | 변경을 거부하고 기존 상태와 파일을 보존한다. |
| 존재하는 완료 조건 | acceptance done·undone | 해당 조건의 boolean 값만 변경하고 updatedAt을 갱신한다. |
| 존재하지 않는 태스크·완료 조건 | 변경 요청 | 어떤 파일도 변경하지 않고 대상 식별자를 포함한 오류를 반환한다. |
| 기존 값과 같은 변경 | task set·acceptance | 새 operation과 commit을 만들지 않는다. |
| 존재하지 않는 문서·section 링크 | 검사·변경 저장 | 깨진 근거 링크 오류를 반환한다. |
| 존재하지 않는 선행 태스크 | 검사 | 누락된 dependency를 포함한 오류를 반환한다. |
| 의존성 순환 존재 | 검사 | 순환 경로를 포함한 오류를 반환한다. |
| 현재 Client segment가 500개 미만 | 태스크 생성 | 같은 마지막 segment에 추가한다. |
| 현재 Client segment가 500개 | 태스크 생성 | 다음 6자리 segment 파일을 만들어 기록한다. |
| 같은 ID가 여러 샤드에 존재 | 전체 읽기·검사 | 중복 오류를 반환하고 projection을 신뢰 가능한 상태로 만들지 않는다. |
| 기존 단일 저장소 존재, 샤드 비어 있음 | task migrate | 지정 Client와 최대 크기에 따라 분할하고 건수·샤드 수를 반환한다. |
| 대상 샤드에 기존 태스크 있음 | task migrate | 기존 샤드를 덮어쓰지 않고 중단한다. |

## 수용 기준

- [ ] task add가 제목·요약·책임 주체·우선순위·문서 링크·복수 완료 조건을 정본에 보존한다.
- [ ] 신규 태스크가 `todo`, 기본 `mid` 우선순위, null blocker와 고유 TASK ID를 가진다.
- [ ] 완료 조건 없는 태스크와 등록되지 않은 owner·reviewer·stakeholder를 생성할 수 없다.
- [ ] 존재하지 않는 문서·section과 선행 태스크 링크가 strict 검사에서 탐지된다.
- [ ] 의존성 순환 fixture에서 오류가 순환 태스크 경로를 제공한다.
- [ ] `doing`, `review`, `done`에 owner가 없으면 상태 변경과 save가 실패한다.
- [ ] `waiting`의 blocker 필드 누락과 waiting 이외 상태의 blocker 존재가 각각 오류로 탐지된다.
- [ ] externalRef 없는 `review`와 미완료 조건 또는 TST 링크가 없는 `done`이 거부된다.
- [ ] 모든 완료 조건과 TST 링크가 있는 태스크만 `done`으로 저장된다.
- [ ] acceptance 명령은 선택한 조건 외 다른 태스크 필드를 변경하지 않는다.
- [ ] 존재하지 않는 태스크·조건과 동일 값 재설정이 새 commit을 만들지 않는다.
- [ ] 유효한 변경마다 updatedAt이 갱신되고 status 변경에서만 statusChangedAt이 갱신된다.
- [ ] 태스크 생성·수정 실패 시 대상 샤드 byte와 프로젝트 HEAD가 이전 상태로 복원된다.
- [ ] 서로 다른 두 Client가 생성한 태스크가 별도 샤드에 기록되고 통합 조회에서 모두 나타난다.
- [ ] 501번째 태스크가 다음 segment에 저장되고 전체 logical count가 유지된다.
- [ ] 여러 샤드의 중복 태스크 ID가 명시적 오류로 탐지된다.
- [ ] 단일 저장소 마이그레이션 전후 태스크 ID와 전체 필드가 동일하고 원본 파일이 자동 삭제되지 않는다.
- [ ] projection을 삭제한 뒤 refresh하면 정본 샤드에서 동일한 목록을 재생성한다.
- [ ] Board의 검색·상태·담당자 필터와 Needs Attention 집계가 같은 logical store 결과를 사용한다.
- [ ] 모든 태스크 명령의 JSON 결과에서 changed, taskId, commit과 projection을 파싱할 수 있다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 무결성 | 상태별 책임·검토·완료 게이트를 통과하지 않은 태스크는 commit되지 않는다. | 각 오류 fixture에서 명령 전후 HEAD와 샤드 hash를 비교한다. |
| 동시성 | 서로 다른 Client의 태스크 생성이 같은 파일을 수정하지 않는다. | 두 Client의 병렬 생성 후 Git diff와 병합 결과를 검사한다. |
| 확장성 | 1만 건 태스크에서 전체 조회·검사가 일반 개발 환경 5초 이내 완료된다. | 20개 이상의 segment fixture에서 20회 측정한 95백분위 값을 사용한다. |
| 결정성 | 샤드 파일 열거 순서와 무관하게 같은 logical store와 진단을 생성한다. | 파일 시스템 열거 순서를 바꾼 반복 테스트 결과를 비교한다. |
| 추적성 | 모든 태스크가 문서 근거, operation과 생성·변경 commit으로 추적된다. | 임의 태스크 ID로 문서 link, OP 기록과 Git log를 역추적한다. |
| 복구성 | projection과 로컬 index 손실이 정본 손실로 이어지지 않는다. | `.rundol/state` 삭제 후 refresh 결과를 기존 logical store와 비교한다. |
| 이식성 | 태스크 JSON이 지원 OS와 표준 Git 도구에서 동일하게 처리된다. | Windows·macOS·Linux의 parse·migrate·merge fixture를 실행한다. |

## 제외 범위

- 문서 유형·메타데이터·Wiki link 자체의 상세 규칙은 문서 거버넌스 요구사항에서 다룬다.
- Workspace와 프로젝트 branch 생성·연결·분리 규칙은 프로젝트 수명주기 요구사항에서 다룬다.
- 원격 동기화와 충돌 해결 전략은 별도 동기화 요구사항에서 다룬다.
- 범용 이슈 트래커의 사용자 정의 workflow, 임의 상태와 필드 schema는 제공하지 않는다.
- 자동 일정 산정, 리소스 최적화, 청구·원가 계산과 간트 계획은 제공하지 않는다.
- 문자 단위 실시간 공동 편집과 중앙 분산 잠금은 제공하지 않는다.
- `ours`·`theirs`보다 세밀한 대화형 필드별 충돌 해결은 현재 범위에 포함하지 않는다.
