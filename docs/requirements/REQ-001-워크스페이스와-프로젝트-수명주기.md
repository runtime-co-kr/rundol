# 워크스페이스와 프로젝트 수명주기

## 배경

사용자는 Rundol이 없는 Git 저장소에서 새 프로젝트를 시작할 수도 있고, 원격에 이미 존재하는 Rundol Workspace에 참여할 수도 있다. 로컬에는 Registry만 있고 프로젝트 worktree가 없거나, ref는 남아 있지만 mount가 끊어진 불완전한 상태도 발생할 수 있다.

초기화 명령이 이러한 상태를 구분하지 않고 항상 새 파일과 ref를 만들면 기존 정본을 중복하거나 덮어쓸 수 있다. 반대로 생성과 연결을 서로 다른 명령과 사전 지식에 의존시키면 사용자는 저장소 상태를 직접 해석해야 한다.

따라서 `rdl init`은 새 파일을 만드는 명령에 앞서 저장소의 Rundol 상태를 발견하고, 그 결과에 따라 기존 프로젝트 연결, 로컬 복구, 프로젝트 선택 또는 신규 생성을 결정하는 멱등적인 부트스트랩 진입점이어야 한다.

## 요구사항

- REQ-001-FR-01: 시스템은 초기화 관련 파일이나 ref를 쓰기 전에 Git 저장소, 로컬 Workspace manifest, Rundol ref, worktree와 선택한 remote의 Rundol ref를 검사해야 한다.
- REQ-001-FR-02: 시스템은 발견 결과를 `new`, `already-connected`, `attachable`, `repairable`, `needs-selection`, `conflict` 상태 중 하나로 분류하고 판단 근거를 제공해야 한다.
- REQ-001-FR-03: 사용자는 이미 정상 연결된 저장소에서 `rdl init`을 다시 실행해도 기존 파일·ref·commit을 변경하지 않고 현재 연결 상태를 확인할 수 있어야 한다.
- REQ-001-FR-04: 사용자는 유효한 로컬 Registry와 ref가 있으나 worktree가 누락된 경우 기존 정본에서 연결을 복구할 수 있어야 한다.
- REQ-001-FR-05: 선택한 remote에 유효한 Workspace와 프로젝트가 하나만 있으면 시스템은 신규 프로젝트를 만들지 않고 해당 프로젝트를 자동 연결해야 한다.
- REQ-001-FR-06: 선택한 remote에 프로젝트가 여러 개이면 사용자는 대화형 환경에서 프로젝트를 선택하거나 비대화형 환경에서 `--project`로 대상을 지정할 수 있어야 한다.
- REQ-001-FR-07: 로컬과 선택한 remote 어디에도 Rundol Workspace가 없을 때만 사용자는 새 Workspace와 첫 프로젝트를 생성할 수 있어야 한다.
- REQ-001-FR-08: 사용자는 기존 Workspace에 독립 프로젝트를 추가하고, 정본 ref와 Registry를 보존한 채 로컬 프로젝트 worktree만 분리할 수 있어야 한다.
- REQ-001-FR-09: 사용자는 구형 Workspace schema를 명시적으로 현재 schema로 이전할 수 있어야 하며, 시스템은 이전 ref를 자동 삭제하지 않아야 한다.
- REQ-001-FR-10: 시스템은 모든 부트스트랩 결과를 사람이 이해할 수 있는 출력과 안정적인 JSON 계약으로 제공해야 한다.

## 사전조건

- 대상 경로는 Git 저장소 루트여야 한다. 하위 디렉터리에서 실행한 경우 기존 저장소 루트를 발견할 수는 있지만 신규 Workspace를 임의의 하위 경로에 만들지 않는다.
- 실행 환경에는 지원 범위의 Node.js와 linked worktree를 지원하는 Git이 설치되어 있어야 한다.
- 원격 발견에는 사용자가 선택한 remote가 존재하고 읽기 접근이 가능해야 한다.
- 신규 프로젝트 키는 영문 소문자, 숫자와 하이픈만 사용하며 `workspace`는 예약어로 사용할 수 없다.
- 신규 프로젝트 생성에는 비어 있지 않은 표시 이름과 문서 프로파일 결정에 필요한 입력이 제공되어야 한다.
- worktree 대상 경로에 관리되지 않은 파일이 있으면 해당 파일을 자동 삭제하거나 덮어쓰지 않는다.

## 동작 규칙

1. `rdl init`은 상태 발견을 완료하기 전에는 manifest, ref, worktree와 제외 규칙을 변경하지 않는다.
2. 발견은 로컬 manifest와 ref를 먼저 확인하고, remote가 있으면 `rundol/workspace`와 Registry에 등록된 `rundol/<project-key>`를 확인한다.
3. 기본 remote는 `origin`이며 사용자는 `--remote <name>`으로 다른 remote를 명시할 수 있다.
4. 원격 `rundol/workspace`는 지원 schema의 manifest와 프로젝트 Registry를 포함해야 하며, 자동 연결 대상 프로젝트에는 대응하는 `rundol/<project-key>` ref가 있어야 한다.
5. 로컬 Workspace와 선택한 remote의 Workspace가 서로 다른 이력으로 분기되었으면 어느 한쪽을 자동 채택하지 않고 충돌 상태로 중단한다.
6. 인증, 권한, DNS, TLS, 프록시와 전송 오류를 원격 ref 부재로 해석하지 않는다. 원격 존재 여부를 판정할 수 없으면 신규 생성을 수행하지 않는다.
7. 정상 연결된 상태에서 `rdl init`을 반복하면 `already-connected`를 반환하며 새 commit을 만들거나 파일을 다시 생성하지 않는다.
8. Registry와 ref는 유효하지만 worktree만 없거나 끊어진 경우 기존 commit을 사용해 worktree를 복구하고 `repaired`를 반환한다.
9. 연결 가능한 원격 프로젝트가 하나이면 해당 프로젝트를 자동 연결한다. 여러 개이면 임의의 첫 프로젝트나 전체 프로젝트를 자동 선택하지 않는다.
10. 대화형 모드는 프로젝트 후보를 표시하고 사용자의 선택을 받을 수 있다. `--json`을 포함한 비대화형 모드는 stdin을 기다리지 않고 `needs-selection`과 후보 목록을 반환한다.
11. 신규 생성은 `--new` 또는 신규 생성 의도가 명확한 기존 위치 인수와 필수 입력을 사용하며, 발견된 기존 Workspace를 조용히 무시하지 않는다.
12. 신규 Workspace는 `rundol/workspace`, 프로젝트는 `rundol/<project-key>`의 독립 정본 이력을 가지며 각각 `projects/workspace/`, `projects/<project-key>/` linked worktree로 연결한다.
13. 신규 프로젝트 ref는 제품 branch에서 분기하지 않는다. 제품 branch의 추적 파일, commit, `.gitignore`와 `.rundol`을 변경하지 않는다.
14. `rdl project add`는 기존 Workspace Registry에 프로젝트를 등록한 뒤 해당 프로젝트의 독립 ref와 worktree를 생성한다. 일부 단계가 실패하면 완성되지 않은 등록을 성공 상태로 남기지 않는다.
15. `rdl detach`는 선택 프로젝트의 로컬 worktree만 제거하며 Workspace 등록, 로컬 ref, commit과 원격 ref를 보존한다.
16. 발견과 연결은 자동 push하지 않는다. 원격 변경은 사용자가 명시적으로 `rdl sync`를 실행할 때만 반영한다.
17. 구형 `rundol/settings` 발견과 schema migration은 명시적인 호환·이전 경로로 처리하며 신규 표준 Workspace로 오인하지 않는다.
18. JSON 결과는 최소한 `action`, `root`, `remote`, Workspace ref·commit·worktree, 대상 프로젝트와 후보 프로젝트를 표현할 수 있어야 한다.

## 상태와 예외

| 현재 상태 또는 상황 | 입력 또는 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 로컬·원격에 Rundol 없음 | 신규 프로젝트 정보로 `rdl init` | Workspace와 첫 프로젝트를 생성하고 `created`를 반환한다. |
| 로컬 Workspace와 선택 프로젝트가 정상 연결됨 | `rdl init` 재실행 | 기존 정본을 변경하지 않고 `already-connected`를 반환한다. |
| 로컬 Registry와 ref가 있고 worktree가 없음 | `rdl init --project <key>` | 기존 commit에서 worktree를 복구하고 `repaired`를 반환한다. |
| 원격 Workspace에 프로젝트가 하나 있음 | clone에서 `rdl init` | 해당 프로젝트를 연결하고 `attached`를 반환한다. |
| 원격 Workspace에 프로젝트가 여러 개 있음 | 대화형 `rdl init` | 후보를 표시하고 선택한 프로젝트만 연결한다. |
| 원격 Workspace에 프로젝트가 여러 개 있음 | `rdl init --json` | 파일을 변경하지 않고 `needs-selection`과 후보 목록을 반환한다. |
| 사용자가 프로젝트를 명시함 | `rdl init --project <key>` | Registry와 ref를 검증한 뒤 해당 프로젝트만 연결한다. |
| 지정 프로젝트가 Registry에 없음 | init 또는 attach | 가능한 프로젝트 목록과 함께 오류를 반환하며 새 프로젝트를 만들지 않는다. |
| Workspace Registry는 있으나 프로젝트 ref가 없음 | 연결 시도 | 불완전한 원격 상태를 보고하고 신규 프로젝트 ref를 임의 생성하지 않는다. |
| 로컬과 원격 Workspace ref가 분기됨 | init 또는 attach | `conflict`를 반환하고 동기화·복구 절차를 안내한다. |
| 원격 확인 중 인증·네트워크 오류 | init 또는 attach | 원인을 보존한 오류로 중단하며 로컬 seed를 만들지 않는다. |
| worktree 경로에 관리되지 않은 파일이 있음 | 연결 또는 복구 | 대상 파일을 보존하고 충돌 경로를 포함한 오류를 반환한다. |
| 기존 Workspace가 발견됨 | `rdl init ... --new` | 기존 Workspace를 덮어쓰지 않고 명시적인 충돌로 중단한다. |
| 프로젝트 worktree가 연결됨 | `rdl detach <key>` | worktree만 제거하고 Registry와 ref를 보존한다. |
| 프로젝트 worktree가 없음 | detach 재실행 | 기존 ref를 변경하지 않고 분리할 대상이 없음을 반환한다. |
| 구형 schema Workspace가 발견됨 | 일반 `rdl init` | 지원 상태와 migration 명령을 안내하고 자동 변환하지 않는다. |
| 구형 schema Workspace가 발견됨 | 명시적 migration | 현재 schema Workspace를 만들고 이전 ref를 보존한다. |

## 수용 기준

- [ ] fresh Git 저장소에서 신규 init을 실행하면 `rundol/workspace`, `rundol/<key>`와 두 linked worktree가 생성된다.
- [ ] 신규 init 전후 제품 branch의 추적 파일 목록과 commit은 동일하다.
- [ ] 동일 저장소에서 init을 반복해도 ref, commit, manifest와 worktree 내용이 변경되지 않고 `already-connected`가 반환된다.
- [ ] Registry와 ref만 남은 fixture에서 init을 실행하면 새 commit 없이 누락된 worktree만 복구된다.
- [ ] 기존 원격 프로젝트가 하나인 clone에서 init을 실행하면 신규 seed 없이 원격 commit이 연결된다.
- [ ] 기존 원격 프로젝트가 여러 개인 clone의 비대화형 init은 파일을 변경하지 않고 후보 목록과 `needs-selection`을 반환한다.
- [ ] 같은 다중 프로젝트 fixture에서 `--project <key>`를 사용하면 선택한 프로젝트만 연결된다.
- [ ] 지원하지 않는 schema, Registry 누락, 프로젝트 ref 누락과 로컬·원격 분기를 서로 다른 진단으로 구분한다.
- [ ] 원격 ref 부재와 인증·DNS·TLS 실패를 구분하며, 원격 확인 실패 시 로컬 Rundol ref를 생성하지 않는다.
- [ ] 관리되지 않은 worktree 대상 디렉터리를 덮어쓰지 않고 기존 파일 hash가 유지된다.
- [ ] 발견과 attach 전후 remote ref는 변경되지 않으며 push가 발생하지 않는다.
- [ ] detach 후 Registry와 프로젝트 ref는 남고 worktree만 제거되며 init 또는 명시적 연결로 다시 복구할 수 있다.
- [ ] schema migration 후 현재 Workspace 검사를 통과하고 이전 settings ref가 삭제되지 않는다.
- [ ] 사람용 출력과 JSON 출력이 동일한 action과 대상 프로젝트를 표현한다.
- [ ] Windows, macOS와 Linux에서 경로 정규화, remote 발견과 worktree 연결 시나리오가 통과한다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 데이터 안전성 | 발견·연결·복구 실패가 기존 ref, commit과 사용자 파일을 삭제하거나 덮어쓰지 않는다. | 단계별 실패를 주입하고 작업 전후 ref와 파일 hash를 비교한다. |
| 멱등성 | 같은 입력과 저장소 상태에서 init을 반복해도 첫 성공 이후 정본 변경이 발생하지 않는다. | 반복 실행 전후 ref, commit, worktree 목록과 Git status를 비교한다. |
| 진단성 | 모든 실패 결과가 상태 코드와 관련 project, remote, ref 또는 경로를 포함한다. | 실패 시나리오별 사람용 출력과 JSON schema를 검사한다. |
| 자동화 가능성 | 비대화형 실행은 사용자 입력을 기다리지 않고 안정적인 action과 후보 목록을 반환한다. | stdin이 닫힌 프로세스에서 다중 프로젝트 및 오류 시나리오를 실행한다. |
| 성능 | 로컬 상태만 사용하는 발견과 정상 재진입은 일반 개발 환경에서 2초 이내 완료된다. | 표준 fixture에서 20회 측정한 95백분위 값을 사용한다. |
| 호환성 | 지원 Node.js·Git과 Windows·macOS·Linux에서 같은 상태 전이와 JSON 계약을 제공한다. | 지원 환경 CI matrix에서 동일 E2E fixture를 실행한다. |
| 보안 | remote 자격 증명과 URL 내 비밀을 출력, 파일 또는 로그에 기록하지 않는다. | credential fixture의 stdout, stderr와 생성 파일을 secret scan한다. |

## 제외 범위

- 프로젝트 성격 인터뷰, 문서 프로파일 선택과 canonical 문서 경로는 문서·거버넌스 요구사항에서 다룬다.
- 프로젝트 문서와 태스크의 생성·편집·검증 규칙은 별도 요구사항에서 다룬다.
- 연결 이후의 fetch·merge·push와 의미적 충돌 해결은 원격 동기화 요구사항에서 다룬다.
- Git remote와 저장소 생성, 사용자 계정 발급, 인증 수단과 접근 권한 관리는 제공하지 않는다.
- 제품 source branch 생성·전환·병합과 일반 개발 worktree 관리는 제공하지 않는다.
- 사용자의 관리되지 않은 파일을 자동 삭제·이동하거나 분기된 ref를 강제로 재작성하지 않는다.
