# 워크스페이스와 프로젝트 수명주기

## 배경

사용자는 제품 코드가 이미 존재하는 Git 저장소에 프로젝트 거버넌스 자료를 도입하거나, 다른 환경에서 기존 원격 프로젝트를 다시 연결해야 한다. 이 과정에서 제품 브랜치에 관리 파일이 섞이거나 기존 원격 이력이 덮어써지면 안 된다. Workspace Registry, 프로젝트별 정본 브랜치와 linked worktree의 일부만 생성된 상태에서도 원인을 확인하고 안전하게 복구할 수 있어야 한다.

Workspace 수명주기는 최초 생성, 기존 원격 연결, 프로젝트 추가, 로컬 연결 해제, 브랜치·worktree 복구와 schema migration을 포함한다. 각 동작은 사람이 사용하는 CLI와 자동화가 동일하게 판단할 수 있도록 명확한 입력·출력·오류 계약을 제공해야 한다.

## 요구사항

- REQ-001-FR-01: 사용자는 기존 Git 저장소 루트에서 Workspace와 첫 프로젝트를 한 번의 초기화 명령으로 생성할 수 있어야 한다.
- REQ-001-FR-02: 사용자는 원격의 기존 Workspace와 전체 또는 선택 프로젝트를 로컬 linked worktree로 연결할 수 있어야 한다.
- REQ-001-FR-03: 사용자는 기존 Workspace에 독립적인 프로젝트를 추가할 수 있어야 한다.
- REQ-001-FR-04: 사용자는 프로젝트 정본 브랜치와 원격 이력을 삭제하지 않고 로컬 worktree 연결만 해제할 수 있어야 한다.
- REQ-001-FR-05: 사용자는 Registry에 등록된 프로젝트의 누락된 로컬 ref와 worktree를 복구할 수 있어야 한다.
- REQ-001-FR-06: 시스템은 Workspace 및 프로젝트 ref의 출처, 생성 여부, worktree 경로와 commit을 구조화된 결과로 제공해야 한다.
- REQ-001-FR-07: 시스템은 기존 schema의 Registry를 명시적인 migration으로 현재 schema로 전환하되 이전 ref를 자동 삭제하지 않아야 한다.

## 사전조건

- 실행 환경에 지원 버전의 Node.js와 Git이 설치되어 있어야 한다.
- 초기화 대상 경로는 Git 저장소 루트여야 하며, 하위 디렉터리에서의 신규 초기화는 허용하지 않는다.
- 프로젝트 키는 영문 소문자, 숫자와 하이픈만 사용하며 `workspace`는 예약어로 사용할 수 없다.
- 신규 프로젝트에는 비어 있지 않은 표시 이름이 제공되어야 한다.
- 원격 연결에는 요청한 remote가 존재하고 필요한 Git 인증·네트워크가 구성되어 있어야 한다.
- 대상 worktree 경로에 관리되지 않은 파일이 있으면 사용자가 정리하거나 별도 위치로 이동하기 전에는 덮어쓰지 않는다.

## 동작 규칙

1. 최초 초기화는 `rundol/workspace`와 `rundol/<project-key>` 브랜치, `projects/workspace/`와 `projects/<project-key>/` linked worktree를 생성한다.
2. Workspace Registry는 schemaVersion 6의 `workspace.yaml`, Client·프로젝트·이벤트 경로를 포함해야 하며 프로젝트 등록 파일은 `project-<key>.yaml` 형식을 사용한다.
3. 신규 프로젝트 ref는 제품 브랜치에서 분기하지 않는 독립 이력으로 시작해야 한다.
4. 로컬 ref가 이미 존재하면 그대로 재사용한다. 로컬 ref가 없고 `origin`에 대응 ref가 있으면 원격 commit을 가져와 사용한다.
5. 원격 ref가 명시적으로 존재하지 않고 완전한 로컬 seed가 있을 때만 신규 ref를 생성한다.
6. 인증, DNS, TLS, 프록시와 연결 오류를 원격 ref 부재로 간주하지 않으며, 로컬 신규 ref 생성으로 우회하지 않고 작업을 중단한다.
7. `rdl attach`는 `rundol/workspace`를 우선 사용하고, 전환 기간에만 구형 `rundol/settings`를 fallback으로 읽는다.
8. 프로젝트를 지정하지 않은 attach는 Registry에 등록된 모든 프로젝트를 연결하고, 지정한 경우 해당 프로젝트가 Registry에 있는지 확인한다.
9. `rdl project add`는 프로젝트 등록 파일, 로컬 seed, 전용 ref와 worktree가 모두 준비된 경우에만 성공 결과를 반환한다.
10. `rdl detach`는 선택한 프로젝트 worktree만 제거하고 Workspace 등록, 로컬 ref, commit과 원격 ref는 보존한다.
11. `rdl git init`은 기존 ref와 commit을 변경하지 않는 멱등 동작이어야 하며 누락된 worktree만 다시 연결할 수 있어야 한다.
12. 제품 브랜치의 제품 파일, `.gitignore`와 `.rundol`은 생성·수정하지 않는다. linked worktree 숨김 규칙은 로컬 `.git/info/exclude`에만 추가한다.
13. 파일 생성은 가능한 한 원자적으로 수행하고 실패 시 이미 존재하던 파일과 ref를 삭제하거나 덮어쓰지 않는다.
14. `--json` 요청은 성공과 자동화 가능한 식별자·경로·브랜치·commit 정보를 JSON으로 출력해야 한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| Workspace가 없는 Git 루트 | `rdl init <key> --name <name>` | Workspace와 첫 프로젝트를 생성하고 두 worktree가 연결된 상태가 된다. |
| Workspace manifest가 이미 존재함 | 같은 저장소에서 `rdl init` 재실행 | 기존 자료를 변경하지 않고 이미 초기화되었다는 오류를 반환한다. |
| Workspace가 정상 연결됨 | `rdl project add <key> --name <name>` | Registry와 프로젝트 ref·worktree에 새 프로젝트가 추가된다. |
| 같은 키의 프로젝트가 등록됨 | 동일 키로 project add | 기존 프로젝트를 변경하지 않고 중복 오류를 반환한다. |
| 로컬 ref 없음, 원격 ref 있음 | init·project add·git init | 원격 commit을 로컬 ref로 연결하고 새 이력을 만들지 않는다. |
| 로컬 ref 없음, 원격 ref 명시적 부재 | 완전한 로컬 seed로 init·git init | 독립적인 초기 commit과 ref를 생성한다. |
| 원격 확인 중 인증·네트워크 오류 | init·project add·git init·attach | ref 부재로 처리하지 않고 원인을 포함한 오류로 중단한다. |
| 대상 worktree가 올바른 branch에 연결됨 | git init 재실행 | commit과 worktree를 바꾸지 않고 성공한다. |
| 대상 경로에 관리되지 않은 파일이 있음 | worktree 연결 시도 | 파일을 덮어쓰지 않고 충돌 경로를 포함한 오류를 반환한다. |
| 프로젝트 worktree가 연결됨 | `rdl detach <key>` | worktree만 제거하고 Registry와 ref는 유지한다. |
| 프로젝트 worktree가 없음 | detach 재실행 | 삭제할 대상이 없음을 나타내며 기존 ref를 변경하지 않는다. |
| 구형 schemaVersion 5 Registry | `rdl workspace migrate` | schemaVersion 6 Workspace를 생성하고 기존 settings ref는 보존한다. |
| 초기화가 중간 단계에서 실패함 | 오류 수정 후 복구 명령 실행 | 완성된 기존 ref는 재사용하고 누락된 등록·worktree만 안전하게 복구할 수 있다. |

## 수용 기준

- [ ] 깨끗한 Git fixture에서 init을 실행하면 `rundol/workspace`, `rundol/<key>`와 두 linked worktree가 생성된다.
- [ ] 초기화 전후 제품 브랜치의 추적 파일 목록과 commit이 변하지 않는다.
- [ ] 생성된 Workspace와 프로젝트는 `rdl workspace check` 및 `rdl check --strict`를 오류 없이 통과한다.
- [ ] 동일한 init을 재실행하면 기존 ref·commit·파일을 변경하지 않고 중복 상태를 보고한다.
- [ ] 기존 프로젝트의 git init을 두 번 실행해도 두 번째 실행에서 새 commit을 만들지 않는다.
- [ ] 원격 ref가 있는 fixture에서는 해당 commit을 연결하고 별도의 seed commit을 생성하지 않는다.
- [ ] 존재하지 않는 원격 ref와 인증 실패를 서로 다른 결과로 처리하며 인증 실패 시 로컬 ref를 만들지 않는다.
- [ ] attach에서 전체 프로젝트와 단일 프로젝트 선택이 각각 Registry 목록과 일치한다.
- [ ] project add 성공 후 Registry manifest, 프로젝트 branch와 worktree가 동일 키를 가리킨다.
- [ ] 관리되지 않은 대상 디렉터리를 worktree로 덮어쓰지 않으며 기존 파일이 보존된다.
- [ ] detach 후 프로젝트 branch와 Registry는 남고 worktree만 제거되며 git init으로 다시 연결할 수 있다.
- [ ] schema migration 후 현재 schema 검증을 통과하고 이전 settings branch는 삭제되지 않는다.
- [ ] 성공한 `--json` 출력에서 root, project, branch, worktree와 commit을 파싱할 수 있다.
- [ ] Windows, macOS와 Linux fixture에서 경로 정규화와 worktree 연결 테스트가 통과한다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 원자성 | 실패한 동작이 기존 ref·commit과 사용자 파일을 손상시키지 않는다. | 각 생성 단계에 실패를 주입한 뒤 이전 Git object와 파일 hash를 비교한다. |
| 멱등성 | 복구·연결 명령의 반복 실행이 기존 상태를 변경하지 않는다. | 동일 명령 전후 ref, commit과 worktree 목록을 비교한다. |
| 성능 | 로컬 ref만 사용하는 단일 프로젝트 초기화·복구가 일반 개발 환경에서 5초 이내 완료된다. | 네트워크를 차단한 표준 fixture에서 20회 측정한 95백분위 값을 사용한다. |
| 진단성 | 모든 실패가 대상 경로·project key·remote 또는 ref 중 관련 식별자를 포함한다. | 오류 시나리오별 stderr와 JSON 오류 계약을 검사한다. |
| 호환성 | 지원 Node.js·Git 및 Windows·macOS·Linux에서 동일한 상태 계약을 제공한다. | CI 운영체제·버전 matrix의 통합 테스트로 검증한다. |
| 보안 | remote 자격 증명을 출력·파일·로그에 기록하지 않는다. | 토큰이 포함된 credential helper fixture의 출력과 생성 파일을 검색한다. |

## 제외 범위

- 프로젝트 문서와 태스크의 생성·편집·검증 세부 규칙은 별도 요구사항에서 다룬다.
- 프로젝트 변경의 원격 병합, push와 충돌 해결 정책은 동기화 요구사항에서 다룬다.
- Git remote·저장소 생성, 사용자 계정 발급과 자격 증명 관리는 제공하지 않는다.
- 제품 소스 branch 생성·전환·병합과 일반 개발 worktree 관리는 제공하지 않는다.
- 문자 단위 실시간 공동 편집이나 중앙 잠금 서버는 제공하지 않는다.
- 사용자의 관리되지 않은 파일을 자동 삭제·이동하거나 손상된 ref를 강제로 재작성하지 않는다.
