# 협업 클라이언트 등록

## 배경

여러 장치와 에이전트가 같은 Workspace에서 작업하려면 변경 주체를 안정적으로 식별하고 프로젝트 멤버에게 귀속할 수 있어야 한다.

## 요구사항

- 시스템은 `device`, `agent`, `service`, `human` 유형의 Client를 Workspace 전역 저장소에 등록·조회·활성화·비활성화해야 한다.
- 등록 결과는 `projects/workspace/clients/client-<id>.yaml`에 보존되어야 한다.
- 등록은 명령줄과 Board 화면 두 경로에서 수행할 수 있어야 하며 두 경로는 같은 저장 절차를 사용해야 한다.
- Board 화면은 미등록 기기가 편집·댓글·동기화를 시도한 자리에서 등록을 받고, 등록이 끝나면 시도하던 동작으로 이어가야 한다.

## 사전조건

- Workspace `schemaVersion`은 6 이상이어야 한다.
- 등록 요청은 소문자 영숫자와 하이픈으로 된 ID, 이름, 허용 유형, `MEMBER-###` 소유자를 포함해야 한다.

## 동작 규칙

1. Client ID와 유형은 소문자로, owner는 대문자로 정규화한다.
2. 새 Client는 `revision: 1`, `status: active`, 등록 시각과 등록 주체를 가진다.
3. 이미 존재하는 ID는 덮어쓰지 않고 오류로 거절한다.
4. 상태 변경은 revision을 1 증가시키며 동일 상태 요청은 파일을 바꾸지 않는다.
5. 등록과 실제 상태 변경은 Workspace 설정 브랜치 저장 절차를 호출한다.
6. 화면 등록은 이 기기의 식별자를 그대로 사용하며 사람이 고르지 않는다.
7. 미등록 거절은 `unknown-client` 코드를 함께 반환하고, 안내 문구는 화면 경로를 명령줄보다 먼저 가리킨다.
8. 등록 때문에 중단된 동작은 등록 성공 이후 최신 스냅샷을 기준으로 다시 수행하며, 등록을 닫으면 그 동작도 함께 버린다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 미등록 | 유효한 등록 요청 | `active`, revision 1 Client 생성 |
| 등록됨 | 같은 ID 등록 | 중복 등록 오류, 기존 파일 유지 |
| `active` | disable | `disabled`, revision 증가 |
| `disabled` | enable | `active`, revision 증가 |
| 현재 상태와 요청 상태 동일 | 상태 변경 | `changed: false`, 저장 생략 |
| 미등록 | 화면에서 편집·댓글·동기화 시도 | 명령줄 안내 대신 등록 절차를 그 자리에서 연다 |
| 미등록 | 화면 등록 완료 | 등록 후 중단됐던 동작을 최신 스냅샷으로 이어서 수행 |
| 미등록 | 등록 절차를 닫음 | 저장 없이 종료하고 이어갈 동작도 버린다 |
| 식별자 없음 | 화면 등록 시도 | 등록을 열지 않고 프로젝트 준비(`rdl git init`)를 안내 |

## 수용 기준

- [ ] CLI 등록 결과의 ID·상태가 입력과 일치하고 Client YAML 파일이 생성된다.
- [ ] `client show`가 등록된 owner를 반환하며 목록은 파일명 순서로 안정적으로 정렬된다.
- [ ] 잘못된 ID·유형·owner·빈 이름과 중복 ID는 명확한 오류로 거절된다.
- [ ] 미등록 기기가 화면에서 편집을 시도하면 명령줄 문자열이 아니라 등록 절차가 열리고, 등록 후 편집이 이어진다.
- [ ] 화면의 등록 칸은 한 벌만 존재하며 식별자 칸은 고칠 수 없다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 원자성 | 임시 파일 작성 후 rename으로 완전한 YAML만 노출 | 저장 함수 코드 검토와 등록 테스트 |
| 추적성 | 등록 시각·등록 주체·revision을 보존 | 생성 YAML 검사 |
| 호환성 | schemaVersion 6 미만에서는 마이그레이션 안내와 함께 중단 | 하위 schema fixture 검사 |

## 제외 범위

- Client가 특정 문서의 편집 lease를 획득·갱신·해제하는 규칙은 REQ-020에서 다룬다.

## 기능별 설계 계약

### COL-01

#### 입력

- 등록: `id`, `name`, `type(device|agent|service|human)`, `owner(MEMBER-###)`. 화면 등록은 `id`를 이 기기의 값으로 고정한다.
- 상태 변경: 등록된 `id`와 `active` 또는 `disabled` 상태.

#### 출력

- 등록은 `{ id, file, status: active, commit }`, 상태 변경은 `{ id, status, changed, commit? }`을 반환한다.
- 조회는 정규화된 `id`, `name`, `type`, `owner`, `status`, `file`을 반환한다.

#### 업무 규칙

- ID는 `^[a-z0-9]+(?:-[a-z0-9]+)*$`, owner는 `^MEMBER-\d{3}$`를 만족해야 하며 Client 유형은 네 허용값 중 하나여야 한다.
- 유형에는 기본값을 두지 않는다. `device`는 기계의 종류일 뿐 행위 주체를 담지 않아, 그 값에서 파생한 주체 판정이 실제로 틀린 적이 있다.

#### 상태와 전이

- 최초 상태는 `active`이고 enable/disable 요청으로 `active`와 `disabled` 사이를 전이한다. 실제 전이마다 revision이 증가한다.

#### 권한과 승인

- owner는 등록된 프로젝트 멤버 형식으로 기록하며, 문서 lease 사용 시 해당 프로젝트 `project.md`의 실제 멤버인지 추가 검증한다.

#### 정상·오류·취소

- 정상 등록과 상태 변경은 설정 저장을 완료한다. 중복·형식 오류·미등록 조회는 파일을 변경하지 않고 예외를 반환한다. 화면 등록의 취소는 저장을 남기지 않으며 중단됐던 동작도 수행하지 않는다.

#### 감사 기록

- Client YAML의 `registeredAt`, `registeredBy`, `revision`, `status`와 설정 저장 commit이 변경 근거다.

#### 수용 기준

- `test/collaboration-store.test.js`에서 등록 파일 생성, ID, owner 조회가 통과하고 Board snapshot에서 등록 Client를 조회할 수 있다.
- `test/board-ui.test.js`에서 화면이 등록 명령줄을 건네지 않고, 등록 칸이 한 벌이며, 등록 후 중단된 동작으로 이어지는 것이 확인된다.
- `test/comment.test.js`에서 미등록 거절이 `unknown-client` 코드와 화면 우선 안내를 함께 반환한다.
