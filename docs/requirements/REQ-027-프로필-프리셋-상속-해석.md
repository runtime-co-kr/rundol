# 프로필 프리셋 상속 해석

## 배경

프로필 프리셋의 상속 해석은 [[REQ-010-문서-계획-계약-요구사항|REQ-010]]이 나르던 기능 하나를 문서 1개 = 기능 1개 계약에 따라 분리한 정본이다. 프리셋과 유형별 하부 요소를 계약이 들고 다니면 저장할 때마다 보존해야 하고 빠뜨리면 조용히 빈 값이 된다. 계약은 프로필 이름 하나만 저장하고 그 뜻은 `board.json` 상속(내장 기본값 → Workspace → 프로젝트)에서 읽을 때마다 다시 계산한다.

## 요구사항

- 프리셋이 정하지 않은 유형의 하부 요소는 내장 기본값을 그대로 쓴다.
- 정책에서 어디에도 배치되지 않은 유형은 onDemand로 둔다.
- 프로필 이름은 영문 소문자·숫자·하이픈만 허용하고, 내장에 없는 이름은 정책을 반드시 함께 요구한다.
- 팀이 정의한 프리셋을 CLI와 Board가 같은 목록으로 제공한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 프리셋 정의 변경 | 조회 | 계약은 그대로이고 다음 읽기부터 새 정의가 유효하다. |
| 정책 없는 커스텀 프리셋 | 파일 읽기 | 조용한 기본값 대체 대신 거절한다. |

## 기능별 설계 계약

### DCP-03

#### 입력

- `board.json` 상속 결과(내장 기본값 → Workspace → 프로젝트)와 계약이 가리키는 프로필 이름

#### 출력

- 고를 수 있는 프리셋 목록과 각 프리셋의 라벨·설명·정책·유형별 하부 요소

#### 업무 규칙

- 프리셋이 정하지 않은 유형의 하부 요소는 내장 기본값을 쓴다. 정책에서 어디에도 배치되지 않은 유형은 onDemand로 둔다. 빠뜨린 유형이 사라지면 그 유형은 계약에서 없는 것이 되어 검사도 안내도 받지 못한다.

#### 상태와 전이

- 프리셋이 늘거나 줄어도 계약은 그대로다. 계약은 이름 하나만 저장하고 그 뜻은 읽을 때마다 다시 계산된다.

#### 권한과 승인

- 프리셋 정의는 Workspace와 프로젝트의 `board.json`이 소유하고, 어떤 프리셋을 쓸지는 계약 revision으로 바꾼다.

#### 정상·오류·취소

- 이름 형식 위반, 정책 없는 커스텀 프리셋, 한 유형이 두 상태에 걸친 정책은 파일을 읽는 시점에 거절한다.

#### 감사 기록

- 프리셋 변경은 `board.json`의 Git 이력에, 어떤 프리셋을 쓰는지는 계약 revision과 history에 남는다.

#### 수용 기준

- 팀이 정의한 프리셋을 CLI와 Board가 같은 목록으로 제공하고, 그 이름으로 저장한 계약이 다시 읽을 때도 그 이름을 유지한다.
