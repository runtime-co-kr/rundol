# 인공지능 클라이언트와 도구 연동

## 배경

Codex, Claude Code, GitHub Copilot과 다른 AI 도구가 같은 프로젝트를 지원해도 각 클라이언트가 별도 규칙과 문맥 복제본을 사용하면 문서 구조, 책임과 완료 조건이 달라질 수 있다. AI가 파일명·ID·Git 상태를 추정해 직접 조작하면 원자적 생성과 검증 계약을 우회할 위험도 있다.

런돌은 하나의 Agent Skills 정본과 표준 action routing을 통해 모든 클라이언트가 같은 절차를 사용하게 해야 한다. IDE와 Obsidian도 별도 데이터베이스가 아니라 프로젝트 worktree를 열어야 한다. 운영 개선을 위해 실행 주체 선택과 보고된 토큰 사용량은 집계하되 프롬프트·문서 본문 같은 민감한 작업 내용을 로그에 남기지 않아야 한다.

## 요구사항

- REQ-008-FR-01: 시스템은 AI 클라이언트 공통 거버넌스 계약을 하나의 Agent Skills 정본으로 제공해야 한다.
- REQ-008-FR-02: 사용자는 Codex, Claude Code와 GitHub Copilot의 개인 skill 경로에 같은 스킬을 명시적으로 설치·갱신할 수 있어야 한다.
- REQ-008-FR-03: 프로젝트 instruction 기반 도구는 최소 adapter로 공통 스킬과 governance contract를 발견할 수 있어야 한다.
- REQ-008-FR-04: AI 클라이언트는 작업 전에 표준 action의 권장 실행 주체와 command hint를 조회할 수 있어야 한다.
- REQ-008-FR-05: 사용자는 CLI, LLM 또는 hybrid의 실제 실행 선택, 관련 문서·태스크와 fallback 이유를 기록할 수 있어야 한다.
- REQ-008-FR-06: 시스템은 Client가 보고한 모델·provider별 토큰 사용량과 미보고 이벤트를 기록·집계해야 한다.
- REQ-008-FR-07: IDE와 Obsidian은 프로젝트 worktree의 동일 Markdown·JSON 정본을 읽고 편집할 수 있어야 한다.
- REQ-008-FR-08: 사용자는 프로젝트 Vault에 최소 Obsidian 설정을 설치하되 기존 개인 설정을 기본적으로 보존할 수 있어야 한다.
- REQ-008-FR-09: 모든 클라이언트 작업은 동일한 strict 검사와 프로젝트 branch 저장·동기화 품질 게이트를 통과해야 한다.

## 사전조건

- 런돌 CLI와 governance skill source가 정상 설치되어 있어야 한다.
- 작업 대상 Workspace와 프로젝트 worktree가 연결되어 있어야 한다.
- 문서·태스크 작업의 owner·reviewer·stakeholder가 프로젝트 헌장에 등록되어 있어야 한다.
- 스킬 설치 대상 AI 클라이언트의 개인 설정 경로에 사용자 쓰기 권한이 있어야 한다.
- action record에는 지원 action, 실제 executor와 필요한 artifact·task 식별자가 제공되어야 한다.
- token record에는 0 이상의 정수 사용량 또는 명시적 unreported 상태가 제공되어야 한다.
- Obsidian 연동에서는 선택 프로젝트 자체를 Vault root로 열 수 있어야 한다.

## 동작 규칙

1. `rundol-project-governance/SKILL.md`와 연결 references를 클라이언트 공통 계약의 정본으로 사용하고 클라이언트별 내용을 따로 수정하지 않는다.
2. 개인 스킬 설치 대상은 Codex, Claude Code, GitHub Copilot이며 환경 변수로 각 테스트·사용자 home을 override할 수 있어야 한다.
3. Rundol 관리 스킬에는 `.rundol-managed.json` marker를 두고 다음 설치에서만 안전하게 갱신한다.
4. marker가 없는 기존 스킬 디렉터리는 사용자 소유로 판단해 기본 설치에서 보존하고, 사용자가 명시한 `--force`에서만 교체한다.
5. 스킬 설치는 npm `postinstall`과 분리하고 CLI 설치 실패나 임시 clone link를 유발하지 않아야 한다.
6. Gemini CLI, Cursor와 AGENTS.md 기반 도구는 discovery adapter만 별도로 두고 실제 계약은 공통 SKILL과 governance reference를 읽어야 한다.
7. 표준 executor는 `cli`, `llm`, `hybrid`로 제한한다.
8. Workspace·프로젝트·문서·태스크의 ID·경로·ref·상태처럼 결정적 변경은 CLI를 우선 권장한다.
9. 코드나 자연어 본문 생성은 LLM, LLM 작성 후 CLI 검증·저장은 hybrid를 권장한다.
10. action resolve는 action, recommendedExecutor, commandHint와 reason을 구조화해 반환해야 한다.
11. action record는 planned·actual executor, adopted 여부, artifactId·taskId와 선택적 fallbackReason을 기록해야 한다.
12. 권장 executor와 실제 executor가 다르고 planned가 hybrid가 아니면 fallbackReason을 필수로 요구한다.
13. 알려진 action alias는 canonical action으로 정규화하고 지원하지 않는 action은 명시적 오류로 처리한다.
14. token record는 provider, model, client, reported, input·output·cached·total token을 로컬 debug log에 기록해야 한다.
15. Rundol은 모델 공급자 수치를 추정하지 않고 Client가 보고한 값만 합산한다. unreported 이벤트의 token 수치는 모두 0이어야 한다.
16. debug summary는 토큰 총계, 보고·미보고 이벤트, planned·actual executor별 건수, 채택·fallback 건수와 채택률을 제공해야 한다.
17. debug·action log는 프로젝트의 Git 비추적 `.rundol/logs/debug.jsonl`에 append하고 prompt와 content 필드를 제거해야 한다.
18. 여러 프로젝트에서 로그 대상을 추론할 수 없으면 `--project`를 요구해 잘못된 프로젝트에 기록하지 않는다.
19. Obsidian Vault root는 저장소 root가 아닌 `projects/<project-key>/`이며 정본 문서와 태스크를 그대로 사용한다.
20. Obsidian 기본 설정은 app, core plugins, graph, templates JSON만 관리하고 workspace, tab, cache, hotkey와 plugin data 같은 개인 상태는 Git에서 제외한다.
21. `rdl obsidian init`은 기존 같은 이름 설정을 기본 보존하고 `--force`에서만 유효한 JSON template로 교체한다.
22. AI·IDE·Obsidian의 모든 변경은 실제 파일명 Wiki link, 책임 구조와 strict 검사를 동일하게 적용하며 클라이언트 편의를 이유로 필드를 생략하지 않는다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 지원 AI client home 비어 있음 | skill install | 공통 skill 전체와 관리 marker를 각 대상에 설치한다. |
| Rundol 관리 skill 존재 | skill install 재실행 | 최신 source와 같은 내용으로 갱신한다. |
| marker 없는 사용자 skill 존재 | 일반 skill install | 기존 디렉터리를 보존하고 preserved 상태를 반환한다. |
| marker 없는 사용자 skill 존재 | force install | 명시적 요청에 따라 공통 skill로 교체한다. |
| 알려진 표준 action | action resolve | canonical action과 권장 executor·명령·근거를 반환한다. |
| alias action | action resolve | canonical action으로 정규화한 같은 권장을 반환한다. |
| 지원하지 않는 action | resolve·record | 로그를 쓰지 않고 지원하지 않는 action 오류를 반환한다. |
| 권장·실제 executor 일치 | action record | adopted true 이벤트를 append한다. |
| planned hybrid | actual cli·llm·hybrid | fallback 이유 없이도 adopted true로 기록한다. |
| 권장과 다른 executor | fallback 이유 없음 | 이벤트를 기록하지 않고 이유 필요 오류를 반환한다. |
| 유효한 token 수치 | debug record | reported 이벤트와 정확한 합계를 기록한다. |
| 공급자가 사용량 미제공 | `--unreported`와 0 수치 | 미보고 이벤트로 기록하고 총계에 0을 더한다. |
| 음수·비정수 또는 unreported의 양수 | debug record | 로그를 변경하지 않고 입력 오류를 반환한다. |
| prompt·content를 포함한 내부 event | append | 해당 필드를 제거하고 나머지 안전 metadata만 기록한다. |
| 프로젝트 하나 또는 project 내부 실행 | debug 기록 | 올바른 프로젝트 로컬 log를 선택한다. |
| 여러 프로젝트에서 대상 불명 | debug 기록 | project key 필요 오류를 반환한다. |
| Obsidian 설정 없음 | obsidian init | 최소 설정과 assets·inbox·templates 디렉터리를 준비한다. |
| 기존 개인 설정 존재 | 일반 obsidian init | 기존 파일을 preserved로 반환하고 덮어쓰지 않는다. |
| 기존 설정 존재 | force init | template JSON 유효성을 확인한 뒤 원자적으로 교체한다. |

## 수용 기준

- [ ] 세 지원 AI 클라이언트에 설치된 SKILL과 reference 파일 hash가 공통 source와 같다.
- [ ] 설치된 각 스킬에 관리 주체·client·skill을 식별하는 marker가 있다.
- [ ] unmanaged skill이 일반 설치에서 byte 단위로 보존되고 force에서만 교체된다.
- [ ] npm 설치만으로 사용자 skill home이 변경되지 않는다.
- [ ] project adapter가 계약 내용을 복제하지 않고 공통 SKILL과 governance reference를 발견하게 한다.
- [ ] 모든 표준 action이 canonical ID, 권장 executor, 명령 hint 또는 null, 근거를 반환한다.
- [ ] alias가 canonical action과 동일한 resolve 결과를 제공한다.
- [ ] 권장과 실제 executor 불일치가 fallback 이유 없이는 기록되지 않는다.
- [ ] action event가 관련 artifact·task와 planned·actual·adopted·fallback을 정확히 보존한다.
- [ ] debug summary가 executor별 계획·실제 건수, 채택·fallback 수와 채택률을 정확히 계산한다.
- [ ] reported token event의 input·output·cached·total 합계가 summary와 일치한다.
- [ ] unreported event가 별도 집계되고 0이 아닌 수치를 허용하지 않는다.
- [ ] 음수·비정수 token 입력이 기존 debug log를 변경하지 않는다.
- [ ] prompt, content와 문서 본문 marker가 debug·action log에 존재하지 않는다.
- [ ] debug·action log가 프로젝트 branch의 추적 파일에 포함되지 않는다.
- [ ] 다중 프로젝트 대상 불명확 상태에서 로그가 임의 프로젝트에 기록되지 않는다.
- [ ] Obsidian이 프로젝트 worktree를 Vault로 열고 실제 문서 link·tag·block 관계를 탐색할 수 있다.
- [ ] 일반 Obsidian init이 기존 설정을 보존하고 force init의 모든 결과 JSON을 파싱할 수 있다.
- [ ] workspace·tab·cache·개인 plugin data가 프로젝트 branch에 추적되지 않는다.
- [ ] AI, IDE와 Obsidian에서 수정한 동일 문서가 strict 검사 및 save 후 같은 Git 정본으로 읽힌다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 일관성 | 모든 지원 client가 같은 skill·governance contract와 strict 검사 결과를 사용한다. | client별 설치 hash와 동일 fixture 작업 결과를 비교한다. |
| 개인정보 보호 | prompt·본문·비밀을 기록하지 않고 필요한 실행 metadata만 로컬에 보존한다. | 민감 marker를 주입한 action·debug log secret scan을 수행한다. |
| 추적성 | 실행 주체 선택과 관련 artifact·task를 프로젝트별로 집계할 수 있다. | action fixture의 raw event와 summary를 역검증한다. |
| 이식성 | Markdown·JSON 정본이 AI·IDE·Obsidian 왕복 후 의미와 encoding을 유지한다. | 한글·Wiki link·Mermaid 문서의 cross-client round-trip을 비교한다. |
| 안전성 | 사용자 관리 skill과 개인 Obsidian 설정을 기본 동작에서 덮어쓰지 않는다. | unmanaged·existing fixture의 설치 전후 tree hash를 비교한다. |
| 결정성 | 같은 action·event 집합이 같은 canonical action과 summary를 만든다. | alias·event 순서가 다른 반복 테스트 결과를 비교한다. |
| 성능 | 10만 debug event summary가 일반 환경 3초 이내 완료된다. | 대규모 JSONL fixture에서 20회 측정한 95백분위를 사용한다. |

## 제외 범위

- AI 모델 실행, provider 계정·API key 관리와 모델 응답 품질 자체를 제공·보장하지 않는다.
- 공급자가 보고하지 않은 token 사용량을 추정하거나 비용을 임의 계산하지 않는다.
- 프롬프트, 전체 응답, 문서 본문과 소스 코드 내용을 debug log에 보존하지 않는다.
- Client별로 서로 다른 governance contract를 독립 유지하지 않는다.
- AI가 strict 검사·책임 구조·Git 품질 게이트를 우회하도록 허용하지 않는다.
- Obsidian 실행 파일, plugin binary와 개인 workspace 상태를 배포·동기화하지 않는다.
- 범용 IDE extension, LSP와 원격 AI 작업 queue 구현은 현재 제공하지 않는다.
- 스킬 설치가 사용자 승인 없이 unmanaged 디렉터리를 삭제·교체하지 않는다.
