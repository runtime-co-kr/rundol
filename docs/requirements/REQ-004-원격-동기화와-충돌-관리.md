# 원격 동기화와 충돌 관리

## 배경

런돌의 Workspace Registry와 프로젝트 문서·태스크는 서로 다른 Git 브랜치가 소유한다. 여러 장치와 Agent가 같은 프로젝트를 수정하면 로컬과 원격 이력이 분기하거나 동일 파일·태스크 필드가 충돌할 수 있다. 단순 push 또는 강제 덮어쓰기는 등록 정보, 문서와 완료 증거를 유실시킬 수 있다.

동기화는 로컬 변경 저장, 원격 fetch, 이력 관계 판정, 안전한 병합, 전체 검증과 push를 하나의 명시적 흐름으로 제공해야 한다. 자동으로 해결할 수 없는 충돌은 원격 변경을 덮어쓰지 않고 재현 가능한 pending 기록으로 남겨 사용자가 전략을 선택할 수 있어야 한다.

## 요구사항

- REQ-004-FR-01: 사용자는 선택 프로젝트 또는 등록된 전체 프로젝트의 로컬 변경을 지정 Git remote와 동기화할 수 있어야 한다.
- REQ-004-FR-02: 시스템은 프로젝트보다 Workspace Registry를 먼저 저장·동기화해야 한다.
- REQ-004-FR-03: 시스템은 fetch 결과와 공통 base를 기준으로 unchanged, publish-new, fast-forward, local-ahead 또는 merge 동작을 결정해야 한다.
- REQ-004-FR-04: 시스템은 문서·샤드 태스크의 Git 병합과 기존 단일 태스크 저장소의 필드 단위 의미 병합을 지원해야 한다.
- REQ-004-FR-05: 병합 결과는 push 전에 프로젝트 전체 엄격 검증을 통과해야 한다.
- REQ-004-FR-06: 해결되지 않은 충돌은 ours·theirs commit, 대상 파일 또는 필드와 프로젝트를 포함한 pending 기록으로 보존해야 한다.
- REQ-004-FR-07: 사용자는 pending 충돌을 조회하고 명시적으로 ours 또는 theirs 전략으로 해결한 뒤 검증된 merge commit을 만들 수 있어야 한다.
- REQ-004-FR-08: 사용자는 원격 상태 확인과 로컬 병합까지만 수행하고 push를 생략할 수 있어야 한다.
- REQ-004-FR-09: 사용자는 일정 간격 또는 단일 반복으로 동기화 watch를 실행할 수 있어야 한다.

## 사전조건

- Workspace와 대상 프로젝트가 Registry에 등록되고 로컬 ref·worktree가 연결되어 있어야 한다.
- 지정한 Git remote가 저장소에 존재해야 한다.
- fetch·push가 필요한 경우 remote에 대한 네트워크와 Git 인증이 구성되어 있어야 한다.
- 로컬 프로젝트 변경은 엄격 검증이 가능한 정본 형식이어야 한다.
- 충돌 해결 요청에는 현재 프로젝트의 pending 충돌 기록과 `ours` 또는 `theirs` 전략이 제공되어야 한다.
- watch 중복 실행을 방지하기 위한 로컬 lock을 획득할 수 있어야 한다.

## 동작 규칙

1. sync는 Workspace 저장·동기화, 프로젝트 save, 프로젝트 fetch, 이력 판정·병합, materialize, 엄격 검증, 선택적 push 순서로 실행한다.
2. save는 변경이 있을 때만 commit을 만들며 검증 실패 시 fetch와 push를 시작하지 않는다.
3. fetch는 명시한 remote와 정확한 `rundol/workspace` 또는 `rundol/<project-key>` ref만 대상으로 한다.
4. 원격 ref가 없으면 로컬 ref를 새 원격 branch로 게시할 수 있으며 action을 `publish-new`로 반환한다.
5. 원격 commit이 로컬과 같으면 `unchanged`, 로컬의 후손이면 `fast-forward`, 원격이 로컬의 조상이면 `local-ahead`로 처리한다.
6. 양쪽이 분기했지만 공통 base가 있으면 저장 형식에 맞는 3-way 병합을 수행한다.
7. 공통 이력이 없으면 자동 병합이나 강제 push를 수행하지 않고 중단한다.
8. 샤드 저장 프로젝트의 문서와 태스크 파일은 Git 병합하고, 충돌 파일이 있으면 merge를 abort한 뒤 pending 기록을 남긴다.
9. 기존 단일 태스크 저장소는 base·ours·theirs의 필드 단위 의미 병합을 사용하고 같은 필드의 양립 불가능한 변경을 pending 의미 충돌로 기록한다.
10. 병합 중 문서 충돌 또는 병합 후 strict 검사 오류가 발생하면 merge commit과 push를 만들지 않고 기존 유효 상태를 복구한다.
11. 충돌이 없고 검증을 통과한 경우에만 merge commit을 생성한다.
12. 기본 sync는 같은 이름의 원격 ref로 push하며 강제 push를 사용하지 않는다. `--no-push`에서는 로컬 결과만 유지한다.
13. 충돌 해결은 pending 기록에 포함된 대상만 처리하고 예상하지 못한 추가 충돌이 있으면 중단한다.
14. ours·theirs 전략은 기록된 충돌 전체에 일관되게 적용하며 해결 결과를 strict 검사한 뒤 commit한다.
15. 충돌 해결 성공 후 pending 기록을 삭제한다. `conflict clear`는 기록만 제거하며 branch나 파일을 해결하지 않는다.
16. 전체 프로젝트 sync는 Registry 순서대로 각 프로젝트를 처리하는 독립 연산이며 하나의 원자적 다중 branch 트랜잭션으로 간주하지 않는다.
17. 인증·DNS·TLS·프록시 오류는 원격 ref 부재로 간주하지 않고 원인을 포함한 fetch·push 오류로 반환한다.
18. HTTP remote 명령에 필요한 전송 호환 설정은 명령 범위에만 적용하고 사용자의 전역 Git 설정을 변경하지 않는다.
19. 결과는 remote, branch, action, commit, saved, pushed와 projection 정보를 구조화해 반환한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 로컬·원격 commit 동일 | sync | 변경 없이 검증하고 `unchanged`를 반환한다. |
| 원격 ref 없음 | sync | 로컬 ref를 새 원격 branch로 push하고 `publish-new`를 반환한다. |
| 로컬이 원격보다 뒤처짐 | sync | 원격으로 fast-forward하고 worktree·projection을 갱신한다. |
| 로컬만 앞섬 | sync | 로컬 commit을 유지하고 검증 후 push한다. |
| 공통 base에서 양쪽이 분기함 | sync | 자동 병합 가능한 변경을 merge commit으로 통합하고 검증 후 push한다. |
| 로컬 변경이 strict 검사 실패 | sync | commit·fetch·push 없이 오류를 반환한다. |
| 로컬과 원격에 공통 이력 없음 | sync | 자동 병합·강제 push 없이 중단한다. |
| 샤드 파일 또는 문서 충돌 | sync | merge를 abort하고 version 2 pending 충돌 파일을 남기며 push하지 않는다. |
| 단일 태스크 동일 필드 충돌 | sync | base·ours·theirs와 JSON pointer를 pending 기록에 남기고 push하지 않는다. |
| 병합 결과 검증 실패 | sync | merge를 abort하고 마지막 유효 로컬 상태를 보존한다. |
| pending 충돌 있음 | conflict list | commit과 충돌 파일·필드 목록을 변경 없이 반환한다. |
| 유효한 pending과 전략 제공 | conflict resolve | 선택 전략 적용, strict 검사와 merge commit 후 pending 기록을 삭제한다. |
| 기록되지 않은 추가 충돌 발견 | conflict resolve | merge를 abort하고 수동 확인 필요 오류를 반환한다. |
| pending 충돌 없음 | conflict resolve | branch를 변경하지 않고 해결할 충돌이 없다는 오류를 반환한다. |
| `--no-push` 지정 | sync | save·fetch·병합·검증까지 수행하고 remote ref는 변경하지 않는다. |
| 여러 프로젝트 중 하나 실패 | 전체 sync | 이전 프로젝트 결과는 유지하고 실패 위치를 보고하며 전체 원자 성공으로 표시하지 않는다. |
| remote 없음 또는 인증 실패 | sync | ref를 만들거나 변경하지 않고 식별 가능한 오류를 반환한다. |

## 수용 기준

- [ ] sync가 Workspace branch를 프로젝트 branch보다 먼저 처리한다.
- [ ] 변경 없는 동기화가 새 commit을 만들지 않고 로컬·원격 commit 일치를 보고한다.
- [ ] 원격 ref가 없는 프로젝트가 `publish-new`로 게시되고 양쪽 ref가 같은 commit을 가리킨다.
- [ ] 원격 단독 변경이 fast-forward되고 worktree와 태스크 projection에 반영된다.
- [ ] 로컬 단독 변경이 검증 후 같은 이름의 원격 ref로 push된다.
- [ ] 서로 다른 문서 또는 샤드의 양립 가능한 분기 변경이 merge commit에서 모두 보존된다.
- [ ] 단일 태스크의 서로 다른 필드 변경이 의미 병합에서 모두 보존된다.
- [ ] 같은 문서·파일 또는 태스크 필드 충돌 시 remote ref가 변경되지 않는다.
- [ ] 충돌 pending 기록이 project, ours, theirs와 파일 또는 필드별 충돌 정보를 포함한다.
- [ ] 공통 이력이 없는 branch와 강제 push가 자동 수행되지 않는다.
- [ ] 병합 후 strict 검사 실패 시 merge commit과 push가 생성되지 않고 로컬 유효 상태가 보존된다.
- [ ] conflict list가 정본이나 pending 파일을 변경하지 않는다.
- [ ] ours와 theirs 해결 전략이 각각 선택한 값을 반영하고 strict 검사 통과 후 pending을 제거한다.
- [ ] 기록되지 않은 문서 충돌이 해결 명령에서 자동 선택되지 않는다.
- [ ] `--no-push` 동기화 전후 remote ref가 동일하고 로컬 결과만 갱신된다.
- [ ] 인증·DNS·TLS 실패가 publish-new로 잘못 처리되지 않는다.
- [ ] 전체 sync의 부분 실패 결과에서 성공한 프로젝트와 실패한 프로젝트를 구분할 수 있다.
- [ ] watch의 중복 실행이 동일 프로젝트 lock으로 차단되고 종료 후 lock을 복구할 수 있다.
- [ ] JSON 결과에서 Workspace와 프로젝트별 action, commit, saved, pushed를 파싱할 수 있다.
- [ ] 동기화 완료 후 conflict list가 비어 있고 `rdl check --strict`가 오류 없이 통과한다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 데이터 안전성 | 자동 동기화가 원격 변경을 유실하거나 강제 push하지 않는다. | divergent·unrelated history fixture에서 원격 ref와 commit graph를 비교한다. |
| 원자성 | 단일 프로젝트 병합·검증 실패가 불완전한 merge commit을 남기지 않는다. | 병합과 검사 단계에 실패를 주입하고 HEAD·MERGE_HEAD·worktree를 확인한다. |
| 멱등성 | 변경 없는 sync 반복 실행 결과가 동일하고 새 commit이 없다. | 연속 3회 실행의 ref·commit·파일 hash를 비교한다. |
| 진단성 | 실패가 remote, branch, 단계와 충돌 대상을 식별할 수 있게 한다. | 오류 시나리오별 stderr·JSON·pending schema를 검사한다. |
| 복구성 | 충돌 상태를 프로세스 종료 후에도 조회·해결할 수 있다. | sync 실패 후 새 프로세스에서 conflict list·resolve를 실행한다. |
| 보안 | Git 자격 증명과 세션 비밀이 결과·pending·로그에 기록되지 않는다. | 비밀 marker를 사용한 credential fixture 결과 파일과 출력을 검색한다. |
| 성능 | 변경 없는 단일 프로젝트 로컬 단계가 일반 환경 2초 이내 완료된다. | 로컬 remote fixture에서 네트워크 시간을 제외한 95백분위를 측정한다. |

## 제외 범위

- Git remote 생성, 계정·권한 발급과 자격 증명 보관은 제공하지 않는다.
- 제품 소스 branch와 일반 개발 branch의 동기화·병합을 관리하지 않는다.
- 강제 push, 공통 이력이 없는 branch의 자동 결합과 원격 이력 재작성은 제공하지 않는다.
- 문자 단위 실시간 공동 편집과 중앙 잠금 서버는 제공하지 않는다.
- 문서별·필드별 대화형 충돌 선택 UI는 현재 제공하지 않으며 recorded set 전체에 ours 또는 theirs를 적용한다.
- 여러 프로젝트 branch를 묶는 분산 트랜잭션과 전체 rollback은 제공하지 않는다.
- remote 서비스의 가용성, 백업, 보존 정책과 서버 측 hook을 보장하지 않는다.
