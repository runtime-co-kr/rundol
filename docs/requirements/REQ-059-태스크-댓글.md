# 태스크 댓글

## 배경

두 세션이 같은 저장소에서 동시에 도는 것이 이미 일어나고 있다. 그런데 서로에게 말을 걸 수단이 없다.

2026-08-20 하루에 세 번 부딪혔다. 다른 세션이 진행 중인 태스크의 코드가 작업 트리에 있어 그대로 커밋했지만 그 사실을 알릴 자리가 없었다. 같은 제목의 태스크를 중복으로 만들었는데 상대가 만든 것을 볼 방법이 없었다. 미커밋 문서가 떠 있는데 손대도 되는지 물을 곳이 없었다.

지금 있는 소통 수단은 전부 다른 일을 위한 것이다. `rdl decision`은 선택지와 권고와 영향 범위를 요구하는 무거운 구조이고, 태스크의 반려 사유는 반려에만 붙으며, 문서 본문은 정본이라 논의를 담을 자리가 아니다. "이거 제가 커밋했습니다" 한 줄을 남길 곳이 없다.

Rundol은 사람 워커와 AI 워커를 같은 계층으로 두겠다고 말한다. 그런데 그 둘이 대화할 자리가 없었다.

## 요구사항

- 태스크에 서술 기록을 남기고 읽을 수 있어야 한다.
- 작성 주체가 사람인지 에이전트인지 구분되어 남아야 한다.
- 그 구분은 작성자가 주장하는 값이 아니라 등록된 Client 유형에서 파생되어야 한다.
- AI가 남긴 기록은 승인 근거 자격을 갖지 않아야 한다.
- 두 세션이 같은 태스크에 동시에 남겨도 사람이 충돌을 풀지 않아야 한다.

## 사전조건

- 작성자의 Client가 등록되어 있고 활성이다.
- 대상 태스크 식별자가 형식을 지킨다.

## 동작 규칙

1. 저장은 Workspace 이벤트 원장의 `comment` 종류에 append-only로 쌓는다.
2. 조각 파일은 작성 Client별로 갈린다. 그래야 두 세션이 동시에 써도 Git 병합이 그대로 푼다.
3. 작성 주체는 Client 유형에서 파생한다. `human`·`device`는 사람, `agent`·`service`는 에이전트다.
4. 모르는 유형은 에이전트로 본다. 사람으로 잘못 보면 승인 근거 자격을 잘못 주지만 에이전트로 잘못 보면 자격을 잘못 뺏을 뿐이므로, 덜 위험한 쪽으로 틀린다.
5. 승인 근거 자격은 작성 시점에 값으로 굳혀 저장한다. 읽는 쪽마다 다시 계산하면 규칙이 바뀔 때 지난 기록의 자격이 조용히 달라진다.
6. 본문 상한은 4000자다. 길어지면 태스크를 쪼개거나 결정으로 올린다.
7. 조회는 시각 순으로 정렬하고, 같은 시각이면 Client 식별자로 가른다.
8. 태스크를 지정하지 않은 조회는 어느 태스크에 논의가 있는지를 집계로 돌려준다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 활성 Client가 사람 유형 | 댓글 작성 | 저장되고 승인 근거 자격을 가짐 |
| 활성 Client가 에이전트 유형 | 댓글 작성 | 저장되되 승인 근거 자격 없음 |
| 등록되지 않은 Client | 댓글 작성 | 거절. 신원 없는 기록은 나중에 누구에게도 물을 수 없다 |
| 비활성 Client | 댓글 작성 | 거절하고 사유를 밝힘 |
| 본문이 비었거나 상한 초과 | 댓글 작성 | 거절하고 어느 쪽인지 밝힘 |
| 태스크 식별자 형식 위반 | 댓글 작성 | 거절 |
| 두 Client가 같은 태스크에 동시 작성 | 병합 | 조각이 갈려 있어 충돌 없이 합쳐짐 |

## 수용 기준

- [ ] 사람과 에이전트가 같은 자리에 남기되 자격이 갈린다.
- [ ] 작성자별로 원장 조각이 갈린다.
- [ ] 등록되지 않았거나 비활성인 Client가 거절된다.
- [ ] 조회 결과의 순서가 읽는 쪽과 무관하게 같다.
- [ ] 사람이 읽는 출력에서 본문과 작성 주체가 보인다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 판정 순수성 | 자격 판정이 값만 보고 이뤄지며 파일을 읽지 않는다 | 전이 의존 검사 |
| 동시 작성 | 두 Client의 동시 작성이 사람 개입 없이 병합된다 | 조각 파일 분리 확인 |
| 결정성 | 같은 원장이면 언제 읽어도 같은 순서 | 반복 조회 비교 |

## 제외 범위

- 문서에 대한 댓글은 다루지 않는다. 문서는 정본이라 논의가 붙으면 정본이 오염된다.
- 결정 요청과 응답은 `rdl decision`의 몫이다. 선택지가 있는 물음은 댓글이 아니다.
- 승인 판정 자체는 다루지 않는다. 여기서는 자격 여부만 값으로 남긴다.
- 알림·구독은 다루지 않는다.

## 기능별 설계 계약

### CMT-01

#### 입력

- 대상 태스크 식별자, 본문, 작성 Client 식별자, 선택적 구성원 식별자.
- 판정부는 여기에 Client 유형과 작성 시각을 값으로 더 받는다.

#### 출력

- 저장된 이벤트: 종류, 태스크, 본문, 작성 Client, 워커 종류, 구성원, 승인 근거 자격, 기록 시각, 정본 다이제스트.
- 조회: 시각 순 댓글 목록, 또는 태스크별 집계(건수, 사람·에이전트 내역, 마지막 시각).

#### 업무 규칙

- 작성 주체는 파생값이고 주장값이 아니다.
- 자격은 저장 시점에 굳힌다.
- 조각은 작성 Client별로 나눈다.
- 거절할 때는 아무것도 쓰지 않는다.

#### 상태와 전이

- 댓글은 상태를 갖지 않는다. 수정도 삭제도 없다 — append-only 원장에 쌓인 기록은 나중에 고치면 그 자체가 상충으로 잡힌다.
- 정정이 필요하면 새 댓글을 남긴다. 지난 기록을 지우는 것보다 정정한 사실이 남는 편이 낫다.

#### 권한과 승인

- 등록된 활성 Client면 남길 수 있다. 태스크 소유자가 아니어도 된다 — 남의 작업에 알릴 것이 있는 상황이 바로 이 기능이 필요한 상황이다.
- 남긴 것이 승인 근거가 되는지는 별개이며 작성 주체가 정한다.

#### 정상·오류·취소

- 정상: 이벤트가 원장에 쌓이고 저장 파일 경로와 내용이 돌아온다.
- 오류: 계약 위반은 사유 코드를 담은 예외로 알리고 아무것도 쓰지 않는다.
- 취소: 없다. 한 번의 append로 끝난다.

#### 감사 기록

- 댓글 자체가 원장 기록이다. 정본 다이제스트가 내용을 덮으므로 나중에 고치면 같은 식별자에 다른 다이제스트가 생겨 상충으로 드러난다.
- 작성 행위는 태스크 갱신 행위로 계측에 남는다.

#### 수용 기준

- [ ] 작성 주체가 Client 유형에서 파생된다.
- [ ] 에이전트 댓글의 승인 근거 자격이 거짓이다.
- [ ] 작성자별 조각 분리가 파일로 확인된다.
- [ ] 거절된 작성이 파일을 남기지 않는다.
