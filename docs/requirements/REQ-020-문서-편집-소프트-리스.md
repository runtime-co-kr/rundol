# 문서 편집 소프트 리스

## 배경

분산된 Client가 같은 문서를 동시에 편집할 때 충돌 가능성을 조기에 알리되, 만료된 잠금 때문에 작업이 영구 중단되어서는 안 된다.

## 요구사항

- 활성 Client는 존재하는 프로젝트 문서에 5분짜리 소프트 lease를 획득하고 같은 lease를 갱신하거나 해제할 수 있어야 한다.
- 시스템은 append-only JSONL 이벤트로 lease 이력을 보존하고 현재 유효 lease만 조회해야 한다.
- lease는 저장 권한이 아니라 **조율 신호**여야 한다. lease를 갖지 않은 주체의 문서 저장을 거절해서는 안 되며, 대신 어긋남을 저장 결과에 실어 알려야 한다.

## lease의 성격

lease는 잠금이 아니다. 유실 방지는 lease가 아니라 아래 세 층이 맡는다.

| 층 | 담당 | 어긋나면 |
|---|---|---|
| `baseRevision` 낙관적 동시성 | 남의 변경 위에 덮어쓰기 차단 | HTTP 409로 저장 거절 (REQ-022) |
| 브랜치 경계와 `pre-push` 훅 | 다른 역할의 파일 수정·푸시 차단 | 경계 위반으로 거절 |
| 태스크 의미 기반 병합 | 같은 태스크의 동시 변경 통합 | 병합으로 해소 |

lease가 이 층들을 대신하지 않으므로, lease를 저장의 전제 조건으로 삼지 않는다. 강제하면 편집 중 브라우저가 죽었을 때 남은 5분짜리 lease가 그동안 다른 주체의 저장을 통째로 잠근다. 만료를 기다리는 것 말고 손쓸 방법이 없는 이 상태가, lease가 막아 주는 어떤 위험보다 나쁘다. 그래서 어긋난 저장은 통과시키고 누구와 겹쳤는지를 알린다.

## 사전조건

- Workspace schemaVersion은 6 이상이고, Client는 `active` 상태이며 owner가 대상 프로젝트 멤버로 등록되어야 한다.
- 대상 `documentId`가 프로젝트 charter 또는 docs 아래 실제 Markdown frontmatter ID로 존재해야 한다.

## 동작 규칙

1. acquire는 문서에 유효 lease가 없을 때 새 `LEASE-*` 식별자를 만든다.
2. renew와 release는 같은 Client가 보유한 유효 lease에만 허용한다.
3. acquire·renew의 만료 시각은 사건 시각으로부터 5분 후이며 release의 만료 시각은 null이다.
4. 이벤트는 프로젝트와 Client별 `lease-<project>-<client>-NNNNNN.jsonl`에 추가하고 500건 또는 1MiB에 도달하면 다음 세그먼트를 사용한다.
5. 현재 lease 계산은 acquire/renew를 적용하고 release·force release·conflict 사건을 제거한 뒤 만료 시각이 지난 항목을 제외한다.

## 상태와 예외

| 현재 상태 또는 상황 | 사건 | 기대 상태 또는 동작 |
|---|---|---|
| 유효 lease 없음 | acquire | 새 lease와 `lease.acquired` 기록 |
| 다른 Client가 유효 lease 보유 | acquire | 보유 Client와 만료 시각을 포함한 충돌 오류 |
| 같은 Client가 유효 lease 보유 | renew | 동일 lease ID로 만료 연장 |
| 같은 Client가 유효 lease 보유 | release | `lease.released` 기록 후 활성 목록에서 제거 |
| 유효 lease 없음 또는 다른 Client 소유 | renew/release | 보유 lease 없음 오류 |
| lease 만료 | list | 활성 목록에서 제외 |
| 다른 Client가 유효 lease 보유 | 문서 본문 저장 | 저장은 성공하고 결과에 `leaseNotice`가 실린다 |
| 유효 lease 없음 또는 본인 소유 | 문서 본문 저장 | 저장은 성공하고 `leaseNotice`는 없다 |

## 수용 기준

- [ ] acquire 후 활성 lease가 1개이며 renew는 같은 lease를 유지하고 release 후 0개가 된다.
- [ ] 비활성 Client, 미등록 프로젝트 멤버, 없는 문서, 중복 acquire와 타 Client renew/release는 거절된다.
- [ ] 이벤트에는 projectId, documentId, clientId, memberId, leaseId, Git baseRevision, occurredAt, expiresAt이 기록된다.
- [ ] 다른 Client가 lease를 보유한 문서를 저장해도 거절되지 않고, 응답에 보유자와 만료 시각을 담은 `leaseNotice`가 실린다.

## 비기능 요구

| 품질 속성 | 기준 | 측정 방법 |
|---|---|---|
| 충돌 안전성 | 한 문서에는 동시에 하나의 유효 lease만 반환 | 중복 acquire 시나리오 |
| 복구성 | 만료된 lease는 별도 삭제 없이 조회에서 자동 제외 | 시간 주입 단위 테스트 |
| 감사성 | 이벤트를 append-only JSONL로 보존하고 파일명과 clientId 일치 검증 | 이벤트 파일 검사 |

## 제외 범위

- lease는 Git merge나 revision 충돌 해결을 대신하지 않으며 문서 본문 저장은 REQ-022의 동시성 규칙을 따른다.

## 기능별 설계 계약

### COL-02

#### 입력

- `action(acquire|renew|release)`, `project`, `documentId`, `clientId`.

#### 출력

- `{ project, documentId, clientId, leaseId, type, expiresAt, file, commit }` 또는 `{ project, leases }` 조회 결과.

#### 업무 규칙

- acquire만 새 lease ID를 만들고 renew/release는 현재 활성 lease ID를 재사용한다. 유효기간은 5분이다.

#### 상태와 전이

- 없음 → acquired → renewed(반복 가능) → released이며, 만료·force_released·conflicted도 활성 상태를 종료한다.

#### 권한과 승인

- 활성 Client의 owner가 대상 프로젝트 `project.md`의 멤버 블록이어야 하며 Client 본인만 renew/release할 수 있다.
- lease 보유는 문서 저장의 권한이 아니다. 보유자가 아니어도 저장은 통과하고 어긋남만 통보된다.

#### 정상·오류·취소

- 정상 사건은 JSONL에 추가되고 설정 저장 commit을 남긴다. 검증 실패는 사건을 추가하지 않는다. 사용자의 취소는 release로 표현한다.

#### 감사 기록

- `EVT-*` 이벤트 ID, 사건 유형, Git HEAD baseRevision, 발생·만료 시각과 세그먼트 파일이 감사 근거다.

#### 수용 기준

- `test/collaboration-store.test.js`와 `test/board-workspace.test.js`에서 acquire·list·renew·release 흐름과 Board lease API가 통과한다.
