# Rundol 0.40 마이그레이션

이 문서는 `0.39.x`에서 `0.40.0`으로 올릴 때 필요한 작업을 다룬다. **태스크 저장 파일은 이 판올림으로 바뀌지 않는다.** 태스크는 여전히 `status`를 저장하고, 코드가 읽는 시점에 워크플로 스텝으로 옮긴다.

바뀌는 것은 셋이다 — 진단 출력의 `rule` 필드, 문서의 기능 ID 표기, 그리고 없어진 진단 둘.

## 변경 요약

| 항목 | 0.39.x까지 | 0.40.0 |
|---|---|---|
| `rdl check --json` 진단의 `rule` 필드 | `{ document, functionId }` | **없음.** 제품이 남의 문서 번호를 들지 않는다 |
| 문서 frontmatter의 `diagnostics` | 없음 | **추가.** 문서가 자기 소관 진단 코드를 선언한다 |
| 원천 문서 안의 기능 ID | `HRN-02` (사람이 지은 접두) | **`FN-001`** (종류 두 글자 + 일련 세 자리) |
| 하위 산출물이 가리키는 기능 ID | `HRN-02` | **`REQ-033#FN-001`** (부모 + `#` + 서브) |
| `RDL-IMPL-009` 기능 ID 중복 정의 | 있음 | **없어짐.** 표기가 중복을 불가능하게 만든다 |
| `RDL-IMPL-011` 원천 없는 참조 | 있음 | **없어짐.** 같은 이유 |
| 태스크 상태값 | `todo` · `doing` · `waiting` · `review` · `done` · `cancelled` | **그대로.** 저장은 안 바뀐다 |
| 묶음 롤업의 `open` | 어휘 밖 일곱 번째 값 | **없어짐.** `unclaimed`가 받고, 섞인 묶음은 섞였다고 답한다 |
| 새 명령 | — | `rdl rule history` · `rdl rule bypasses` · `rdl rule dead` |

## 실행할 명령

**태스크에는 없다.** 저장 형태가 그대로이므로 판올림만으로 끝난다.

문서에는 자동 이관 명령이 **없다.** 아래 둘을 손으로 옮긴다.

### 1. 기능 ID 표기를 옮긴다

원천 문서(REQ)의 `functionIds`에서 사람이 지은 접두를 서브 표기로 바꾼다.

```yaml
# 전
functionIds:
  - HRN-02

# 후
functionIds:
  - FN-001
```

그 기능을 가리키던 하위 산출물(SCR · MOD · IFC · TST)에는 부모를 단다.

```yaml
# 전
functionIds:
  - HRN-02

# 후
functionIds:
  - REQ-033#FN-001
```

한 자리에서 한 표기만 받는다. 원천 문서 안에서는 부모가 자명하므로 `FN-001`이고, 그 밖에서는 `REQ-033#FN-001`이다. 둘 다 받으면 같은 기능을 가리키는 글자가 둘이 되고, 부모를 달아 없앤 중복이 표기 차이로 되돌아온다.

일련은 세 자리 이상이다. 자릿수를 열어 두면 `FN-1`과 `FN-001`이 같은 항목을 뜻하면서 문자열로는 다른 값이 된다.

종류는 대문자 두 글자이고 `FN`(기능) · `SC`(시나리오) · `AC`(수용조건) 셋이다. 정규 문서 유형이 세 글자이므로 두 글자면 서브가 문서 식별자로 읽힐 길이 없다.

**어긋난 표기는 `RDL-IMPL-003`이 잡는다.** 옮긴 뒤 `rdl check`를 돌려 남은 것을 찾는다.

### 2. 진단의 근거를 문서로 옮긴다 (해당하면)

이 저장소의 요구 문서가 진단 코드의 근거였다면, 그 사실을 이제 문서가 선언한다. Rundol 자신의 저장소는 옛 표 136건 중 132건을 요구 문서 16건으로 옮겼다.

```yaml
diagnostics:
  - RDL-ASSET-005
```

기능 ID는 함께 적지 않는다. 선언 문서 자신의 `functionIds`에서 파생하므로, 두 곳에 적으면 한쪽만 고쳐지는 날이 온다.

본문에 코드를 적는 것과 다르다. 본문의 코드는 설명이고 반례일 수도 있다. 소관은 기계가 읽는 칸에 적는다.

## 확인이 필요한 것

### `rdl check --json`을 읽는 자동화가 있다면

진단에서 `rule` 필드가 사라졌다. 그 필드는 진단 코드 136건에 이 저장소의 요구 문서 번호를 붙인 표에서 나왔고, **남의 저장소에서 검사를 돌려도 그 번호가 붙어 나갔다.** 없는 문서를 가리키는 근거는 근거가 아니라 오답이므로 걷어냈다.

같은 물음은 방향을 뒤집어 답한다. "이 진단의 근거는 어디인가"와 "이 요구를 고치면 어떤 검사가 흔들리는가"는 문서의 `diagnostics` 선언을 모아서 답한다.

### `RDL-IMPL-009` 또는 `RDL-IMPL-011`을 참조하는 문서나 도구가 있다면

둘 다 없어졌다. 규칙이 느슨해진 것이 아니라 **표기가 그 둘이 막던 것을 일어나지 못하게 만들었다.** `REQ-012#FN-001`과 `REQ-013#FN-001`은 같은 값이 될 수 없고, 하위 산출물은 부모를 적지 않고는 기능을 가리킬 수 없다.

적힌 부모가 실제로 그 기능을 선언했는지는 남는 물음이지만, 그것은 "원천이 없다"가 아니라 "가리킨 것이 해결되지 않는다"이며 참조 해결은 링크 계층이 답한다.

### 묶음 롤업을 읽는 자동화가 있다면

어휘 밖 값 `open`이 사라졌다. 아직 아무도 안 잡은 묶음은 `unclaimed`이고, **성취와 취소가 섞인 묶음은 답을 고르지 않고 섞였다는 사실을 내보낸다.** 예전에는 그것도 조용히 `open`이 되어, 안착한 묶음이 열린 것으로 보였다.

## 판정의 뜻은 바뀌지 않았다

무엇이 위반인지, 어느 전환이 허용되는지, 어떤 게이트가 면제될 수 있는지는 전부 그대로다. 상태 이름을 코드가 문자열로 비교하던 자리를 스텝으로 옮기고 흩어져 있던 규칙을 한 카탈로그로 모았지만, 그 카탈로그가 내는 답은 이관 전과 같다.

달라진 것은 한 번에 몇 개를 말하느냐다. 전에는 저장 게이트가 진단 중 첫 줄만 꺼내 던져서, 하나를 고치면 다음 것이 다시 막았다. 이제 막는 규칙을 전부 돌려준다.
