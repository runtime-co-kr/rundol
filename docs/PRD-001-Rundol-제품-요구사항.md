# 런돌 제품 요구사항

## 문제와 배경

IT 프로젝트의 요구사항, 설계 결정, 역할, 이해관계자, 태스크와 완료 조건은 여러 문서 도구와 이슈 관리 시스템에 흩어지기 쉽다. 이 상태에서는 코드 변경의 근거를 추적하기 어렵고, 담당자와 검토 책임이 누락되며, AI 코딩 클라이언트와 사람이 서로 다른 프로젝트 문맥을 사용하게 된다.

기존 도구는 중앙 서버나 특정 SaaS에 의존하거나, 문서 형식만 제공하고 문서 간 연결·책임·완료 조건을 지속적으로 검증하지 못하는 경우가 많다. 프로젝트 코드와 문서의 수명 주기도 달라 제품 브랜치에 관리용 파일을 섞으면 저장소의 소유 경계가 흐려진다.

Rundol은 Markdown과 JSON을 실제 파일로 보존하고, 프로젝트별 Git 브랜치와 linked worktree를 통해 제품 코드와 프로젝트 운영 자료를 분리한다. CLI가 공통 메타데이터, 책임 구조, 문서 연결, 태스크 상태와 품질 게이트를 검증하여 IDE, Obsidian, 로컬 Board와 AI 클라이언트가 같은 정본을 사용하게 한다.

## 사용자

| 사용자 | 목표 | 현재 불편 |
|---|---|---|
| 프로젝트 책임자·제품 담당자 | 목표, 범위, 책임과 진행 상태를 하나의 추적 가능한 체계로 관리한다. | 문서와 태스크가 분산되어 최신 상태와 최종 책임자를 확인하기 어렵다. |
| 개발자·설계자 | 구현 전에 요구사항과 설계 근거를 확인하고 코드 변경을 상위 목표까지 추적한다. | 문서 링크가 깨지거나 구현 세부사항과 결정 근거가 여러 위치에 중복된다. |
| 검토자·이해관계자 | 완료 조건과 증거를 기준으로 산출물을 검토하고 의사결정 이력을 확인한다. | 상태 표기만으로 실제 완료 여부와 검증 근거를 판단하기 어렵다. |
| AI 코딩 클라이언트·자동화 서비스 | 사람이 사용하는 것과 동일한 구조화된 프로젝트 문맥을 읽고 안전하게 갱신한다. | 도구마다 별도 지침과 비정형 문맥을 사용해 결과의 일관성과 추적성이 낮다. |
| 폐쇄망·로컬 우선 환경의 운영자 | 외부 서비스 없이 설치, 검증, 백업과 협업을 수행한다. | SaaS 의존성, 네트워크 제한과 데이터 반출 정책 때문에 기존 협업 도구를 쓰기 어렵다. |

## 목표와 성공 지표

| 목표 | 지표 | 기준값 | 목표값 | 측정 방법 |
|---|---|---:|---:|---|
| 프로젝트 문맥의 단일 정본 제공 | 등록 프로젝트 중 엄격 검증을 통과한 비율 | 측정 필요 | 100% | 프로젝트별 `rdl check --strict` 결과 집계 |
| 책임과 추적성 누락 방지 | 정규 문서의 필수 메타데이터·유효 링크 오류 수 | 측정 필요 | 0건 | `rdl check --strict` 진단 결과 확인 |
| 빠른 도입 | 기존 Git 저장소에서 첫 프로젝트 생성과 검증까지 걸리는 시간 | 측정 필요 | 5분 이내 | 새 환경에서 quick-start 시나리오 반복 측정 |
| 제품 코드와 운영 자료의 소유 경계 유지 | 초기화 후 제품 브랜치에 추가되는 Rundol 추적 파일 수 | 0건 | 0건 유지 | `git status`와 브랜치별 파일 목록 검사 |
| 설치·배포 신뢰성 확보 | 지원 설치 시나리오와 릴리스 검사 통과율 | 측정 필요 | 100% | `npm run release:check` 및 tarball 설치 테스트 |
| 로컬 우선 운영 보장 | 핵심 로컬 명령 중 외부 서비스가 필수인 명령 비율 | 0% | 0% 유지 | 네트워크 차단 환경에서 init, check, doc, task, board 검증 |

## 범위

### 포함

- 기존 Git 저장소에 Workspace와 첫 프로젝트를 생성하거나 원격 프로젝트를 연결하는 기능
- Workspace Registry, Client Registry와 프로젝트별 Git 브랜치·linked worktree 관리
- 프로젝트 헌장과 PRD, REQ, ARC, SCR, MOD, API, ADR, TST, RUN, GLS 문서의 표준 생성 및 검증
- 역할, 멤버, 이해관계자, RACI, 위험, 완료 정의를 포함한 프로젝트 거버넌스 계약
- 태스크 생성, 담당자·상태·완료 조건 관리와 문서 연결
- 로컬 검증, 저장, 원격 동기화, 충돌 탐지·해결 지원
- 프로젝트 탐색과 태스크 관리를 위한 localhost 전용 Board
- IDE, Obsidian과 AI 코딩 클라이언트가 같은 파일 기반 문맥을 사용하는 연동 방식
- 통합·개별 npm 패키지 설치, 진단, 버전 정합성과 릴리스 검증

### 제외

- 특정 조직의 업무 내용이나 문서 표현을 강제하는 기능. Rundol은 내용이 아니라 누락 방지와 추적 계약을 표준화한다.
- Git을 대체하는 자체 중앙 데이터베이스나 독점 저장 형식. 이식성과 로컬 우선 원칙을 유지하기 위해 Git과 일반 파일을 정본으로 사용한다.
- 범용 원격 협업 SaaS 제공. 원격 협업은 사용자가 선택한 Git remote를 통해 수행한다.
- 제품 소스 브랜치에 Rundol 런타임이나 프로젝트 문서를 강제로 커밋하는 방식. 제품 코드와 운영 자료의 소유 경계를 유지한다.
- 강한 실시간 공동 편집과 문자 단위 충돌 방지. Git 기반 임대와 병합은 제공하지만 범용 동시 편집 엔진은 범위에 포함하지 않는다.
- 프로젝트별 상세 구현 요구사항과 화면·API·데이터 설계. 해당 내용은 하위 REQ, SCR, API, MOD, ARC 문서에서 정의한다.

## 제약과 가정

- 지원 환경에는 Node.js 14 이상, npm 6 이상과 Git 2.20 이상이 설치되어 있다고 가정한다.
- Markdown, JSON, YAML과 Git ref가 정본이므로 파일·브랜치 계약의 하위 호환성과 마이그레이션 가능성을 유지해야 한다.
- 핵심 로컬 기능은 외부 runtime dependency나 상시 네트워크 연결 없이 동작해야 한다.
- 원격 fetch·push에는 사용자가 구성한 Git 인증과 네트워크가 필요하며, 인증·DNS·TLS 오류를 원격 브랜치 부재로 간주해서는 안 된다.
- Windows, macOS와 Linux에서 경로, linked worktree와 설치 동작이 일관되어야 한다.
- 사람과 AI 클라이언트가 동일 파일을 수정할 수 있으므로 원자적 쓰기, 엄격 검증, 충돌 기록과 복구 경로가 필요하다.
- 역할·멤버·이해관계자 분류와 정규 문서 메타데이터는 프로젝트 규모와 관계없이 생략하지 않는다.
- 일정과 예산은 현재 확정된 근거가 없으며 프로젝트 책임자가 별도로 결정한다.

## 제품 원칙

- 로컬 우선: 핵심 작업은 로컬 파일과 Git만으로 수행할 수 있어야 한다.
- 열린 정본: 사용자는 전용 애플리케이션 없이도 모든 프로젝트 자료를 읽고 복구할 수 있어야 한다.
- 명시적 책임: 문서와 태스크에는 담당자, 검토 관계와 완료 조건이 남아야 한다.
- 검증 가능한 계약: 규칙은 설명에 그치지 않고 CLI 검사와 자동 테스트로 확인할 수 있어야 한다.
- 분리된 소유권: 제품 코드, Workspace Registry와 프로젝트 자료는 각자의 브랜치 경계를 유지해야 한다.
- 도구 중립성: IDE, Obsidian, Board와 AI 클라이언트는 동일한 정본을 서로 다른 인터페이스로 사용해야 한다.

## 수용 기준

- 신규 Git 저장소에서 `rdl init` 실행 후 Workspace 및 프로젝트 브랜치와 linked worktree가 생성된다.
- 기존 원격 Rundol 프로젝트는 제품 브랜치 변경 없이 연결할 수 있다.
- 정규 문서와 태스크는 표준 ID, 메타데이터, 담당자와 관련 문서를 추적할 수 있다.
- 누락되거나 잘못된 메타데이터, 책임 구조, 링크와 완료 조건은 `rdl check --strict`에서 오류로 보고된다.
- 문서와 태스크 변경은 프로젝트 전용 브랜치에 저장되며 제품 브랜치의 추적 파일을 변경하지 않는다.
- 로컬 Board와 Obsidian, 지원 AI 클라이언트가 동일 프로젝트 파일을 읽을 수 있다.
- 동기화 충돌 시 원격 변경을 덮어쓰지 않고 pending 충돌 정보와 명시적 해결 절차를 제공한다.
- 지원되는 설치 조합과 릴리스 산출물은 자동 설치·버전·테스트 검사를 통과한다.
