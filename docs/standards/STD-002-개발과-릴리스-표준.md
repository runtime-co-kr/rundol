# 개발과 릴리스 표준

## 적용 범위

이 저장소의 소스, 시험, 문서, 릴리스에 적용한다. 사람이 쓰든 에이전트가 쓰든 같다.

적용되지 않는 것: 제품 도메인의 업무 규칙, 그리고 개인 작업 트리에서 커밋하지 않는 실험.

## 규칙과 근거

### 주석에 적은 통제는 통제가 아니다

- 규칙: 통제는 코드로 도달 가능해야 한다. 주석·문서가 약속한 검사는 그 검사가 실제로 존재하고 실행될 때만 통제다.
- 근거: 한 판에서 같은 실수를 두 번 했다. 환경 표시를 "난간이지 경계가 아니다"라고 적고 그 위에 공유 판정을 얹었고, "check가 대조한다"고 적고 그 check를 만들지 않았다. 둘 다 외부 검증에서 걸렸다.

### 만족될 수 없는 설정은 선언 시점에 거부한다

- 규칙: 설정 조합이 구조적으로 만족될 수 없으면 로드에서 거부한다. 런타임에 실패로 나타나게 두지 않는다.
- 근거: 런타임 실패는 정상 판정과 얼굴이 같다. 다양성 요구를 켰는데 어댑터가 하나뿐이면 결과가 계속 "사람 판단 필요"로 나오고, 켠 사람은 그것이 판정인지 오설정인지 알 수 없다.

### 확인하지 못한 것과 이상이 없는 것은 다른 값이다

- 규칙: 검사할 수 없었던 경우를 통과로 기록하지 않는다.
- 근거: 얕은 복제에서 append-only 검사가 "위반 없음"을 돌려주어 잘린 구간의 변조가 전부 무사통과했다.

### 실패는 원인을 삼키지 않는다

- 규칙: 실패 결과에 사유를 담는다. 코드만 남기지 않는다.
- 근거: 이름 없는 실패 셋을 진단으로 바꾸자 그중 하나가 직전에 넣은 패치의 TDZ 버그였다.

### 우회는 사유를 요구하고 저장하지 않는다

- 규칙: 통제를 지나가는 경로는 사유를 요구하고, 그 사유를 설정에 저장하지 않는다.
- 근거: 저장되는 우회는 한 번 켜면 계속 통한다. 매번 말하게 해야 우회가 예외로 남는다.

### 시험은 옳은 이유로 통과해야 한다

- 규칙: 새 방어를 넣으면 그 방어를 꺼서 대응 시험이 실패하는지 확인한다.
- 근거: 네 번 겪었다. 대상 밖 파일을 막는 검사를 껐더니 그 런은 전혀 다른 이유로 멈췄고, 시험은 그대로 통과했다.

### 픽스처가 무엇을 시켰는지 확인한다

- 규칙: 시험이 조종한 값이 실제로 대상에 전달됐는지 본다.
- 근거: 종단 시험이 스텁을 환경 변수로 조종했는데 그 값이 어댑터 allowlist를 넘지 못했다. 모든 통과가 기본값으로 돈 것이었다. 격리 worktree를 넣은 뒤에는 제어 파일이 gitignore라 또 안 넘어갔다.

### 이길 수 없는 경쟁을 단언하지 않는다

- 규칙: 결과가 타이밍에 달린 성질은 시험의 단언으로 쓰지 않는다.
- 근거: 고아 손자 종료는 성질이 아니라 경쟁이다. 단독 실행과 전체 게이트에서 결과가 달랐다. 비결정적 시험은 게이트가 아니다.

### 새 시험 파일은 러너에 등록한다

- 규칙: 시험을 만들면 전체 러너에 등록한다.
- 근거: 등록되지 않은 시험은 없는 시험이다. 실제로 미등록 파일이 여럿 있었다.

### 릴리스 판단은 release:check로 한다

- 규칙: `npm test`가 아니라 `npm run release:check`로 판단한다.
- 근거: 타볼 호환 시험이 `npm test`에 없어서, 게이트가 초록인 채로 배포가 CI에서 깨졌다.

### 교차 OS 결과를 보고 배포한다

- 규칙: 세 OS CI 결과를 확인하고 배포한다.
- 근거: 한 OS에서만 게이트를 돌리고 배포했더니 세 OS가 모두 실패했다.

### 태그는 커밋 뒤에 만든다

- 규칙: 작업 트리가 깨끗한 것을 확인하고 태그를 만든다.
- 근거: 스테이지에 남은 수정을 두고 태그를 걸어, 그 태그가 가리키는 커밋이 자기 릴리스 검사를 통과하지 못했다.

### lockfile은 재생성하지 않는다

- 규칙: 버전을 올릴 때 `package-lock.json`은 문자열만 바꾼다.
- 근거: 재생성했더니 workspace 패키지가 로컬 link 대신 registry 의존으로 기록되어, 아직 없는 버전을 요구하는 lockfile이 되었다.

### 이름을 바꾸면 이관 경로를 함께 만든다

- 규칙: 식별자·유형 이름을 바꾸는 변경은 옛 이름을 읽어 새 이름으로 옮기는 경로를 함께 낸다.
- 근거: 옛 이름을 오류로 읽으면 이름을 바꾼 것만으로 기존 프로젝트가 멈춘다. 유형을 더하는 것도 같다 — 모르는 유형이 빠졌다고 계약을 무효로 읽으면 안 된다.

### 계산할 수 있는 값은 저장하지 않는다

- 규칙: 이미 저장된 다른 값에서 결정되는 값은 필드로 두지 않고 읽을 때 계산한다.
- 근거: `implementationReadiness`는 `task.links`를 보고 정해지는데 저장된다. 링크가 나중에 바뀌어도 갱신 경로가 없어 조용히 어긋난다. 두 곳에 있는 하나의 사실은 언젠가 두 개의 사실이 된다.

### 새 필드는 그 값이 틀렸을 때의 정본을 함께 정한다

- 규칙: 필드를 더할 때 "이 값과 저 값이 다르면 어느 쪽이 사실인가"에 답한다. 답하지 못하면 그것은 필드가 아니라 파생값이다.
- 근거: 정본을 정하지 않은 채 늘어난 필드는 동기화 코드를 부르고, 그 코드는 다시 검증 코드를 부른다. 검증이 어려워지는 이유는 규칙이 어려워서가 아니라 같은 사실이 여러 곳에 있어서다.

### 사람이 입력하는 값은 그 사람만 아는 것으로 한정한다

- 규칙: 목적, 완료 조건, 책임자, 예외 사유, 문서의 책임 경계만 묻는다. 나머지는 원장과 Git에서 계산한다.
- 근거: 기계가 알 수 있는 것을 묻는 통제는 우회된다. 저장이 어느 태스크의 일인지도 런과 브랜치가 이미 아는 경우가 많다 — 그때 묻는 것은 확인이 아니라 요금이다.

### 관계는 한 방향만 저장한다

- 규칙: 역방향은 계산한다.
- 근거: 양방향을 저장하면 한쪽만 지운 상태가 만들어지고, 그 상태를 막는 검사가 또 하나 필요해진다.

### 막지 않는 통제는 세어서 보여 준다

- 규칙: 우회를 허용하기로 한 통제는 우회 횟수를 요약에 노출한다.
- 근거: 허용하는 대신 세기로 했는데 그 수가 경고 수십 개 사이에 묻히면 아무도 세지 않는다. 세지 않는 우회는 예외가 아니라 그냥 다른 길이다.

## 예시

### 확인하지 못함을 값으로 남기기 — 그대로 복사

```js
// 검사할 수 없었던 경우를 통과로 접지 않는다. checked:false와 사유를 함께 남긴다.
if (!canInspect) return { checked: false, reason: 'shallow-clone', violations: [] };
return { checked: true, reason: null, violations: found };
```

### 만족 불가능한 선언을 로드에서 거부 — 그대로 복사

```js
// 런타임 실패로 두면 오설정과 정상 판정이 같은 얼굴을 한다.
if (policy.requireDiversity && adapters.length < policy.quorum) {
  throw new Error(`${step.id}: 다양성 요구는 quorum(${policy.quorum}) 이상의 어댑터를 필요로 합니다.`);
}
```

### 방어가 실제로 막는지 확인 — 설명용

```bash
cp src/target.js /tmp/bak
sed -i 'N s/.*/  if (false) {/' src/target.js   # 방어를 끈다
node test/case.test.js                          # 실패해야 한다
cp /tmp/bak src/target.js
```

- 그대로 쓰면 안 되는 이유: 줄 번호와 조건문 모양이 파일마다 다르다. 끄는 방법은 매번 그 코드를 보고 정한다. 중요한 것은 절차이지 이 명령이 아니다.

### 하지 말 것

```js
// 주석이 통제를 약속하고 구현하지 않는다.
// 이 값의 신원 대조는 check가 한다(RDL-RUN-031).
if (event.basis === 'human-approval') accept(event);
```

- 무엇이 문제인가: `RDL-RUN-031`이 존재하지 않으면 이 코드는 아무 대조 없이 받아들인다. 그리고 주석을 읽는 사람은 대조가 있다고 믿는다. 실제로 이 형태가 두 판에 걸쳐 배포됐다.

## 예외와 승인

지킬 수 없는 경우가 있다는 것은 표준의 결함이 아니다. 예외를 인정하지 않으면 표준이 우회되고, 우회는 기록되지 않는다.

- 예외는 그 변경의 커밋 메시지에 사유와 함께 적는다. 별도 신청 절차를 두지 않는다 — 절차를 무겁게 하면 표준 자체가 우회된다.
- 릴리스 관련 예외는 CHANGELOG의 알려진 한계에 남긴다.
- 통제를 우회하는 예외는 사람 승인이 필요하고 그 승인은 원장에 남는다.
