# 문서 계획 계약 검증

## 목적과 범위

문서 계약의 정규화·검증·평가, CLI 경계, checkpoint/advisory 동작, Board revision 충돌, 설치 스킬과 CLI 문서 동기화를 검증한다. 범용 그래프 편집이나 자동 문서 본문 생성은 범위에 포함하지 않는다.

## 테스트 수준

| 수준 | 대상 | 책임 | 자동화 여부 |
|---|---|---|---|
| 단위 | profile 파싱·직렬화·추천 문맥·omission·결정성 | test/document-profile.test.js | 자동 |
| CLI 통합 | init, contract, doc create, strict/save/sync 경계 | test/document-contract.test.js 및 기존 CLI suite | 자동 |
| HTTP 통합 | contract 조회·plan·update·409·snapshot parity | test/board-workspace.test.js | 자동 |
| UI 정적 계약 | Settings 필드와 typed API 연결 | test/board-ui.test.js | 자동 |
| 자체 E2E | Rundol 프로젝트의 PRD → REQ → TST와 SCR 흡수 | 이 문서와 CLI 검증 결과 | 자동+수동 확인 |

## 기능별 검증 계약

### DCP-01

#### 사전 조건

- 빈 Git 저장소와 유효한 project key, profile 입력을 준비한다.

#### 입력과 데이터

- lean 기본값과 유효·무효 trait 및 정책 override 표본을 사용한다.

#### 실행 절차

- init을 실행하고 생성된 project.md 계약을 파싱한 뒤 동일 명령을 다시 실행한다.

#### 기대 결과

- 최초 실행은 완전한 schemaVersion 2 revision 1을 만들고 재실행은 계약을 변경하지 않는다.

#### 오류와 취소

- 알 수 없는 profile·trait·불완전 정책은 파일 생성 전에 실패한다.

#### 증거

- guided, document-profile, init 테스트와 생성 파일 비교 결과를 사용한다.

#### 수용 기준

- 모든 정규 유형이 정확히 한 정책 상태에 있고 rules·omissions가 결정적으로 채워진다.

### DCP-02

#### 사전 조건

- 유효한 계약과 서로 다른 present 문서 집합을 준비한다.

#### 입력과 데이터

- required, onDemand, disabled와 추천 문맥 누락 조합을 사용한다.

#### 실행 절차

- evaluator, contract show·next와 Board snapshot을 같은 입력으로 실행한다.

#### 기대 결과

- 세 표면의 revision·present·ready·violations가 같고 blocked는 빈 배열이다.

#### 오류와 취소

- unsupported schema는 읽기 전용 오류를 반환하고 문서를 변경하지 않는다.

#### 증거

- document-contract 및 board-workspace deep equality assertion을 사용한다.

#### 수용 기준

- 반복 평가 결과가 byte-equivalent JSON 의미를 유지한다.

### DCP-03

#### 사전 조건

- SCR disabled와 REQ 흡수 설정을 가진 프로젝트를 준비한다.

#### 입력과 데이터

- 필수 섹션 완전·누락, 대상 없음과 notApplicable 사유 표본을 사용한다.

#### 실행 절차

- contract check와 strict check를 각 표본에 실행한다.

#### 기대 결과

- 완전한 흡수는 통과하고 누락 대상·섹션은 정확한 omission 진단을 반환한다.

#### 오류와 취소

- invalid omission 저장은 원본 revision을 보존한다.

#### 증거

- document-contract와 document-profile 회귀 테스트를 사용한다.

#### 수용 기준

- 생략 유형의 필수 책임이 삭제되지 않고 지정 문서 또는 사유로 추적된다.

### DCP-04

#### 사전 조건

- 동일한 violation을 가진 advisory와 checkpoint 계약을 준비한다.

#### 입력과 데이터

- required 누락, disabled 문서 존재, omission 누락과 recommended 누락을 사용한다.

#### 실행 절차

- check, save와 sync를 각 강제 수준에 실행한다.

#### 기대 결과

- checkpoint의 비권장 위반만 persistence를 차단하고 recommended 누락은 경고다.

#### 오류와 취소

- 차단 시 원격 ref와 정본 파일이 변경되지 않는다.

#### 증거

- document-contract, check와 git 테스트 결과를 사용한다.

#### 수용 기준

- 경고와 차단의 경계가 세 명령에서 동일하다.

### DCP-05

#### 사전 조건

- revision이 같은 두 계약 변경 요청을 준비한다.

#### 입력과 데이터

- profile·enforcement·omission 변경과 stale baseRevision을 사용한다.

#### 실행 절차

- 첫 변경을 저장한 후 이전 revision으로 두 번째 CLI·Board 변경을 요청한다.

#### 기대 결과

- 첫 요청만 revision을 증가시키고 두 번째는 current 계약과 충돌을 반환한다.

#### 오류와 취소

- stale·invalid 요청은 기존 문서를 삭제·이동하거나 history를 손상하지 않는다.

#### 증거

- document-contract와 board-workspace 409 테스트를 사용한다.

#### 수용 기준

- 동시 변경이 조용히 덮어써지지 않고 변경 impact가 반환된다.

### HRN-01

#### 사전 조건

- 유효한 프로젝트, owner, 관련 문서와 구현 문서 유형을 준비한다.

#### 입력과 데이터

- 한 개 및 여러 개의 유효 function-id와 무효 ID·인덱스 제목 표본을 사용한다.

#### 실행 절차

- doc create를 실행하고 생성 frontmatter·경로·기능별 섹션을 검사한다.

#### 기대 결과

- bounded-v1·atomic-v1 메타와 모든 ID의 독립 유형별 필드가 생성된다.

#### 오류와 취소

- function-id 누락과 무효 입력은 ID 예약 외 정본 파일을 남기지 않는다.

#### 증거

- action, document-contract와 implementation-contract 테스트를 사용한다.

#### 수용 기준

- 여러 기능을 한 파일에 생성해도 각 기능이 단독 생성과 같은 필드 집합을 가진다.

### HRN-02

#### 사전 조건

- 완전한 독립 계약과 묶음·미확정·누락 변형을 준비한다.

#### 입력과 데이터

- 복수 독립 섹션, 기능 범위, 통합 행, 외부 규칙 위임과 결정 보류 문구를 사용한다.

#### 실행 절차

- 일반 strict와 `--implementation` 검사를 각각 실행한다.

#### 기대 결과

- 완전한 계약만 통과하고 묶음은 RDL-IMPL-004, 미확정은 기능별 오류가 된다.

#### 오류와 취소

- 진단은 파일을 수정하지 않으며 선언하지 않은 본문 기능도 오류로 보고한다.

#### 증거

- implementation-contract의 atomic, grouped, unresolved, type별 필드 테스트를 사용한다.

#### 수용 기준

- 기능별 명세 완전성이 문서 존재 여부와 분리되어 검증된다.

### HRN-03

#### 사전 조건

- REQ·TST와 acceptance를 연결한 새 구현 태스크를 준비한다.

#### 입력과 데이터

- 초기 템플릿과 모든 필드를 확정한 문서 두 상태를 사용한다.

#### 실행 절차

- acceptance를 완료하고 각 문서 상태에서 task done 전환을 시도한다.

#### 기대 결과

- 미확정 상태는 거부되고 완전한 기능 대응 상태만 done이 된다.

#### 오류와 취소

- 실패한 전환은 이전 task status와 원본 shard를 유지한다.

#### 증거

- action routing 테스트의 blockedDone과 성공 전환 assertion을 사용한다.

#### 수용 기준

- task의 implementationReadiness가 atomic-v1로 기록되고 기능별 TST 누락을 허용하지 않는다.

### HRN-04

#### 사전 조건

- functionIds를 가진 REQ와 대응·누락 TST 문서를 준비한다.

#### 입력과 데이터

- ready, TST missing, REQ missing과 인덱스 제목 표본을 사용한다.

#### 실행 절차

- contract trace와 implementation trace 검사를 실행하고 doc create로 인덱스 제목을 시도한다.

#### 기대 결과

- 기능별 ready·missing과 근거 문서를 계산하고 persistedIndex는 false다.

#### 오류와 취소

- 무원천 하위 문서와 별도 인덱스 생성은 오류이며 추적 파일은 생성되지 않는다.

#### 증거

- implementation-contract computed trace와 index artifact 테스트를 사용한다.

#### 수용 기준

- 추적 결과가 직접 ID에서 재생성 가능하고 별도 정본을 요구하지 않는다.

### HRN-05

#### 사전 조건

- main 코드 branch와 원격 HEAD 변형 및 Rundol worktree를 준비한다.

#### 입력과 데이터

- origin/HEAD가 main, master, trunk인 경우와 잘못된 project branch를 사용한다.

#### 실행 절차

- git boundary와 pre-push 입력 검증을 각 저장소에 실행한다.

#### 기대 결과

- 원격 표준 기본 브랜치를 감지하고 역할별 worktree와 동일 이름 push만 허용한다.

#### 오류와 취소

- branch mismatch, 교차 push와 삭제 push는 원격 변경 전에 실패한다.

#### 증거

- branch-boundary와 bootstrap 회귀 테스트를 사용한다.

#### 수용 기준

- 기본 브랜치 이름을 하드코딩하지 않으면서 rundol 전용 경계를 유지한다.

### HRN-06

#### 사전 조건

- 설치 가능한 Rundol 스킬과 연결된 샘플 프로젝트를 준비한다.

#### 입력과 데이터

- 문서 생성, 기능 구현, DESIGN.md 발견과 conflict 상태 시나리오를 사용한다.

#### 실행 절차

- 스킬 설치 후 workflow 명령 순서와 정적 계약 문자열을 검사한다.

#### 기대 결과

- 스킬이 2~4개 문맥, atomic-v1, 무인덱스, branch boundary와 check·sync 순서를 안내한다.

#### 오류와 취소

- conflict와 품질 오류에서는 완료·sync를 진행하지 않고 원본을 보존한다.

#### 증거

- skill-install, docs, CLI 문서와 structure 테스트를 사용한다.

#### 수용 기준

- 지원 AI 클라이언트의 설치본이 소스 스킬 해시와 일치한다.
