# 보드 문서 계획과 표시 설정 검증

## 목적과 범위

유형별 하부 요소 기본값과 프리셋 대체, 프로필 선택의 미리보기, `board.json` 상속과 표시 일관성을 검증한다. 문서 계약 자체의 Workspace 상속과 임의 kind 확장은 범위에서 제외한다.

## 테스트 수준

| 수준 | 대상 | 책임 | 자동화 여부 |
|---|---|---|---|
| 단위 | 기본 섹션, profile 정규화, 표시 설정 병합과 검증 | document-profile, board-presentation 테스트 | 자동 |
| HTTP 통합 | snapshot contract catalog와 presentation 결과 | board-workspace 테스트 | 자동 |
| UI 정적 계약 | 프리셋 미리보기, 하부 요소 표시, 저장값과 라벨의 분리 | board-ui 테스트 | 자동 |
| 브라우저 E2E | 계약 설정 화면, 문서 표시, 테마와 레이아웃 | 로컬 보드 | 자동+육안 |
| 자체 적용 | Rundol Workspace와 프로젝트 설정 및 문서 추적성 | CLI strict/structure | 자동 |

## 테스트 데이터와 환경

- 프로젝트 계약은 lean, checkpoint, SCR은 사용 안 함을 쓴다.
- Workspace `board.json`은 공통 한글 문구와 순서를 정의한다.
- 프로젝트 `board.json`은 최소 한 개 문구를 override하여 상속 우선순위를 검증한다.
- 자동 테스트는 임시 Workspace를 만들고 종료 시 정리한다.

## 통과 기준

- 문서 profile, 표시 설정, Board HTTP/UI 테스트가 통과한다.
- 실제 보드에서 프리셋 미리보기, 유형별 하부 요소와 상속된 문구가 확인된다.
- `rdl contract check`, `rdl check --strict`, `rdl check --structure`가 통과한다.
- REQ-011 연결 태스크의 수용 기준과 검증 링크가 완료된다.

## 기능별 검증 계약

### BRD-01

#### 사전 조건

- 모든 정규 유형의 템플릿과 contract catalog 조회 환경을 준비한다.

#### 입력과 데이터

- 실제 2단계 제목, 템플릿 누락 fallback과 사용자 정의 구성요소를 사용한다.

#### 실행 절차

- catalog를 조회하고 Board 추천 chip을 렌더링한 뒤 구성요소를 추가·삭제한다.

#### 기대 결과

- 템플릿 순서의 추천값과 자유 편집 결과가 중복 없이 분리된다.

#### 오류와 취소

- 빈 값과 중복 추가는 저장값을 바꾸지 않는다.

#### 증거

- document-profile, document-contract와 board-ui 테스트를 사용한다.

#### 수용 기준

- 모든 유형이 실제 추천 목록과 자유 추가·삭제 컨트롤을 제공한다.

### BRD-02

#### 사전 조건

- 유효한 schemaVersion 2 계약과 Board token을 준비한다.

#### 입력과 데이터

- 활성·사용 안 함 전환, 프로필 변경과 stale baseRevision을 사용한다.

#### 실행 절차

- Settings에서 상태와 구성요소를 편집하고 정상·stale 요청을 차례로 전송한다.

#### 기대 결과

- 프로필 선택은 화면에서만 반영되고 정상 저장은 revision을 증가시키며 stale은 409다.

#### 오류와 취소

- token 없음·무효 payload·stale 요청은 project.md를 변경하지 않는다.

#### 증거

- board-workspace HTTP와 board-ui DOM 계약 테스트를 사용한다.

#### 수용 기준

- 키보드 조작과 aria-live 상태 안내를 포함한 revision 안전 편집이 동작한다.

### BRD-03

#### 사전 조건

- 내장 기본값과 Workspace·프로젝트 board.json 조합을 준비한다.

#### 입력과 데이터

- 부분 label override, order 변경, 파일 없음과 잘못된 필드를 사용한다.

#### 실행 절차

- snapshot을 조회하고 사이드바·최근 문서·카드·상세 표시를 비교한다.

#### 기대 결과

- 프로젝트가 Workspace를, Workspace가 내장값을 덮고 모든 화면이 같은 label을 쓴다.

#### 오류와 취소

- 잘못된 설정은 파일과 필드를 포함해 실패하며 문서 ID·경로는 변하지 않는다.

#### 증거

- board-presentation, board-data, board-ui와 board-workspace 테스트를 사용한다.

#### 수용 기준

- 유효값과 상속 출처가 결정적으로 같고 화면별 표현 불일치가 없다.

### BRD-04

#### 사전 조건

- 프로젝트 루트에 DESIGN.md가 있는 fixture를 준비한다.

#### 입력과 데이터

- REQ·ARC·ADR·태스크로 이전 가능한 설계 내용과 cleanup dry-run을 사용한다.

#### 실행 절차

- strict와 structure를 실행하고 cleanup을 apply 없이 조회한다.

#### 기대 결과

- 비정본 경고와 수동 이전 후보를 반환하고 원본 파일을 보존한다.

#### 오류와 취소

- 승인되지 않은 자동 삭제·이동은 발생하지 않는다.

#### 증거

- structure와 check의 DESIGN.md 회귀 테스트를 사용한다.

#### 수용 기준

- 스킬과 CLI가 DESIGN.md 신규 생성을 안내하지 않고 책임별 정본 라우팅을 제공한다.

### BRD-05

#### 사전 조건

- atomic-v1 REQ·TST와 계산형 trace가 포함된 Board snapshot을 준비한다.

#### 입력과 데이터

- 모든 기능 ready 상태와 TST 하나가 누락된 상태를 사용한다.

#### 실행 절차

- Settings를 렌더링하고 각 snapshot의 구현 계약 요약을 비교한다.

#### 기대 결과

- atomic-v1, 묶음 금지, ready/전체 수와 별도 인덱스 없음이 표시된다.

#### 오류와 취소

- legacy 계약에서는 잘못된 준비 수를 표시하지 않고 요약을 비운다.

#### 증거

- board-ui 정적 계약과 board-workspace snapshot 테스트를 사용한다.

#### 수용 기준

- 기능 문서 변경 후 새 snapshot이 계산된 준비 수를 반영하며 파일 인덱스를 생성하지 않는다.
