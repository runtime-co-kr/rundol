# 보드 런 대기 조회와 사람 게이트 승인 검증

## 목적과 범위

BOP-03의 조회가 런 원장에 아무것도 쓰지 않는다는 것과, 승인이 활성 human Client·사유·현재 커서 사람 게이트를 모두 갖춘 요청에만 기록된다는 것을 검증한다. 갈래 판정 자체와 명령줄 승인은 각자의 문서가 검증하므로 여기서 다시 다루지 않는다.

| HTTP 통합 | 런 조회·승인 endpoint | 프로젝트 책임자 | 자동 |
| 원장 통합 | 승인 사건 기록과 커서 전진 | 프로젝트 책임자 | 자동 |
| 경계 | 자격·사유·하네스 표시 거부 | 프로젝트 책임자 | 자동 |

## 테스트 데이터와 환경

임시 Workspace에 프로젝트 하나와 사람 게이트를 가진 절차의 런 하나를 만든다. Client는 세 개를 등록한다 — 활성 human(활성 멤버 owner), 활성 device, 활성 멤버가 아닌 owner를 가진 human. Board는 고정 token으로 실행하고, 하네스 경로는 서버 실행 환경에 하네스 자식 표시를 넣어 검증한다. 각 시나리오 전후로 런 이벤트 파일을 읽어 비교하고 종료 시 서버와 임시 저장소를 정리한다.

## 통과 기준

- `node test/board-run.test.js`가 종료 코드 0이다.
- 승인 거부 시나리오 전부에서 런 이벤트 파일이 요청 전과 동일하다.
- 승인 성공 시나리오에서 기록된 사건이 사람 승인 근거를 지니고 커서가 다음 스텝으로 이동한다.

## 기능별 검증 계약

### BOP-03

#### 사전 조건

- 사람 게이트에서 멈춘 런과 세 종류의 Client를 가진 임시 Workspace, 고정 token으로 실행 중인 Board 서버가 준비된다.

#### 입력과 데이터

- 목록 조회: 프로젝트 key.
- 내막 조회: 프로젝트 key와 런 ID(있는 런 / 없는 런).
- 승인: 런 ID, 승인자 Client ID(활성 human / device / 비활성 멤버 owner), 사유(있음 / 빈 문자열), 세션 token(일치 / 불일치).

#### 실행 절차

- 런 목록을 조회하고 이벤트 파일을 기록한다. 이어서 자격·사유·token을 하나씩 어긋나게 한 승인 요청을 보낸 뒤, 마지막으로 모두 갖춘 요청을 보낸다. 하네스 표시를 넣은 서버로 조회와 승인을 각각 한 번씩 수행한다.

#### 기대 결과

- 조회는 waiting 갈래에 그 런을 human-gate 사유로 담고 원장을 바꾸지 않는다.
- 갖춘 요청만 200과 함께 사람 승인 사건을 남기고 커서를 전진시킨다. 나머지는 각각의 사유로 거부되고 이벤트 파일이 그대로다.

#### 오류와 취소

- 자격·사유·스텝·token·하네스 표시 위반은 런 도메인 함수에 닿기 전이든 후든 원장에 사건을 남기지 않는다. 요청이 중간에 끊겨도 부분 기록이 생기지 않는다.

#### 증거

- 테스트 로그, HTTP status와 JSON 본문, 각 요청 전후의 런 이벤트 파일 내용과 접힌 커서 값.

#### 수용 기준

- REQ-067의 조회 무부작용, 승인 자격, 사유 필수, 거부 경로의 상태 불변 기준을 자동 검증한다.
