# 프로젝트 멤버 등록 검증

## 목적과 범위

COL-03이 `project.md`의 `프로젝트 팀원` 절에 charter 계약을 만족하는 멤버 블록을 추가하는지, 거절 경로에서 원본을 보존하는지 검증한다. Client 등록과 lease 성립은 REQ-019·REQ-020이 담당하므로 여기서는 추가된 멤버가 Client owner로 받아들여지는 경계까지만 확인한다.

## 테스트 수준

| 수준 | 대상 | 책임 | 자동화 여부 |
|---|---|---|---|
| 단위 | 채번, 역할 검증, 블록 렌더링 | 구현·검증 담당 | 자동 |
| 통합 | 명령 실행부터 commit까지 | 구현·검증 담당 | 자동 |

## 시나리오

| ID | 사전조건 | 실행 | 기대 결과 | 우선순위 |
|---|---|---|---|---|
| COL-03-S01 | 멤버 2명 등록됨 | ID 없이 멤버 추가 | `MEMBER-003`으로 채번되고 블록이 마지막 멤버 뒤에 생긴다 | P1 |

| COL-03-S04 | `ROLE-009` 없음 | 그 역할로 추가 | 미등록 역할로 거절하고 파일이 원본과 같다 | P1 |
| COL-03-S05 | 정상 입력 | 이름을 공백으로 추가 | 필수 입력 누락으로 거절한다 | P2 |

## 비기능 검증

| 품질 속성 | 목표 | 환경 | 측정 방법 |
|---|---|---|---|
| 무결성 | 거절 시 `project.md`가 바이트 단위로 동일 | 임시 workspace | 실행 전후 파일 비교 |

## 테스트 데이터와 환경

임시 디렉터리에 workspace를 부트스트랩하고 프로젝트 하나를 연결한다. 기본 charter의 `ROLE-001`·`ROLE-002`와 초기 멤버를 사용하며 개인정보는 사용하지 않는다. 각 시나리오는 자체 임시 디렉터리에서 실행하고 종료 시 삭제한다.

## 통과 기준

- P1 시나리오가 모두 통과한다.
- 거절 경로 후 `project.md`가 원본과 같다.
- 추가된 멤버로 `rdl check --strict`가 오류 없이 통과한다.

## 기능별 검증 계약

### COL-03

#### 사전 조건

연결된 workspace와 프로젝트가 있고 `project.md`에 `프로젝트 팀원` 절과 `ROLE-001` 이상의 역할 블록이 존재한다.

#### 입력과 데이터

이름, 소속, 업무 계정, 책임 영역, 역할 목록을 정상값으로 준비한다. 거절 검증용으로 기존 멤버 ID, 존재하지 않는 역할 `ROLE-009`, 공백 이름을 사용한다.

#### 실행 절차

임시 workspace를 만들고 프로젝트를 연결한다. 정상 입력으로 멤버를 추가하고 결과 ID와 파일 내용을 확인한다. 이어서 중복 ID, 미등록 역할, 공백 이름으로 각각 추가를 시도하고 매번 파일이 바뀌지 않았는지 비교한다. 마지막으로 추가된 멤버를 owner로 Client를 등록한다.

#### 기대 결과

정상 입력은 다음 번호로 채번된 블록을 만들고 다섯 필수 필드를 모두 포함한다. 블록은 `프로젝트 팀원` 절 안에 있으며 다른 절은 변하지 않는다. 거절 경로는 오류를 던지고 파일을 그대로 둔다. 추가 후 `rdl check --strict`가 오류 0으로 통과하고 Client 등록이 성공한다.

#### 오류와 취소

중복 ID는 이미 존재한다는 메시지로, 미등록 역할은 해당 역할을 찾지 못했다는 메시지로, 공백 이름은 필수 입력 누락으로 거절한다. 어떤 실패에서도 commit을 만들지 않는다.

#### 증거

테스트 실행 결과와 각 시나리오의 단언이 증거다. 원본 보존은 실행 전후 파일 내용 비교로 남긴다.

#### 수용 기준

- 자동 채번이 기존 최대 번호 다음 값을 사용한다.
- 생성된 블록이 charter 필수 필드 다섯 개를 모두 갖는다.
- 세 가지 거절 경로가 각각 파일을 바꾸지 않는다.
- 추가된 멤버로 Client 등록이 성립한다.
