# 문서 리비전 제출 검증

## 목적과 범위

REQ-074#FN-001이 제출을 승인 원장의 두 번째 사건 종류로 남긴다는 것과, 그 사실에서 파생하는 제출 축이 편집·재제출·승인에 따라 규칙대로 갈린다는 것을 검증한다. 함께 본다: 에이전트 Client의 제출이 성립하는가, 제출이 문서와 신뢰 상태를 건드리지 않는가, 위조된 제출이 인가에서 떨어지고 바꿔치기한 줄이 원장 검증에서 잡히는가, 버전 번호가 저장되지 않고 원장에서 계산되는가.

승인 자체의 인가 판정과 승인본 대비 제출본 차분은 각자의 문서가 검증하므로 여기서 다시 다루지 않는다. 차분은 이 문서에서 상태가 갈리는지를 보는 데 필요한 만큼만 스친다.

## 테스트 데이터와 환경

임시 Workspace 하나에 프로젝트 하나를 만들고 형상 저장소로 초기화한다. Client는 둘을 등록한다 — 활성 에이전트 Client와 활성 사람 Client이며, 둘 다 소유자가 이 프로젝트의 활성 멤버다. 문서 하나를 만들어 커밋하고 한 번 승인한 뒤 본문을 고쳐 커밋해 낡음 상태를 만든 것이 제출 시나리오의 출발점이다.

형태 검증과 인가 시나리오는 파일을 거치지 않고 사건 객체를 직접 만들어 정규화와 접기에 넣는다. 그 사건에는 고정된 식별자와 두 개의 고정 리비전 값을 쓴다. 원장 바꿔치기 시나리오는 이벤트 샤드 파일 내용을 읽어 두었다가 조작해 검사한 뒤 원본 내용으로 되돌리고 다시 검사한다.

개인정보는 쓰지 않는다. 멤버와 Client는 시험용 식별자이며 외부 의존성은 형상 관리 실행 파일 하나뿐이다. 종료 시 임시 Workspace를 통째로 지운다.

## 통과 기준

- `node test/approval.test.js`가 종료 코드 0이다.
- 제출 시나리오 전후로 대상 문서의 파일 내용과 리비전이 같다.
- 제출 전후로 그 문서의 신뢰 상태 값이 같다.
- 위조 명의 시나리오 전부에서 그 제출이 접기 결과에 없고 진단이 남는다.
- 바꿔치기한 원장에서 검사가 오류를 내고, 원본으로 되돌리면 오류가 0이다.
- 사실을 더하지 않는 재제출 전후로 이벤트 파일 줄 수가 같다.

## 기능별 검증 계약

### REQ-074#FN-001

#### 사전 조건

- 임시 Workspace 하나, 형상 저장소로 초기화된 프로젝트 하나, 커밋된 문서 하나, 활성 에이전트 Client와 활성 사람 Client가 준비된다.
- 그 문서는 한 번 승인된 뒤 본문이 고쳐지고 커밋되어 신뢰 상태가 낡음이다.
- 형태·인가 시나리오용으로 고정된 사건 객체 하나와 그것을 판정할 인가 컨텍스트가 준비된다.

#### 입력과 데이터

- 제출 호출: 프로젝트 키, 문서 식별자, Client 식별자(활성 에이전트 / 등록되지 않은 것), 명의(그 Client의 소유자 / 다른 멤버 / 멤버 형식이 아닌 값), 사유(있음 / 없음).
- 사건 객체: 종류(제출 / 승인 / 알 수 없는 값), 승인 근거 칸의 유무, 위임 칸의 유무, 리비전 값 두 가지.
- 문서 편집: 제출 뒤 본문에 덧붙이는 한 줄.
- 원장 조작: 제출 줄의 사유만 바꾸고 봉투 다이제스트는 그대로 둔 이벤트 샤드.

#### 실행 절차

- 먼저 사건 객체로 형태 검증과 접기를 확인한다. 승인 근거·위임·잘못된 명의·알 수 없는 종류를 하나씩 넣어 거부를 보고, 승인 사건과 제출 사건을 섞어 한 번 접어 두 이력이 함께 나오는지 본다.
- 이어서 임시 Workspace에서 제출, 같은 리비전 재제출, 문서 편집, 재제출, 승인, 승인 뒤 제출을 순서대로 수행한다. 각 단계마다 신뢰 상태·제출 축·버전 번호·문서 리비전·이벤트 파일 줄 수를 기록한다.
- 그다음 제출 축으로 거른 문서 상태 조회와 문서 이력 조회를 수행한다.
- 마지막으로 이벤트 샤드의 제출 줄을 바꿔치기해 작업공간 검사를 돌리고, 원본 내용으로 되돌려 다시 검사한다.

#### 기대 결과

- 제출은 사건 하나를 남기고 제출 축만 옮긴다. 신뢰 상태와 문서 리비전과 파일 내용은 그대로다.
- 사실을 더하지 않는 제출은 사건을 남기지 않고 지금 상태를 돌려준다.
- 편집은 제출 축을 흔들림으로 옮기면서 앞서 제출된 리비전을 남긴다. 재제출이 검토 대기로 되돌리고 작은 자리 번호를 올린다. 승인이 판정됨으로 옮기면서 큰 자리를 올리고 작은 자리를 0으로 되돌린다.
- 승인 근거·위임·잘못된 명의·알 수 없는 종류는 형태 검증에서 거부된다.
- 등록되지 않은 Client와 소유자가 아닌 명의의 제출은 접기에서 채택되지 않고 진단으로 남는다.
- 바꿔치기한 제출 줄은 작업공간 검사가 잡고, 되돌리면 오류가 0이다.
- 제출 축으로 거른 조회가 그 상태의 문서만 내고 네 값의 셈이 0을 포함해 실린다.

#### 오류와 취소

- 비활성 Client, 소유자가 아닌 명의, 없는 문서 식별자, 알 수 없는 필드, 알 수 없는 사건 종류는 원장에 줄을 남기지 않는다.
- 접기에서 거부된 사건은 다른 사건의 판정을 무너뜨리지 않는다. 같은 원장의 나머지 승인과 제출은 그대로 선다.
- 취소 조작은 없다. 올린 것을 내리는 경로가 없으므로 그 경로의 시험도 없다. 잘못 올린 것은 고쳐서 다시 올리는 것으로 대신하며, 그때 앞선 줄은 이력으로 남는다.

#### 증거

- 시험 로그와 종료 코드.
- 각 단계의 문서 상태 응답 — 신뢰 상태, 제출 축의 상태와 리비전과 명의, 버전 번호, 문서 리비전.
- 접기가 낸 진단 코드 목록과 채택된 제출 이력의 크기.
- 이벤트 샤드 파일의 조작 전후 내용과 각각에 대한 작업공간 검사의 오류 수.
- 문서 이력 응답에 실린 제출 이력의 명의·사유·순서.
