# Rundol Project Governance

Treat lightweight delivery as an implementation choice, never as permission to remove governance or silently bypass the document contract.

## Start here

- Run `rdl context --json` before exploring the repository. One call returns the workspace, current branch, diagnostics, open tasks, and the next actions computed from that state. Read it instead of working the state out from files.
- When a command or flag is unknown, run `rdl help --json`. It is derived from the CLI's own usage text, so it cannot drift; never read the CLI source to discover a command or its flags.
- Run `rdl run pending --json` when you start and whenever you are about to pick up new work. It answers "what is waiting for someone right now" across every project in the workspace, in one call, and prints nothing when nothing is waiting. A run outlives your session — the ledger is recomputed on every read — so work you left halted last time is still there, and nobody else will notice it for you.
- Claim a task before changing canonical documents or code. `rdl task list --open --json` to see what exists, `rdl task set <TASK-ID> --status doing --owner <MEMBER-ID>` to take it, or `rdl task add` when none fits. Record evidence with `rdl task acceptance <TASK-ID> <AC-ID> --done` as it lands, and set `--status done` only after `rdl check --strict` passes and the change is synced. Working without a task is an exception you state out loud, not a shortcut you take quietly.

## Decisions that need a human

Ask before doing any of these, and record the answer where the work lives — a decision that exists only in chat did not happen. Everything else you decide yourself and report.

- Anything that leaves this machine or is hard to undo: pushing to a shared branch, creating a release tag, publishing a package, deleting or replacing a canonical document.
- Anything that changes what governance permits: contract `enforcement`, policy states, procedure overrides, or the version number of a release.
- Anything that overrides another client's authority: a `--force` takeover or conflict resolution, or cancelling a task someone else owns.
- Anything the request did not cover: a scope change, a new dependency, or a second problem discovered mid-work.

Do not ask what the tools already answer. If `rdl check` decides it, run the check instead of asking; if a safe default exists, take it and say which one you took. A long question list is a defect in the defaults, not diligence.

## Runs and assignments

A run binds a goal, its steps, its gates and its outcome under one `RUN-ID`. Progress is not stored — the ledger is append-only and every read folds it again — so a run survives a session ending, a crash, or a different machine picking it up. That is the point: you are not the thing that keeps the work alive.

Start one with `rdl run start <procedure> --project <key> --client-id <id>`, naming the task or artifact it serves; `rdl run procedures --json` lists what you may start. A run that stopped is resumed with `rdl run resume` — read the halt reason `rdl run pending` printed first, because most reasons need the underlying problem fixed before the cursor will move, and `--grant-attempts` exists for exhausted retry budgets, not for skipping the failure.

**The execution unit is decided by the procedure, not by preference.** `rdl run drive` refuses any procedure that is not pinned `idempotent: true`, so it cannot run authoring at all.

- **Authoring** (`document.authored`, `idempotent: false`) — walk it yourself. `rdl run next --run <RUN-ID> --project <key> --json` returns the cursor step and how to execute it; report completion with `rdl run step`, and let `rdl run gate` run gate steps so the exit code decides, not your reading of the output. Authoring is not idempotent because what to write — type, title, single responsibility, exclusions — is human intent, and a procedure must not invent it.
- **Verification** (`document.verified`, `idempotent: true`) — `rdl run drive` carries it from the canonical cursor to the next explicit boundary in one call. It pins the revision at run start and requires a clean worktree, so do not author into the same run.

Do not report a step you did not perform, and never pass `--force` to move a cursor you could not move honestly — a forced step is recorded and blocks sync until a human resolves it.

**Human gates stop you, and that is the design.** `rdl run approve` accepts only a `human` Client; your agent credential is refused there by contract, not by accident. When `rdl run pending` shows `human-gate`, surface it to the person with the command it printed. Do not look for a way around it.

**Ownership only moves between machines.** A run is owned by the Client that drives it, and `rdl run takeover` is automatic only when the previous owner is visibly halted. You do not need a handoff to resume your own machine's work — use the same Client and the process lock keeps two drivers apart. Reach for `--force --reason` only when a machine is genuinely gone; a forced takeover recorded for routine reasons destroys the signal it exists to carry.

Assignments are how work leaves the person who planned it. `rdl assignment issue` binds a goal, acceptance criteria, function IDs, the paths a worker may change, and a pinned procedure digest; the issuing side refuses overlapping paths so two workers never edit the same files. Workers submit with `rdl assignment report` and the controller runs `rdl assignment verify`. Acceptance and verification are separate questions — a malformed report is refused at intake, a well-formed report that fails its criteria is rejected at verification — so never collapse the two when you explain a result. `rdl assignment list --open --json` shows what is outstanding.

Human and agent workers use the same commands and the same judge. Your worker identity is derived from your registered Client type; do not claim it, and do not ask for a way to claim it.

## Workflow

1. Run `rdl init --json` first. Treat `created`, `already-connected`, `attached`, and `repaired` as connected states; select explicitly for `needs-selection`; stop on `conflict`. Read the returned `boundary` and run `rdl git boundary --project <key> --json`; do not continue while it reports violations.
2. For a new project, select a profile with guided setup or `--profile`. New projects always receive schemaVersion 2 `documentProfile`; never create an unconfigured project.
3. Before planning documents, run `rdl contract show --project <key> --json` and `rdl contract next --project <key> --json`. Read `catalog.granularity.typeResponsibilities` and `splitWhen` before choosing artifact boundaries. The CLI evaluator is authoritative; do not duplicate or reinterpret its rules in the skill.
4. Preserve every regular type (`PRD`, `REQ`, `ARC`, `SCR`, `MOD`, `API`, `ADR`, `TST`, `RUN`, `GLS`) in exactly one policy state, and preserve `enforcement`. The four states are distinct: `required` is a violation when missing, `recommended` warns when missing, `onDemand` is never diagnosed either way, and `disabled` means the project does not create that type at all — `rdl doc create` refuses it and an existing document of that type is a violation.
5. Never create a disabled type. Treat `recommendedContext` from `rdl contract next` as authoring guidance, not as a creation or persistence gate; it is a shipped constant, not project state, and it appears only for types you have not created yet. A present type is not proof that its subject area is complete; never satisfy the contract by creating one catch-all document per type.
6. In a Rundol-governed project, never create or use a generic `DESIGN.md` as a canonical source of truth. Route product and quality intent to `REQ`, UI flows and states to `SCR`, system structure to `ARC`, important decisions to `ADR`, and implementation work to `rdl task add`. If one of those types is disabled, raise the gap with the owner instead of creating `DESIGN.md`; do not smuggle the content into an unrelated type.
7. Fill the sections the contract expects for each type. `rdl contract show --json` reports them per profile in `catalog.profileChoices[].sections`, and `rdl doc create` scaffolds from the same list. A team may extend or replace the list per type in `board.json`; anything it does not set keeps the shipped default. These sections are authoring structure, not a gate — a heading with nothing under it satisfies no one.
8. Contract changes are explicit revisioned operations. Inspect `rdl contract plan` impact before `rdl contract set` or Board settings changes; do not delete or move existing documents as a side effect.
9. Read `references/governance-contract.md` before creating or revising project documents. Read `references/client-compatibility.md` only when installing or adapting the skill for another AI client.
10. Preserve the project charter's mission, goals, scope, roles, members, stakeholders, RACI, decisions, risks, cadence, and Definition of Done. Unknown information remains `미정` with an owner and follow-up task.
11. Use real Obsidian file names and block IDs for owners, reviewers, stakeholders, related artifacts, and task responsibility.
12. Before creating a document, enumerate candidate responsibilities and split them when owner or approver, acceptance criteria, lifecycle or review cadence, or primary consumers differ. Keep one primary responsibility per artifact; summaries link to narrower artifacts instead of duplicating their normative content.
13. Create documents only through `rdl doc create <TYPE> <title> --owner <MEMBER-ID> --scope <single-review-unit> --exclude <adjacent-out-of-scope>`, repeating `--exclude` when useful and adding required `--related` artifacts. For `REQ`, `SCR`, `MOD`, `API`, and `TST`, repeat `--function-id <FUNCTION-ID>` for every implemented function. The CLI-authored `bounded-v1` and `atomic-v1` metadata are mandatory for new implementation documents. Use canonical paths and review `rdl doc migrate` before applying a legacy move.
14. A file may contain several function IDs, but a specification must never group them. Reject ranges, combined rows, shared placeholder prose, shared acceptance criteria, or one test standing in for several functions. Every function ID must have the same complete type-specific contract it would receive in a standalone document. Keep the function ID as the atomicity and coverage axis even when a `TST` is written from a screen — a screen composes many functions, so organizing tests by screen makes one function change ripple across documents. A `TST` still relates to `REQ`; when a function it verifies also has an `SCR`, it must reference that `SCR` too (`RDL-IMPL-018`), and screenless functions stay verifiable through `REQ` alone. When an `SCR` is in scope, take the test's `입력과 데이터` from its `바인딩`, its `실행 절차` from `사용자 흐름`, and its `기대 결과` from `상태`/`전이` — `RDL-IMPL-006` rejects an unfilled placeholder but not a vague sentence, so "a valid value is entered and it succeeds" passes the check and fails as a test.
15. Never create an INDEX, catalog, document list, or traceability-matrix artifact. Use direct document links and `rdl contract trace --project <key> --json`; traceability is a computed view, not another source of truth.
16. Read `catalog.diagrams` from `rdl contract show --project <key> --json` before authoring a type it covers. A `MOD` document carries a Mermaid `erDiagram` inside its `관계` section. The diagram is a derived view: tables stay canonical for cardinality, field constraints, and lifecycle, and the document states that precedence. Give attributes a type and `PK`/`FK` key only — never restate constraints, defaults, or lifecycle in attribute comments, because those belong to the entity table alone.
17. Decide every diagram element with `catalog.diagrams.conventions.<TYPE>.selection`, one question per element. Entity: does this document own the lifecycle? Owned entities show attributes, adjacent entities are bare nodes linked to their owning document, and needing several owned entities means checking for a dependent aggregate before splitting the document. Relationship: does a stored field create the reference? Draw only references stored as a foreign key or identifier, and leave relationships that exist only after replay or computation to their calculation section. Cardinality: is the constraint enforced at write time or at read time? A relationship line carries the stored cardinality only, so a read-time limit such as "at most one currently valid" stays in the invariant or calculation section. Never label a line with a derived concept while drawing its stored cardinality; that mixes the two clocks in one statement. State transitions have no place in relational notation and stay in the per-function 상태와 전이 contract.
18. A `SCR` document carries a Mermaid `flowchart` inside its `전이` section, canonical in the transition table above it, and lists only the moves that leave this screen — inbound moves belong to the screen that starts them. Every node is an `SCR` identifier: moving to another screen is a transition, changing what the current screen displays is a state, and a login failure rendering an error is the second even though it reads as a branch. Label an edge with what decides the move only; error copy, validation rules, permission differences, and timeouts stay in `바인딩` and `디자인에 없는 것`. A walked path with an expected result is a `TST` scenario, not a transition. Never recover the transition graph from scenarios — they walk representative paths, so any unwalked edge vanishes silently.
19. A `TST` carries specification only. Its `시나리오` section is a table whose first column is an ID (`RDL-SCENARIO-001`), unique within the document (`RDL-SCENARIO-003`) and shaped as a referenceable token — letters first, no spaces or separators, 32 characters or fewer (`RDL-SCENARIO-002`). Execution records address a scenario as `TST-017#S-03`, so a scenario written as a bullet has nowhere for a result to attach. Do not unify ID spelling across documents: the document identifier already precedes it, and referencing needs stability and uniqueness, not uniformity. Never put checkboxes in `통과 기준` (`RDL-SCENARIO-004`) — pass criteria state what must be true, and whether this run actually passed belongs to the execution record. A checkbox in a canonical document claims a result nobody maintains, and re-running then means editing the source of truth, which erases the history of what failed last time.
20. Never author a diagram spanning several documents. Run `rdl contract diagram --project <key> --json` to compute the merged data and screen views, and `--write` to place them in the Vault's Git-ignored `views/` for Obsidian. Composites are derived, never canonical, and never committed; fix the source document and regenerate. `rdl check` runs the same composition, so `RDL-COMPOSE-001` (two documents claiming attributes on one entity), `RDL-COMPOSE-002` (a transition pointing at a screen that does not exist), and `RDL-COMPOSE-003` (a generated view that no longer matches the canonical documents) surface without asking. Never fix `RDL-COMPOSE-003` by editing the generated file — that is the drift it detects.
21. Use `rdl task list`, `rdl task add`, `rdl task set`, `rdl task acceptance`, and the Board for tasks. A task carries a `kind`: `normal` by default, or `test` for an execution that walks a `TST` document's scenarios — a test task must link the `TST` it verified (`RDL-TASK-029`) and is exempt from the implementation-readiness gate, because it implements nothing. A test task also carries a `result` (`pass`/`fail`/`blocked`/`skipped`), which is a different axis from `status`: a failed test is still a completed run, so it is `done` with `result: fail`. Never fold the verdict into the status — collapsing them makes "confirmed failing" and "not yet run" the same value, and aggregating tests by outcome stops being possible. Finishing a test task requires the verdict (`RDL-TASK-028`); cancelling it does not, because a cancelled run was never performed. Every test task also carries a `round`: a project-wide integer starting at 1, with exactly one task per `(TST document × round)` (`RDL-TASK-029`, `RDL-TASK-030`, `RDL-TASK-032`) — a cancelled task releases its slot. Never store a list of what a round covers: the tasks you created are the round's scope, and `rdl test rounds --round <n>` computes which `TST` documents were left out. A stored list becomes a second source of truth that silently disagrees with the tasks. Re-running is not a new task — the same task's verdict changes, and each defect found becomes its own normal task linked as a predecessor, because the defect list is what a test report is actually made of. Route only the 2–4 most relevant documents into an AI coding context.
22. Before implementation, run `rdl check --strict --implementation`. Do not implement while a linked function has unresolved rules or lacks an independent TST contract. Run `rdl check <ARTIFACT-ID> --strict` immediately after authoring, then `rdl contract check --project <key>` and `rdl check --strict`. Advisory findings guide the work; checkpoint violations block save, sync, and completion.
23. Run `rdl check --structure`; treat an existing `DESIGN.md` as a manual migration candidate and never delete it automatically. Apply cleanup only after reviewing every candidate.
24. Keep branch roles strict: application code belongs to the repository root's current code branch while the repository default is discovered from `origin/HEAD` (`main`, `master`, or a custom standard); project documents and tasks belong only to `rundol/<project-key>` through its linked worktree; registries, clients, leases, and Workspace presentation belong only to `rundol/workspace`. Never edit another role's files from the current worktree. Task and document state lives on `rundol/<project-key>`, so it never travels inside a code branch's pull request: a task transition is shared the moment it syncs, which is why a task becomes `done` after its code change has actually landed, not when the branch is ready.
25. Use `rdl save` and `rdl sync` for Rundol branches. Never redirect a local ref to a differently named remote ref, bypass the managed `pre-push` hook, or use force push. Run `rdl git boundary --json` again before the final sync.

One person may hold multiple roles, but roles, members, stakeholders, responsibilities, and decision boundaries remain explicit.
