# Rundol Project Governance

Treat lightweight delivery as an implementation choice, never as permission to remove governance or silently bypass the document contract.

## Workflow

1. Run `rdl init --json` first. Treat `created`, `already-connected`, `attached`, and `repaired` as connected states; select explicitly for `needs-selection`; stop on `conflict`. Read the returned `boundary` and run `rdl git boundary --project <key> --json`; do not continue while it reports violations.
2. For a new project, select a profile with guided setup or `--profile`. New projects always receive schemaVersion 2 `documentProfile`; never create an unconfigured project.
3. Before planning documents, run `rdl contract show --project <key> --json` and `rdl contract next --project <key> --json`. Read `catalog.granularity.typeResponsibilities` and `splitWhen` before choosing artifact boundaries. The CLI evaluator is authoritative; do not duplicate or reinterpret its rules in the skill.
4. Preserve every regular type (`PRD`, `REQ`, `ARC`, `SCR`, `MOD`, `API`, `ADR`, `TST`, `RUN`, `GLS`) in exactly one policy state. Preserve `enforcement`, every `rules.<TYPE>.after` AI context recommendation, and every disabled type's omission disposition.
5. Never create a disabled type. Treat `recommendedContext` and `missingRecommendedContext` from `rdl contract next` as authoring guidance, not as a creation or persistence gate. A present type is not proof that its subject area is complete; never satisfy the contract by creating one catch-all document per type.
6. In a Rundol-governed project, never create or use a generic `DESIGN.md` as a canonical source of truth. Route product and quality intent to `REQ`, UI flows and states to `SCR`, system structure to `ARC`, important decisions to `ADR`, and implementation work to `rdl task add`. If one of those types is disabled, follow its configured omission target and sections instead of creating `DESIGN.md`.
7. When a type is disabled, write its required omission sections into the configured `absorbedBy` document, or preserve an explicit not-applicable reason. Never treat omission as silent deletion.
8. Contract changes are explicit revisioned operations. Inspect `rdl contract plan` impact before `rdl contract set` or Board settings changes; do not delete or move existing documents as a side effect.
9. Read `references/governance-contract.md` before creating or revising project documents. Read `references/client-compatibility.md` only when installing or adapting the skill for another AI client.
10. Preserve the project charter's mission, goals, scope, roles, members, stakeholders, RACI, decisions, risks, cadence, and Definition of Done. Unknown information remains `미정` with an owner and follow-up task.
11. Use real Obsidian file names and block IDs for owners, reviewers, stakeholders, related artifacts, and task responsibility.
12. Before creating a document, enumerate candidate responsibilities and split them when owner or approver, acceptance criteria, lifecycle or review cadence, or primary consumers differ. Keep one primary responsibility per artifact; summaries link to narrower artifacts instead of duplicating their normative content.
13. Create documents only through `rdl doc create <TYPE> <title> --owner <MEMBER-ID> --scope <single-review-unit> --exclude <adjacent-out-of-scope>`, repeating `--exclude` when useful and adding required `--related` artifacts. For `REQ`, `SCR`, `MOD`, `API`, and `TST`, repeat `--function-id <FUNCTION-ID>` for every implemented function. The CLI-authored `bounded-v1` and `atomic-v1` metadata are mandatory for new implementation documents. Use canonical paths and review `rdl doc migrate` before applying a legacy move.
14. A file may contain several function IDs, but a specification must never group them. Reject ranges, combined rows, shared placeholder prose, shared acceptance criteria, or one test standing in for several functions. Every function ID must have the same complete type-specific contract it would receive in a standalone document.
15. Never create an INDEX, catalog, document list, or traceability-matrix artifact. Use direct document links and `rdl contract trace --project <key> --json`; traceability is a computed view, not another source of truth.
16. Read `catalog.diagrams` from `rdl contract show --project <key> --json` before authoring a type it covers. A `MOD` document carries a Mermaid `erDiagram` inside its `관계` section. The diagram is a derived view: tables stay canonical for cardinality, field constraints, and lifecycle, and the document states that precedence. Give attributes a type and `PK`/`FK` key only — never restate constraints, defaults, or lifecycle in attribute comments, because those belong to the entity table alone.
17. Decide every diagram element with `catalog.diagrams.conventions.<TYPE>.selection`, one question per element. Entity: does this document own the lifecycle? Owned entities show attributes, adjacent entities are bare nodes linked to their owning document, and needing several owned entities means checking for a dependent aggregate before splitting the document. Relationship: does a stored field create the reference? Draw only references stored as a foreign key or identifier, and leave relationships that exist only after replay or computation to their calculation section. Cardinality: is the constraint enforced at write time or at read time? A relationship line carries the stored cardinality only, so a read-time limit such as "at most one currently valid" stays in the invariant or calculation section. Never label a line with a derived concept while drawing its stored cardinality; that mixes the two clocks in one statement. State transitions have no place in relational notation and stay in the per-function 상태와 전이 contract.
18. A `SCR` document carries a Mermaid `flowchart` inside its `전이` section, canonical in the transition table above it, and lists only the moves that leave this screen — inbound moves belong to the screen that starts them. Every node is an `SCR` identifier: moving to another screen is a transition, changing what the current screen displays is a state, and a login failure rendering an error is the second even though it reads as a branch. Label an edge with what decides the move only; error copy, validation rules, permission differences, and timeouts stay in `바인딩` and `디자인에 없는 것`. A walked path with an expected result is a `TST` scenario, not a transition. Never recover the transition graph from scenarios — they walk representative paths, so any unwalked edge vanishes silently.
19. Never author a diagram spanning several documents. Run `rdl contract diagram --project <key> --json` to compute the merged data and screen views, and `--write` to place them in the Vault's Git-ignored `views/` for Obsidian. Composites are derived, never canonical, and never committed; fix the source document and regenerate. `rdl check` runs the same composition, so `RDL-COMPOSE-001` (two documents claiming attributes on one entity), `RDL-COMPOSE-002` (a transition pointing at a screen that does not exist), and `RDL-COMPOSE-003` (a generated view that no longer matches the canonical documents) surface without asking. Never fix `RDL-COMPOSE-003` by editing the generated file — that is the drift it detects.
20. Use `rdl task add`, `rdl task acceptance`, and the Board for tasks. Route only the 2–4 most relevant documents into an AI coding context.
21. Before implementation, run `rdl check --strict --implementation`. Do not implement while a linked function has unresolved rules or lacks an independent TST contract. Run `rdl check <ARTIFACT-ID> --strict` immediately after authoring, then `rdl contract check --project <key>` and `rdl check --strict`. Advisory findings guide the work; checkpoint violations block save, sync, and completion.
22. Run `rdl check --structure`; treat an existing `DESIGN.md` as a manual migration candidate and never delete it automatically. Apply cleanup only after reviewing every candidate.
23. Keep branch roles strict: application code belongs to the repository root's current code branch while the repository default is discovered from `origin/HEAD` (`main`, `master`, or a custom standard); project documents and tasks belong only to `rundol/<project-key>` through its linked worktree; registries, clients, leases, and Workspace presentation belong only to `rundol/workspace`. Never edit another role's files from the current worktree.
24. Use `rdl save` and `rdl sync` for Rundol branches. Never redirect a local ref to a differently named remote ref, bypass the managed `pre-push` hook, or use force push. Run `rdl git boundary --json` again before the final sync.

One person may hold multiple roles, but roles, members, stakeholders, responsibilities, and decision boundaries remain explicit.
